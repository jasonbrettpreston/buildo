# Project Lessons — Buildo
*Read this at session start. One-line gotchas that have already cost us time.*

## TypeScript
- `process.env.NODE_ENV = 'test'` fails — use `(process.env as Record<string, string>).NODE_ENV`
- Literal type narrowing: `const step = 1; step === 0` fails — use `const step: number = 1`
- `typeof globalThis.google` breaks in Next.js client — use `(window as any).google`
- tsconfig targets ES2017 — regex `s` flag (dotAll) requires ES2018+, use `[\s\S]` instead
- Next.js API routes cannot export non-handler functions — extract helpers to `src/lib/`
- `functions/` (Cloud Functions) was excluded from root tsconfig.json while it existed — DELETED 2026-07-20 (Supabase migration Phase 3.1)

## Database
- Composite PK is `(permit_num, revision_num)` — both required in ALL queries
- `CREATE INDEX` on tables >100K rows MUST use `CONCURRENTLY` or it locks production
- Notifications table columns are `is_read`/`is_sent` (not `read`/`sent`) — mapped in TS interfaces
- CoA column is `application_number`, aliased to `application_num` in SQL queries
- CoA column is `linked_confidence`, aliased to `link_confidence` in queries
- **Migration runner does NOT respect `-- UP` / `-- DOWN` markers** — they're SQL comments, not section directives. `scripts/migrate.js` runs the entire `.sql` file as one transaction. Any uncommented DROP/REVERT statement under `-- DOWN` will execute immediately after the UP section, silently undoing the migration. The migration is recorded as "applied" but the schema is unchanged. ALWAYS comment out every line of the DOWN section (match migration 114's convention). Discovered 2026-05-01 in migrations 113/115/116; backup → fix files → delete bogus `schema_migrations` rows → re-run was the recovery path.
- **`schema_migrations` row presence does NOT prove the schema changed** — it proves the file ran without erroring. Always verify with `\d table_name` after applying migrations that touch important tables.
- **`trigger_set_timestamp()` function from migration 100 may be missing** even when `schema_migrations` says 100 was applied (likely from a `pg_dump`/`pg_restore` cycle that didn't preserve the function). If a later migration fails with `function trigger_set_timestamp() does not exist`, recreate via `CREATE OR REPLACE FUNCTION trigger_set_timestamp() RETURNS TRIGGER AS $$ BEGIN NEW.updated_at = NOW(); RETURN NEW; END; $$ LANGUAGE plpgsql;`

## Pipeline
- `new Date()` is banned for timestamps written to DB — use `pipeline.getDbTimestamp(pool)`
- `pool.query` for advisory lock acquire/release is wrong — locks are session-bound, use a pinned client
- MAX_ROWS_PER_INSERT for permit_trades = 4000 (10 columns × 4000 = 40K params, under 65535 limit)
- **`IS DISTINCT FROM` idempotency guards break when the temp-table column type ≠ the target column type.** A set-based `UPDATE target SET … FROM temp WHERE … OR target.col IS DISTINCT FROM temp.col` is only idempotent if the compared types match. In `enrich-parcels.js` (Spec 65, 2026-05-31) a computed `zoning_dominant_area_share` was `float8` in the temp table (`MAX(area_share)`) but `NUMERIC(5,4)` on the target — so `0.6667` (numeric) vs `0.66666…` (float) compared **unequal on every run**, and every multi-zone parcel was rewritten forever (never reached its fixed point). Single-zone parcels (share exactly `1.0`) round-tripped cleanly and hid the bug. Caught only by running the script twice on live data (`updated` was non-zero on run 2). Fix: `round(MAX(area_share)::numeric, 4)` so the temp column matches the target precision. Guard: `enrich-parcels.db.test.ts` idempotency case now uses a MULTI-ZONE fixture (a single-zone fixture cannot catch this). Pattern: when an `UPDATE…FROM` writes a *computed* value into a typed column, cast/round it to the column's type in the SELECT.
- **A derived value that relies on an upstream DATA invariant must be guarded by an explicit CODE condition, not the invariant.** The as-of-right envelope cap (Spec 78, WF3 2026-07-02) derives the heritage storey cap as `round(max_buildable_gfa / max_buildable_footprint)` when `max_build_stories` is NULL — correct ONLY because the citywide storey-norm backstop means non-heritage parcels always get a non-null `max_build_stories` (so only heritage, whose ratio is an exact integer, ever derives). A reviewer flagged: if that backstop ever lapses, a non-heritage FSI-bound parcel (null stories + non-null `fsi×lot` GFA) would derive a FRACTIONAL-ratio `round()` → a spurious storey cap that UNDER-states opt_aor (the engine's fsiCap already bounds it — a storey cap there is wrong). Verified 0 such rows today, but fixed anyway: guard the derive on `max_buildable_gfa_basis='heritage_existing'` so the "only heritage derives" claim is enforced by code, not a fragile data assumption. Rule: when a fallback/derive is safe "because the data always looks like X", encode X as a predicate — data invariants drift, code guards don't.
- **A data-quality guard applied in ONE pass must be applied in EVERY pass that consumes the same source — else the passes silently disagree.** The existing-structure pass NULLs a primary-massing footprint > `lot×(1+mislink_tol)` (WRONG building linked); the max-build HERITAGE freeze read the SAME `SUM(footprint) FILTER(is_primary)` massing but WITHOUT the guard, so 2,455 heritage parcels froze to a mislinked oversized footprint → `footprint > lot` → FSI 20-1041 → multi-$M garbage cost (parcel 8809: 456 m² on 111 m²; 428548: FSI 1041). The `footprint_exceeds_lot` flag was ALREADY set on 2,304 of them by the other pass — the two passes disagreed on the same rows for months. Fix (WF3 2026-07-02): apply the identical guard (same `mislink_footprint_lot_tol` logic-var) to the heritage freeze. Rule: when two passes derive from the same dirty source, a guard on one is a latent bug on the other — grep every consumer of the source.
- **Nulling an upstream field does NOT clear downstream DERIVED fields whose pass GATES on it — the stale value survives and a COALESCE fallback re-prices it.** When the heritage fix NULLed `max_buildable_footprint_sqm`, `enrichOptimalConfig` (which streams `WHERE max_buildable_footprint_sqm IS NOT NULL`) simply SKIPPED those parcels → their `opt_aor_gfa_sqm` stayed STALE (1368 on 8809), and the cost model's `COALESCE(opt_aor, max_buildable_gfa)` still priced the stale opt_aor → the $8.9M garbage persisted even after a full re-run. A gate-on-X pass never revisits a row that loses X, so it can't clear that row's outputs. Fix: the pass must RESET its output cols for in-scope rows that lost eligibility (`UPDATE … SET opt_*=NULL WHERE footprint IS NULL AND opt_config_confidence IS NOT NULL`) BEFORE the stream. Rule: an incremental/gated enrichment needs an explicit reset for rows that fall OUT of its gate, or downstream consumers keep pricing ghosts. Caught by OUTPUT verification (re-cost still $8.9M), not the plan.
- **Postgres `MIN`/`LEAST` SILENTLY SKIP NULLs — a "most-restrictive" aggregate then borrows a value from a row that should not contribute.** `zoning-precedence.js` (Spec 65) aggregated `bylaw_max_fsi` across every base zone intersecting a parcel with rule `'min'` → `MIN(fsi_max)`. A dominantly-RD parcel whose real RD zone has **no** FSI cap (`fsi_max = NULL`) but which clips a `0.0 m²` sliver of a CR zone (`fsi_max = 2.0`) got `MIN(NULL, 2.0) = 2.0` — the 0%-area sliver's commercial FSI stamped onto the whole parcel (502/555 RD-FSI≥2 parcels; proven: the CR sliver contributes literally 0.0 m² yet dictated FSI). The SAME trap sits in `LEAST(buffer, box, coverage_cap)` for the max-build footprint: when `coverage_cap` is NULL (no bylaw coverage on ~37% of parcels) `LEAST` drops it and the footprint balloons to the uncapped setback box (~67% coverage → inflated GFA/cost). **Mitigation (WF3 2026-07-01):** for FSI, source from the area-**dominant** zone only (`(array_agg(fsi_max ORDER BY intersect_area DESC, …))[1]` → NULL when the dominant zone has none), NOT MIN; + a guard nulling corrupt residential `fsi_max > 10` before aggregation. Regression-locked in `enrich-parcels.db.test.ts` with a 3-case fixture (dominant-NULL+sliver → NULL; ambiguous → NULL; dominant 3.0 vs secondary 2.0 → 3.0 — the only case that catches a silent revert to MIN). Rule: when a "most-restrictive" aggregate spans rows that can legitimately be NULL, decide explicitly whether NULL means "no constraint" (→ don't let a non-NULL sibling win via MIN/LEAST; source from the authoritative/dominant row) or "unknown" — MIN/LEAST encode neither. **The coverage-cap NULL half was fixed the same day (WF3 `cdcc9d1`→next):** `coverage_cap = lot × COALESCE(bylaw_max_coverage_pct, zone-class default)` — a `COVERAGE_DEFAULTS` table in `max-build.js` (empirical medians RD/RS/RT 33, RM 30) fills the NULL so `LEAST` always has a coverage bound; counted `max_build_coverage_defaulted_count`/`_binding_count`; regression fixtures in `enrich-parcels-maxbuild.db.test.ts`.
- **Per-parcel correlated `EXISTS` subqueries do not scale; use set-based join CTEs.** `enrich-parcels.js` first computed 7 overlay memberships as correlated `EXISTS (SELECT 1 FROM overlay o WHERE ST_Intersects(p.geom, o.geom))` columns — O(parcels) spatial lookups that made the 486K-parcel run intractable (>9 min, no completion). Rewriting each as a set-based `mem_x AS (SELECT DISTINCT s.parcel_id FROM scope s JOIN overlay o ON …)` + `LEFT JOIN` (one GiST spatial join apiece) brought the full run to ~8 min. Same lesson for exact-area: compute `ST_Intersection(...)::geography` ONLY for multi-candidate parcels via a lazy `CASE WHEN COUNT(*) OVER (PARTITION BY id)=1 THEN 1.0 ELSE ST_Area(...) END` — single-zone parcels skip the expensive geometry construction.
- **`taskkill`/Ctrl-C on a node pipeline does NOT cancel its running Postgres query.** Killing the client leaves the backend executing (Postgres only notices the dead client when it next tries to send results). A heavy query (e.g. a geography `ST_DWithin` without a bbox prefilter) can run for HOURS post-kill, holding a `virtualxid` lock that blocks `CREATE INDEX CONCURRENTLY` indefinitely. Discovered 2026-05-31 (Spec 65): a killed spike query ran 3h and starved the index backfill. Recovery: `SELECT pg_terminate_backend(pid)` for the runaway query (find it via `pg_stat_activity WHERE state='active'` + `pg_blocking_pids()`), not just `taskkill`. Advisory-lock zombies show as `idle in transaction` and similarly need `pg_terminate_backend`.
- **A new pipeline script MUST be run end-to-end against the live DB before merge.** Spec 47 §R already mandates this; the discipline is enforcement. WF3 #realtor-backfill (2026-05-11) caught four bugs in `backfill-realtor-permit-trades.js` that all came from merging `2901fcd` (2026-05-06) without invoking the script even once: F1 NULL writes to a `NOT NULL DEFAULT` column → PG 23502 crash; F2 not registered in `scripts/manifest.json` so the chain orchestrator never invoked it; F3 advisory lock collision with another script (invisible until F2 was fixed because the Bundle G uniqueness test only iterates manifest entries); F4 SQL bypassed the 3-axis gate that the JS mirror applied (only observable once F1's crash was fixed). The unit-test suite was green on the original merge. **Green tests are not a substitute for running the script.** Sibling-bug check (WF3 §10 self-checklist) caught F4 only because R6 (Green Light → live verify) was scoped into the active task.
- INSERT...SELECT in pipeline scripts must omit columns that have schema-side `NOT NULL DEFAULT X` rather than write literal `NULL` — the explicit NULL overrides the default and trips `23502`. Pattern used by every other Spec 47 script.
- **Spec text and prior migration comments are NOT authoritative for column existence.** Before authorizing a Phase B/C/D pipeline script that filters or writes a column, grep `migrations/` for `ALTER TABLE <table>.*ADD COLUMN <col>` to confirm the column-add migration exists on disk. Discovered 2026-05-14 in `migrate-to-lead-id.js` — referenced `tracked_projects.lead_type` which Spec 42 §6.5/§6.6.C/§6.11 + migration 140's comment block all claimed existed, but no migration ever added it (the only `lead_type` column is on `lead_views` via mig 070). The R5.3 trigger-based dual-write pivot (commit `872ec73`) made the column unnecessary but the cleanup of spec/script/comment references was missed. Pre-flight check: `SELECT column_name FROM information_schema.columns WHERE table_name='<t>' AND column_name='<c>'`.
- **Lead-keyed canonicalization functions collide when source data has equivalent-but-distinct values.** The Phase B `deriveLeadId` uses `LPAD(revision_num, 2, '0')` to produce a canonical `permit:<num>:<rev>` form. Toronto's `permit_type='DCs DeferredFees'` administrative sub-records have `revision_num='0'` (single char) while the main building permit at the same `permit_num` has `revision_num='00'` (two char). Both LPAD to `'00'`, producing identical `lead_id` values for two genuinely distinct permits — discovered 2026-05-14 when migration 138's UNIQUE pre-check found 136 collisions. **Mitigation pattern:** exclude administrative-class records (`permit_type_classifications.class='administrative'`) from the lead_id ecosystem at every write site — matches the de-facto pattern already in `classify-permits.js` (gates `permit_trades` on class='construction') and `compute-cost-estimates.js` (writes `cost_source='none'` for admin). See WF3 #lpad-revision-num-collision (mig 138_a) for the full fix. Before introducing a one-shot canonicalization backfill, verify that the canonical form is *injective* over the source's value space — `SELECT permit_num, LPAD(rev,2,'0') FROM permits GROUP BY 1,2 HAVING COUNT(*)>1` catches the class of issue.
- **UNIQUE constraint shape must match the table's natural cardinality, not the column being keyed on.** Migration 139 promoted `UNIQUE(lead_id)` on `trade_forecasts` despite the table being 1-row-per-(permit, trade_slug) by design — every permit has multiple forecast rows (one per trade slug) all sharing the same lead_id, so single-column UNIQUE on lead_id can never be satisfied. Spec 42 §6.6.C explicitly states the intent: `"PK becomes (lead_id, trade_slug) after backfill"` — the migration just used the wrong column set. Discovered 2026-05-14 when mig 139's Stage-2 pre-check returned 91,724 dups on every populated DB. **Mitigation:** before authorizing a `CREATE UNIQUE INDEX` migration, run the candidate Stage-2 query against the live dev DB to verify the proposed key set actually deduplicates the data — `SELECT COUNT(*) FROM (SELECT <key cols> FROM <table> GROUP BY <key cols> HAVING COUNT(*)>1) d` must return 0. This is now part of the WF3 R0 audit checklist for any migration that promotes a UNIQUE constraint.

## Mobile / Expo
- `tradeSlug` in filterStore defaults to `''` (empty string = falsy) — feed query won't fire until set
- `radius_km` is now server-side (added to `user_profiles` in migration 114) — MMKV is cache only; `user_profiles` is authoritative. `useUserProfile` hydrates filterStore from server on launch.
- Maestro `assertVisible` on Android reads rendered text, not raw source — `uppercase` CSS → assert "LEAD FEED" not "Lead Feed"
- `useRootNavigationState().key` is undefined until the navigation container mounts — guard `router.replace()` behind it
- Deprecated/archived Expo packages can ship native code that breaks silently on Gradle toolchain bumps. `expo-firebase-recaptcha` (transitively `expo-firebase-core@6.0.0`) used the legacy `classifier` Jar property which Gradle 8 removed — `expo run:android` failed with "Could not set unknown property 'classifier'". Audit `package.json` against Expo's deprecation list before any Expo SDK / Gradle bump.
- Apple Sign-In with `@react-native-firebase/auth` requires nonce round-trip: SHA-256 hash to `AppleAuthentication.signInAsync({ nonce: hashedNonce })`, raw value to `auth.AppleAuthProvider.credential(idToken, rawNonce)`. Reversing them produces `auth/invalid-credential`.
- Phone-auth on RNFirebase uses confirmation-style API: `auth().signInWithPhoneNumber(num)` returns a `ConfirmationResult` whose `.confirm(code)` resolves the credential. No JS-side reCAPTCHA — Play Integrity (Android) / APN silent-push (iOS) handle bot prevention natively.
- `transformIgnorePatterns` in `mobile/package.json` jest config must explicitly include `@react-native-firebase` (the existing `@react-native(-community)?` regex matches the prefix but the lookahead won't extend to `-firebase`).
- **Android emulator default GPS is Mountain View, CA** (37.4, -122.08) — Buildo's permits are Toronto-only, so a user choosing "Live Feed" (`location_mode='gps_live'`) on a stock emulator gets ZERO matches and an empty feed. Set the emulator location to Toronto before testing the feed: Android Studio Extended Controls (`...` button) → Location → enter `43.6532` (lat), `-79.3832` (lng) → "Send"; OR `adb emu geo fix -79.3832 43.6532` (note: ADB takes longitude THEN latitude, opposite of every other API).
- **Before adding a new Zustand store, MMKV blob, hydration bridge, or routing useEffect on mobile — check `docs/specs/03-mobile/99_mobile_state_architecture.md` §3-§5.** The field may already be owned elsewhere; the bridge may not be allowed; the routing decision may belong to AuthGate or AppLayout (Spec 99 §5.1). Spec 99 was authored 2026-05-02 after three render-loop incidents in one session traced to undeclared dual-source-of-truth state. Adding state without a Spec 99 row is a §10 compliance failure.
- **Two layout-level `router.replace` effects reading DIFFERENT sources of truth for the same routing decision will ping-pong** — `mobile/app/_layout.tsx` AuthGate read SERVER `profile.onboarding_complete`; `mobile/app/(onboarding)/_layout.tsx` read LOCAL `useOnboardingStore.isComplete`. When server cache held a stale `dev-user` profile (`onboarding_complete=false`) but local store was `isComplete=true` (from a prior `markComplete()` bridge), AuthGate routed `(app)→(onboarding)` while OnboardingLayout routed `(onboarding)→(app)`, alternating ~36 times before Maximum update depth exceeded. Rule: ONE routing authority per gate boundary, reading ONE source of truth (prefer the server profile — Spec 95 §6 makes server-side fields canonical). Discovered 2026-05-02 via `mobile/src/lib/debug/loopDetector.ts` instrumentation; fix in same-session WF3 stripped OnboardingLayout's effect + added UID-change cache invalidation in `initFirebaseAuthListener` to keep `react-query` MMKV cache from leaking across users.
- **Subscribing to Zustand store inside `RootLayout`/`AuthGate` causes render loops if combined with `router.replace` in the effect** — `useStore((s) => s.field)` re-renders the component on every store mutation, so if the effect deps include the subscribed value AND the effect calls `router.replace`, the chain `setStore → re-render → effect fires → router.replace → segments change → re-render → ...` can ping-pong with `(onboarding)/_layout.tsx`'s competing redirect. Use lazy `useStore.getState().field` inside the effect closure when you only need the value at the moment the effect actually runs (not on every change). Discovered 2026-05-02 post-WF2 `3727ceb`; fixed in same-session WF3.

## ESLint / Tooling
- `scripts/CLAUDE.md` must NOT use `@` auto-imports — they load into every session including Admin/WF7
- `scripts/*.js` are CommonJS — not linted for `no-require-imports`
- ESLint flat config (`eslint.config.mjs`) must ignore: `.next/`, `next-env.d.ts`, `scripts/` (`functions/` was on this list until its 2026-07-20 deletion)
- **`scripts/` is unlinted (eslint ignores it) AND untyped (tsc is TS-only), so a JS syntax error in a pipeline loader has ZERO CI coverage unless a test parses the file.** `scripts/load-parcels.js` was committed (2026-05-23, `10db268`) with a backtick inside its multi-line SQL template literal — an SQL `--` comment reading `` passes `null` for missing columns ``. The first backtick terminated the JS template literal early → `SyntaxError: missing ) after argument list` → the file never parsed → the sources chain hard-failed at step 4 (`parcels`) for a week. The husky pre-commit hook (typecheck + lint + test) caught nothing: `tsc` skips `.js`, eslint ignores `scripts/`, and no test required the loader. **Mitigation (WF3 2026-05-30):** give every pipeline loader a parse-smoke test — `expect(() => execFileSync('node', ['--check', loaderPath], { stdio: 'pipe' })).not.toThrow()` (see `src/tests/load-parcels.parse.smoke.test.ts`). Use `node --check`, NOT `require()`: loaders that call `pipeline.run(...)` unconditionally at module scope (no `require.main === module` guard — e.g. `load-parcels.js`, unlike `load-zoning.js`/`load-permits.js`) would fire a real DB-connecting pipeline run as an unawaited background side-effect when `require()`'d inside a test.
- **A per-row scalar derived from a known-dirty upstream column must be range-guarded against its DB column width BEFORE the batched write, or ONE artifact row aborts the entire mutation.** The parcel cost model (`88`, `aea1d40`) wrote `max_build_fsi` = `max_buildable_gfa_sqm ÷ lot_size_sqm` straight into `NUMERIC(6,3)` (max 999.999). ~1,300 residential parcels carry a garbage `max_buildable_gfa` (tree-contaminated massing / setback-box artifacts — see the max-build accuracy investigation), e.g. parcel 428548: 115,825 m² max-build on a 111 m² lot → FSI 1042 → `numeric field overflow` on the batched `UPDATE … FROM (VALUES …)`, which aborts the whole batch (NOT caught by the per-row engine try/catch — the error is at the DB write layer, not the pure engine). The P1 full-population run silently aborted on this (its "393K menus" was a partial write, masked by a background-command pipe); the P2 re-run surfaced it. **Mitigation:** the engine NULLs an implausible FSI (`FSI_MAX_PLAUSIBLE = 99.999` — nothing residential legitimately reaches 100) and emits an `fsi_implausible_count` audit row (surfaced, not hidden). Applies to ANY ratio/gfa-per-lot scalar written to a narrow NUMERIC from a column with documented dirty rows — guard the value against the column bound in the pure engine, count the drops.

## Web Admin
- **The admin specs claimed a UI kit the repo doesn't have — verify UI-kit presence before planning components.** Spec 33 §4/§6 + `.claude/domain-admin.md` mandated composing from **shadcn/ui**, but shadcn is NOT initialized (no `components.json`; `src/components/ui/` = `Badge`+`ScoreBadge`), and `lucide-react`/`react-hook-form`/`recharts`/`@tremor/react`/`motion` are ALL absent from `package.json`. This misled the P15 Flight Center plan (2026-07-09, commits `4bf6050..d4db75f`). The real convention: Tailwind + hand-rolled native elements, `role="alertdialog"` for destructive confirms (`ConfirmSyncModal.tsx` precedent), inline `<svg>` icons, `useState`+Zod forms, Sonner toasts. **Before planning any admin component, `grep package.json` for the library you're about to `import` — a spec naming a tool is NOT evidence it's installed.** (Corrected in Spec 33 §4/§6 + domain-admin, 2026-07-10.)
- **Worktree-isolated reviewers cannot see untracked files — inventory from the MAIN tree.** Review agents spawned with `isolation: "worktree"` (Gemini/DeepSeek/Code Reviewer) work on a committed copy; a brand-new store/hook/component that isn't committed yet is invisible to them, so they can't verify "does `session.ts` enumerate every store?" or "does this precedent file exist?". Run inventory/existence checks from the main tree (Integration + Regression Guardian already run there for this reason). P15 learning.
- **Admin telemetry is TWO helpers — `track()` is server-side, `captureEvent()` is client-side.** Server route handlers call `track(distinctId, event, props)` (`src/lib/admin/analytics.ts`) with a HASHED uid (`sha256(uid).slice(0,16)`); client hooks call `captureEvent(event, props)` (`src/lib/observability/capture.ts`) + `Sentry.addBreadcrumb(...)` BEFORE the network call. Read-only surfaces emit `captureEvent` only (no `admin_action` breadcrumb — it's mutation-scoped). Using the wrong helper for the side silently drops the event (`captureEvent` no-ops off-browser; `track` needs a distinctId). Spec 33 §11 / Spec 35 §7.1.
- **Per-admin identity exists ONLY on the `session` auth path.** `verifyAdminAuth` returns a real Firebase uid only when `authMethod==='session'` (`ADMIN_USER_IDS` allowlist); `admin_key`→`'admin-key'` and `dev_bypass`→`'dev-user'` are SHARED sentinels, not personal identities. Any feature writing per-admin-scoped rows (watchlist, per-admin draft) MUST gate mutations on `authMethod==='session'` and 403 on `admin_key` (the Spec 36 PF1 pattern, Spec 33 §8.1). P15 learning.

## Footgun gate: inline ast-grep suppressions DO NOT work (2026-07-19)
`// ast-grep-disable-next-line <rule-id>` comments are ignored by the pre-commit footgun runner (verified twice: sql-now, silent-catch-fallback — both failed with the comment correctly placed, bare-form, directly above the node). Working remedies, in order: (1) refactor to genuinely satisfy the rule (e.g. `URL.canParse` instead of try/catch; parameterized timestamp instead of NOW()); (2) file-level entry in `scripts/amnesty.json` for operator/seed CLIs (bare-mutation etc.). Do not burn commit cycles on suppression comments. Also: the gate scans the WHOLE working tree, not the staged set — an untracked script with a violation blocks unrelated commits.

## Cloud DB / GitHub Actions scheduling (2026-07-29)
- **Migration checksums must be line-ending invariant.** 28 migrations were applied from a Windows worktree whose on-disk files were CRLF while their git blobs are LF; `schema_migrations.checksum` recorded the CRLF hash, so the first Linux-runner checkout (LF) reported 28 false DRIFTs and failed the chain pre-flight (`migrate.js --verify`) — invisible locally because the local worktree carries the same CRLF bytes the DB recorded. `migrate.js` now CRLF→LF-normalizes before sha256; pre-normalization rows were reconciled by `scripts/analysis/reconcile-migration-checksums.js` (idempotent, per-row checksum-guarded). Any future content-hash that must agree across platforms needs the same normalization.
- **The Supavisor session-mode pooler DROPS startup parameters — verify session-config assumptions LIVE against the pooler.** Both the startup-packet `options` string AND pg's `statement_timeout` config param are silently ignored through `aws-0-*.pooler.supabase.com:5432` (each "worked" locally/direct and failed against the pooler; all three mechanisms were tested live before shipping). Only a session-level `SET` on the established connection sticks. Corollary: the cloud session default `statement_timeout` is **2min** (cluster default, no role setting) — it killed `link_wsib` mid-chain on the first GH dispatch. Pipeline pools now wrap `pool.connect` with a once-per-client awaited `SET statement_timeout` (default 0, `PIPELINE_STATEMENT_TIMEOUT_MS` override); a bare `pool.on('connect')` SET races the first checked-out query (deprecation-warns on pg@8, breaks on pg@9).
