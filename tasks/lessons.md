# Project Lessons — Buildo
*Read this at session start. One-line gotchas that have already cost us time.*

---

## TypeScript
- `process.env.NODE_ENV = 'test'` fails — use `(process.env as Record<string, string>).NODE_ENV`
- Literal type narrowing: `const step = 1; step === 0` fails — use `const step: number = 1`
- `typeof globalThis.google` breaks in Next.js client — use `(window as any).google`
- tsconfig targets ES2017 — regex `s` flag (dotAll) requires ES2018+, use `[\s\S]` instead
- Next.js API routes cannot export non-handler functions — extract helpers to `src/lib/`
- `functions/` (Cloud Functions) was excluded from root tsconfig.json while it existed — DELETED 2026-07-20 (Supabase migration Phase 3.1)

## Database
- Composite PK is `(permit_num, revision_num)` — both required in ALL queries
- `CREATE INDEX` on tables >100K rows MUST use `CONCURRENTLY` or it locks production
- Notifications table columns are `is_read`/`is_sent` (not `read`/`sent`) — mapped in TS interfaces
- CoA column is `application_number`, aliased to `application_num` in SQL queries
- CoA column is `linked_confidence`, aliased to `link_confidence` in queries
- **Migration runner does NOT respect `-- UP` / `-- DOWN` markers** — they're SQL comments, not section directives. `scripts/migrate.js` runs the entire `.sql` file as one transaction. Any uncommented DROP/REVERT statement under `-- DOWN` will execute immediately after the UP section, silently undoing the migration. The migration is recorded as "applied" but the schema is unchanged. ALWAYS comment out every line of the DOWN section (match migration 114's convention). Discovered 2026-05-01 in migrations 113/115/116; backup → fix files → delete bogus `schema_migrations` rows → re-run was the recovery path.
- **`schema_migrations` row presence does NOT prove the schema changed** — it proves the file ran without erroring. Always verify with `\d table_name` after applying migrations that touch important tables.
- **`trigger_set_timestamp()` function from migration 100 may be missing** even when `schema_migrations` says 100 was applied (likely from a `pg_dump`/`pg_restore` cycle that didn't preserve the function). If a later migration fails with `function trigger_set_timestamp() does not exist`, recreate via `CREATE OR REPLACE FUNCTION trigger_set_timestamp() RETURNS TRIGGER AS $$ BEGIN NEW.updated_at = NOW(); RETURN NEW; END; $$ LANGUAGE plpgsql;`

## Pipeline
- `new Date()` is banned for timestamps written to DB — use `pipeline.getDbTimestamp(pool)`
- `pool.query` for advisory lock acquire/release is wrong — locks are session-bound, use a pinned client
- MAX_ROWS_PER_INSERT for permit_trades = 4000 (10 columns × 4000 = 40K params, under 65535 limit)
- **`IS DISTINCT FROM` idempotency guards break when the temp-table column type ≠ the target column type.** A set-based `UPDATE target SET … FROM temp WHERE … OR target.col IS DISTINCT FROM temp.col` is only idempotent if the compared types match. In `enrich-parcels.js` (Spec 65, 2026-05-31) a computed `zoning_dominant_area_share` was `float8` in the temp table (`MAX(area_share)`) but `NUMERIC(5,4)` on the target — so `0.6667` (numeric) vs `0.66666…` (float) compared **unequal on every run**, and every multi-zone parcel was rewritten forever (never reached its fixed point). Single-zone parcels (share exactly `1.0`) round-tripped cleanly and hid the bug. Caught only by running the script twice on live data (`updated` was non-zero on run 2). Fix: `round(MAX(area_share)::numeric, 4)` so the temp column matches the target precision. Guard: `enrich-parcels.db.test.ts` idempotency case now uses a MULTI-ZONE fixture (a single-zone fixture cannot catch this). Pattern: when an `UPDATE…FROM` writes a *computed* value into a typed column, cast/round it to the column's type in the SELECT.
- **A derived value that relies on an upstream DATA invariant must be guarded by an explicit CODE condition, not the invariant.** The as-of-right envelope cap (Spec 78, WF3 2026-07-02) derives the heritage storey cap as `round(max_buildable_gfa / max_buildable_footprint)` when `max_build_stories` is NULL — correct ONLY because the citywide storey-norm backstop means non-heritage parcels always get a non-null `max_build_stories` (so only heritage, whose ratio is an exact integer, ever derives). A reviewer flagged: if that backstop ever lapses, a non-heritage FSI-bound parcel (null stories + non-null `fsi×lot` GFA) would derive a FRACTIONAL-ratio `round()` → a spurious storey cap that UNDER-states opt_aor (the engine's fsiCap already bounds it — a storey cap there is wrong). Verified 0 such rows today, but fixed anyway: guard the derive on `max_buildable_gfa_basis='heritage_existing'` so the "only heritage derives" claim is enforced by code, not a fragile data assumption. Rule: when a fallback/derive is safe "because the data always looks like X", encode X as a predicate — data invariants drift, code guards don't.
- **A data-quality guard applied in ONE pass must be applied in EVERY pass that consumes the same source — else the passes silently disagree.** The existing-structure pass NULLs a primary-massing footprint > `lot×(1+mislink_tol)` (WRONG building linked); the max-build HERITAGE freeze read the SAME `SUM(footprint) FILTER(is_primary)` massing but WITHOUT the guard, so 2,455 heritage parcels froze to a mislinked oversized footprint → `footprint > lot` → FSI 20-1041 → multi-$M garbage cost (parcel 8809: 456 m² on 111 m²; 428548: FSI 1041). The `footprint_exceeds_lot` flag was ALREADY set on 2,304 of them by the other pass — the two passes disagreed on the same rows for months. Fix (WF3 2026-07-02): apply the identical guard (same `mislink_footprint_lot_tol` logic-var) to the heritage freeze. Rule: when two passes derive from the same dirty source, a guard on one is a latent bug on the other — grep every consumer of the source.
- **Nulling an upstream field does NOT clear downstream DERIVED fields whose pass GATES on it — the stale value survives and a COALESCE fallback re-prices it.** When the heritage fix NULLed `max_buildable_footprint_sqm`, `enrichOptimalConfig` (which streams `WHERE max_buildable_footprint_sqm IS NOT NULL`) simply SKIPPED those parcels → their `opt_aor_gfa_sqm` stayed STALE (1368 on 8809), and the cost model's `COALESCE(opt_aor, max_buildable_gfa)` still priced the stale opt_aor → the $8.9M garbage persisted even after a full re-run. A gate-on-X pass never revisits a row that loses X, so it can't clear that row's outputs. Fix: the pass must RESET its output cols for in-scope rows that lost eligibility (`UPDATE … SET opt_*=NULL WHERE footprint IS NULL AND opt_config_confidence IS NOT NULL`) BEFORE the stream. Rule: an incremental/gated enrichment needs an explicit reset for rows that fall OUT of its gate, or downstream consumers keep pricing ghosts. Caught by OUTPUT verification (re-cost still $8.9M), not the plan.
- **Postgres `MIN`/`LEAST` SILENTLY SKIP NULLs — a "most-restrictive" aggregate then borrows a value from a row that should not contribute.** `zoning-precedence.js` (Spec 65) aggregated `bylaw_max_fsi` across every base zone intersecting a parcel with rule `'min'` → `MIN(fsi_max)`. A dominantly-RD parcel whose real RD zone has **no** FSI cap (`fsi_max = NULL`) but which clips a `0.0 m²` sliver of a CR zone (`fsi_max = 2.0`) got `MIN(NULL, 2.0) = 2.0` — the 0%-area sliver's commercial FSI stamped onto the whole parcel (502/555 RD-FSI≥2 parcels; proven: the CR sliver contributes literally 0.0 m² yet dictated FSI). The SAME trap sits in `LEAST(buffer, box, coverage_cap)` for the max-build footprint: when `coverage_cap` is NULL (no bylaw coverage on ~37% of parcels) `LEAST` drops it and the footprint balloons to the uncapped setback box (~67% coverage → inflated GFA/cost). **Mitigation (WF3 2026-07-01):** for FSI, source from the area-**dominant** zone only (`(array_agg(fsi_max ORDER BY intersect_area DESC, …))[1]` → NULL when the dominant zone has none), NOT MIN; + a guard nulling corrupt residential `fsi_max > 10` before aggregation. Regression-locked in `enrich-parcels.db.test.ts` with a 3-case fixture (dominant-NULL+sliver → NULL; ambiguous → NULL; dominant 3.0 vs secondary 2.0 → 3.0 — the only case that catches a silent revert to MIN). Rule: when a "most-restrictive" aggregate spans rows that can legitimately be NULL, decide explicitly whether NULL means "no constraint" (→ don't let a non-NULL sibling win via MIN/LEAST; source from the authoritative/dominant row) or "unknown" — MIN/LEAST encode neither. **The coverage-cap NULL half was fixed the same day (WF3 `cdcc9d1`→next):** `coverage_cap = lot × COALESCE(bylaw_max_coverage_pct, zone-class default)` — a `COVERAGE_DEFAULTS` table in `max-build.js` (empirical medians RD/RS/RT 33, RM 30) fills the NULL so `LEAST` always has a coverage bound; counted `max_build_coverage_defaulted_count`/`_binding_count`; regression fixtures in `enrich-parcels-maxbuild.db.test.ts`.
- **Per-parcel correlated `EXISTS` subqueries do not scale; use set-based join CTEs.** `enrich-parcels.js` first computed 7 overlay memberships as correlated `EXISTS (SELECT 1 FROM overlay o WHERE ST_Intersects(p.geom, o.geom))` columns — O(parcels) spatial lookups that made the 486K-parcel run intractable (>9 min, no completion). Rewriting each as a set-based `mem_x AS (SELECT DISTINCT s.parcel_id FROM scope s JOIN overlay o ON …)` + `LEFT JOIN` (one GiST spatial join apiece) brought the full run to ~8 min. Same lesson for exact-area: compute `ST_Intersection(...)::geography` ONLY for multi-candidate parcels via a lazy `CASE WHEN COUNT(*) OVER (PARTITION BY id)=1 THEN 1.0 ELSE ST_Area(...) END` — single-zone parcels skip the expensive geometry construction.
- **`taskkill`/Ctrl-C on a node pipeline does NOT cancel its running Postgres query.** Killing the client leaves the backend executing (Postgres only notices the dead client when it next tries to send results). A heavy query (e.g. a geography `ST_DWithin` without a bbox prefilter) can run for HOURS post-kill, holding a `virtualxid` lock that blocks `CREATE INDEX CONCURRENTLY` indefinitely. Discovered 2026-05-31 (Spec 65): a killed spike query ran 3h and starved the index backfill. Recovery: `SELECT pg_terminate_backend(pid)` for the runaway query (find it via `pg_stat_activity WHERE state='active'` + `pg_blocking_pids()`), not just `taskkill`. Advisory-lock zombies show as `idle in transaction` and similarly need `pg_terminate_backend`.
- **A new pipeline script MUST be run end-to-end against the live DB before merge.** Spec 47 §R already mandates this; the discipline is enforcement. WF3 #realtor-backfill (2026-05-11) caught four bugs in `backfill-realtor-permit-trades.js` that all came from merging `2901fcd` (2026-05-06) without invoking the script even once: F1 NULL writes to a `NOT NULL DEFAULT` column → PG 23502 crash; F2 not registered in `scripts/manifest.json` so the chain orchestrator never invoked it; F3 advisory lock collision with another script (invisible until F2 was fixed because the Bundle G uniqueness test only iterates manifest entries); F4 SQL bypassed the 3-axis gate that the JS mirror applied (only observable once F1's crash was fixed). The unit-test suite was green on the original merge. **Green tests are not a substitute for running the script.** Sibling-bug check (WF3 §10 self-checklist) caught F4 only because R6 (Green Light → live verify) was scoped into the active task.
- INSERT...SELECT in pipeline scripts must omit columns that have schema-side `NOT NULL DEFAULT X` rather than write literal `NULL` — the explicit NULL overrides the default and trips `23502`. Pattern used by every other Spec 47 script.
- **Spec text and prior migration comments are NOT authoritative for column existence.** Before authorizing a Phase B/C/D pipeline script that filters or writes a column, grep `migrations/` for `ALTER TABLE <table>.*ADD COLUMN <col>` to confirm the column-add migration exists on disk. Discovered 2026-05-14 in `migrate-to-lead-id.js` — referenced `tracked_projects.lead_type` which Spec 42 §6.5/§6.6.C/§6.11 + migration 140's comment block all claimed existed, but no migration ever added it (the only `lead_type` column is on `lead_views` via mig 070). The R5.3 trigger-based dual-write pivot (commit `872ec73`) made the column unnecessary but the cleanup of spec/script/comment references was missed. Pre-flight check: `SELECT column_name FROM information_schema.columns WHERE table_name='<t>' AND column_name='<c>'`.
- **Lead-keyed canonicalization functions collide when source data has equivalent-but-distinct values.** The Phase B `deriveLeadId` uses `LPAD(revision_num, 2, '0')` to produce a canonical `permit:<num>:<rev>` form. Toronto's `permit_type='DCs DeferredFees'` administrative sub-records have `revision_num='0'` (single char) while the main building permit at the same `permit_num` has `revision_num='00'` (two char). Both LPAD to `'00'`, producing identical `lead_id` values for two genuinely distinct permits — discovered 2026-05-14 when migration 138's UNIQUE pre-check found 136 collisions. **Mitigation pattern:** exclude administrative-class records (`permit_type_classifications.class='administrative'`) from the lead_id ecosystem at every write site — matches the de-facto pattern already in `classify-permits.js` (gates `permit_trades` on class='construction') and `compute-cost-estimates.js` (writes `cost_source='none'` for admin). See WF3 #lpad-revision-num-collision (mig 138_a) for the full fix. Before introducing a one-shot canonicalization backfill, verify that the canonical form is *injective* over the source's value space — `SELECT permit_num, LPAD(rev,2,'0') FROM permits GROUP BY 1,2 HAVING COUNT(*)>1` catches the class of issue.
- **UNIQUE constraint shape must match the table's natural cardinality, not the column being keyed on.** Migration 139 promoted `UNIQUE(lead_id)` on `trade_forecasts` despite the table being 1-row-per-(permit, trade_slug) by design — every permit has multiple forecast rows (one per trade slug) all sharing the same lead_id, so single-column UNIQUE on lead_id can never be satisfied. Spec 42 §6.6.C explicitly states the intent: `"PK becomes (lead_id, trade_slug) after backfill"` — the migration just used the wrong column set. Discovered 2026-05-14 when mig 139's Stage-2 pre-check returned 91,724 dups on every populated DB. **Mitigation:** before authorizing a `CREATE UNIQUE INDEX` migration, run the candidate Stage-2 query against the live dev DB to verify the proposed key set actually deduplicates the data — `SELECT COUNT(*) FROM (SELECT <key cols> FROM <table> GROUP BY <key cols> HAVING COUNT(*)>1) d` must return 0. This is now part of the WF3 R0 audit checklist for any migration that promotes a UNIQUE constraint.
- **Template-literal interpolation of a check's `value` is a hidden-rendering defect, not a display nicety.** `scripts/lib/step/verdict.js`'s `errors[]` builder did `` `${check.id}: ${row.value}` `` — fine while every `detail` was a primitive, but 9 sites across `scripts/lib/compute/*.js` report an object-valued `detail`, so the message silently rendered the literal string `"[object Object]"` and lost the actual value (LM-D16, caught live in a captured golden's `records_meta.errors`, then shown verbatim to operators by `FreshnessTimeline.tsx`). Always route a check/row value through a dedicated renderer (`renderValue` — primitives as-is, objects/arrays via sorted-key JSON, capped length) before interpolating it into any message string; never assume a reported value stays a primitive just because it does today.
- **A checker that scores 1/1 on the ABSENCE of a claim (rather than the PRESENCE of proof) is a vacuous-green waiting to happen.** `step-validate.mjs`'s `scoreG2` checked only whether a report claimed `ASSESSMENT-INCOMPLETE`; if it never wrote that literal string, the gate scored a full 1/1 "vacuously satisfied" — with zero evidence the thing it claims to check (a churn×complexity plot) had ever been produced. Every one of 6 real assessment reports scored this way for weeks before it was noticed (Spec 123 §6, confirmed live 2026-08-29). Rule: a gate's PASS branch must require positive evidence the underlying artifact exists (mirror the OTHER gates' own `section()` convention — look for the actual section), never fall through to a pass merely because a negative-claim string is absent. Fixed R-T addendum commit 6, 2026-08-30 (`docs/specs/01-pipeline/123_step_opt_assessment_validation.md:313`).
- **A markdown pipe-table row split (`line.split(/(?<!\\)\|/)`) will silently absorb a missing column** — it does not know the table's declared column COUNT, only where the pipes are, so a hand-edited row missing one cell shifts every LATER cell one column left and the parser never notices. `docs/reports/defect-ledger.md`'s `LM-D13` row was missing its "Step" column entirely (every sibling `LM-D*` row has it); the OLD reader silently read the Anchor cell as if it were Status, failed a vocabulary match, and miscounted the row as "not CLOSED/PIN" for the wrong reason. Caught only once the parser was rewritten to assert the FULL declared column count and throw on a mismatch (R-T addendum commit 6, `parseDefectLedgerRow`), which then surfaced the real, pre-existing data defect on its first live run. Rule: a fixed-width table parsed by pipe-position must validate cell COUNT against the header, not just extract whatever position N happens to land on.
- **`require()`ing an `.mjs` file synchronously from a `.ts`/CJS test works on Node ≥22.12** (this repo runs Node 24) — `require('../../scripts/analysis/some-tool.mjs')` resolves and returns the module's named exports directly (no `.default` wrapper), letting a `.mjs` CLI tool export pure functions for unit-testing without needing a `createRequire`/dynamic-`import()` dance in the TEST file itself (the tool's OWN internals still need `createRequire` to `require()` CJS libraries from inside an ESM file). Verified live, R-T addendum commit 5 (`src/tests/chain-end-synthesis.logic.test.ts`, `src/tests/db/chain-end-synthesis.db.test.ts`) — do not assume `ERR_REQUIRE_ESM` without checking the actual Node version first.

## Mobile / Expo
- `tradeSlug` in filterStore defaults to `''` (empty string = falsy) — feed query won't fire until set
- `radius_km` is now server-side (added to `user_profiles` in migration 114) — MMKV is cache only; `user_profiles` is authoritative. `useUserProfile` hydrates filterStore from server on launch.
- Maestro `assertVisible` on Android reads rendered text, not raw source — `uppercase` CSS → assert "LEAD FEED" not "Lead Feed"
- `useRootNavigationState().key` is undefined until the navigation container mounts — guard `router.replace()` behind it
- Deprecated/archived Expo packages can ship native code that breaks silently on Gradle toolchain bumps. `expo-firebase-recaptcha` (transitively `expo-firebase-core@6.0.0`) used the legacy `classifier` Jar property which Gradle 8 removed — `expo run:android` failed with "Could not set unknown property 'classifier'". Audit `package.json` against Expo's deprecation list before any Expo SDK / Gradle bump.
- Apple Sign-In with `@react-native-firebase/auth` requires nonce round-trip: SHA-256 hash to `AppleAuthentication.signInAsync({ nonce: hashedNonce })`, raw value to `auth.AppleAuthProvider.credential(idToken, rawNonce)`. Reversing them produces `auth/invalid-credential`.
- Phone-auth on RNFirebase uses confirmation-style API: `auth().signInWithPhoneNumber(num)` returns a `ConfirmationResult` whose `.confirm(code)` resolves the credential. No JS-side reCAPTCHA — Play Integrity (Android) / APN silent-push (iOS) handle bot prevention natively.
- `transformIgnorePatterns` in `mobile/package.json` jest config must explicitly include `@react-native-firebase` (the existing `@react-native(-community)?` regex matches the prefix but the lookahead won't extend to `-firebase`).
- **Android emulator default GPS is Mountain View, CA** (37.4, -122.08) — Buildo's permits are Toronto-only, so a user choosing "Live Feed" (`location_mode='gps_live'`) on a stock emulator gets ZERO matches and an empty feed. Set the emulator location to Toronto before testing the feed: Android Studio Extended Controls (`...` button) → Location → enter `43.6532` (lat), `-79.3832` (lng) → "Send"; OR `adb emu geo fix -79.3832 43.6532` (note: ADB takes longitude THEN latitude, opposite of every other API).
- **Before adding a new Zustand store, MMKV blob, hydration bridge, or routing useEffect on mobile — check `docs/specs/03-mobile/99_mobile_state_architecture.md` §3-§5.** The field may already be owned elsewhere; the bridge may not be allowed; the routing decision may belong to AuthGate or AppLayout (Spec 99 §5.1). Spec 99 was authored 2026-05-02 after three render-loop incidents in one session traced to undeclared dual-source-of-truth state. Adding state without a Spec 99 row is a §10 compliance failure.
- **Two layout-level `router.replace` effects reading DIFFERENT sources of truth for the same routing decision will ping-pong** — `mobile/app/_layout.tsx` AuthGate read SERVER `profile.onboarding_complete`; `mobile/app/(onboarding)/_layout.tsx` read LOCAL `useOnboardingStore.isComplete`. When server cache held a stale `dev-user` profile (`onboarding_complete=false`) but local store was `isComplete=true` (from a prior `markComplete()` bridge), AuthGate routed `(app)→(onboarding)` while OnboardingLayout routed `(onboarding)→(app)`, alternating ~36 times before Maximum update depth exceeded. Rule: ONE routing authority per gate boundary, reading ONE source of truth (prefer the server profile — Spec 95 §6 makes server-side fields canonical). Discovered 2026-05-02 via `mobile/src/lib/debug/loopDetector.ts` instrumentation; fix in same-session WF3 stripped OnboardingLayout's effect + added UID-change cache invalidation in `initFirebaseAuthListener` to keep `react-query` MMKV cache from leaking across users.
- **Subscribing to Zustand store inside `RootLayout`/`AuthGate` causes render loops if combined with `router.replace` in the effect** — `useStore((s) => s.field)` re-renders the component on every store mutation, so if the effect deps include the subscribed value AND the effect calls `router.replace`, the chain `setStore → re-render → effect fires → router.replace → segments change → re-render → ...` can ping-pong with `(onboarding)/_layout.tsx`'s competing redirect. Use lazy `useStore.getState().field` inside the effect closure when you only need the value at the moment the effect actually runs (not on every change). Discovered 2026-05-02 post-WF2 `3727ceb`; fixed in same-session WF3.

## ESLint / Tooling
- `scripts/CLAUDE.md` must NOT use `@` auto-imports — they load into every session including Admin/WF7
- `scripts/*.js` are CommonJS — not linted for `no-require-imports`
- ESLint flat config (`eslint.config.mjs`) must ignore: `.next/`, `next-env.d.ts`, `scripts/` (`functions/` was on this list until its 2026-07-20 deletion)
- **`scripts/` is unlinted (eslint ignores it) AND untyped (tsc is TS-only), so a JS syntax error in a pipeline loader has ZERO CI coverage unless a test parses the file.** `scripts/load-parcels.js` was committed (2026-05-23, `10db268`) with a backtick inside its multi-line SQL template literal — an SQL `--` comment reading `` passes `null` for missing columns ``. The first backtick terminated the JS template literal early → `SyntaxError: missing ) after argument list` → the file never parsed → the sources chain hard-failed at step 4 (`parcels`) for a week. The husky pre-commit hook (typecheck + lint + test) caught nothing: `tsc` skips `.js`, eslint ignores `scripts/`, and no test required the loader. **Mitigation (WF3 2026-05-30):** give every pipeline loader a parse-smoke test — `expect(() => execFileSync('node', ['--check', loaderPath], { stdio: 'pipe' })).not.toThrow()` (see `src/tests/load-parcels.parse.smoke.test.ts`). Use `node --check`, NOT `require()`: loaders that call `pipeline.run(...)` unconditionally at module scope (no `require.main === module` guard — e.g. `load-parcels.js`, unlike `load-zoning.js`/`load-permits.js`) would fire a real DB-connecting pipeline run as an unawaited background side-effect when `require()`'d inside a test.
- **A per-row scalar derived from a known-dirty upstream column must be range-guarded against its DB column width BEFORE the batched write, or ONE artifact row aborts the entire mutation.** The parcel cost model (`88`, `aea1d40`) wrote `max_build_fsi` = `max_buildable_gfa_sqm ÷ lot_size_sqm` straight into `NUMERIC(6,3)` (max 999.999). ~1,300 residential parcels carry a garbage `max_buildable_gfa` (tree-contaminated massing / setback-box artifacts — see the max-build accuracy investigation), e.g. parcel 428548: 115,825 m² max-build on a 111 m² lot → FSI 1042 → `numeric field overflow` on the batched `UPDATE … FROM (VALUES …)`, which aborts the whole batch (NOT caught by the per-row engine try/catch — the error is at the DB write layer, not the pure engine). The P1 full-population run silently aborted on this (its "393K menus" was a partial write, masked by a background-command pipe); the P2 re-run surfaced it. **Mitigation:** the engine NULLs an implausible FSI (`FSI_MAX_PLAUSIBLE = 99.999` — nothing residential legitimately reaches 100) and emits an `fsi_implausible_count` audit row (surfaced, not hidden). Applies to ANY ratio/gfa-per-lot scalar written to a narrow NUMERIC from a column with documented dirty rows — guard the value against the column bound in the pure engine, count the drops.

## Web Admin
- **The admin specs claimed a UI kit the repo doesn't have — verify UI-kit presence before planning components.** Spec 33 §4/§6 + `.claude/domain-admin.md` mandated composing from **shadcn/ui**, but shadcn is NOT initialized (no `components.json`; `src/components/ui/` = `Badge`+`ScoreBadge`), and `lucide-react`/`react-hook-form`/`recharts`/`@tremor/react`/`motion` are ALL absent from `package.json`. This misled the P15 Flight Center plan (2026-07-09, commits `4bf6050..d4db75f`). The real convention: Tailwind + hand-rolled native elements, `role="alertdialog"` for destructive confirms (`ConfirmSyncModal.tsx` precedent), inline `<svg>` icons, `useState`+Zod forms, Sonner toasts. **Before planning any admin component, `grep package.json` for the library you're about to `import` — a spec naming a tool is NOT evidence it's installed.** (Corrected in Spec 33 §4/§6 + domain-admin, 2026-07-10.)
- **Worktree-isolated reviewers cannot see untracked files — inventory from the MAIN tree.** Review agents spawned with `isolation: "worktree"` (Gemini/DeepSeek/Code Reviewer) work on a committed copy; a brand-new store/hook/component that isn't committed yet is invisible to them, so they can't verify "does `session.ts` enumerate every store?" or "does this precedent file exist?". Run inventory/existence checks from the main tree (Integration + Regression Guardian already run there for this reason). P15 learning.
- **Admin telemetry is TWO helpers — `track()` is server-side, `captureEvent()` is client-side.** Server route handlers call `track(distinctId, event, props)` (`src/lib/admin/analytics.ts`) with a HASHED uid (`sha256(uid).slice(0,16)`); client hooks call `captureEvent(event, props)` (`src/lib/observability/capture.ts`) + `Sentry.addBreadcrumb(...)` BEFORE the network call. Read-only surfaces emit `captureEvent` only (no `admin_action` breadcrumb — it's mutation-scoped). Using the wrong helper for the side silently drops the event (`captureEvent` no-ops off-browser; `track` needs a distinctId). Spec 33 §11 / Spec 35 §7.1.
- **Per-admin identity exists ONLY on the `session` auth path.** `verifyAdminAuth` returns a real Firebase uid only when `authMethod==='session'` (`ADMIN_USER_IDS` allowlist); `admin_key`→`'admin-key'` and `dev_bypass`→`'dev-user'` are SHARED sentinels, not personal identities. ## Cloud DB / GitHub Actions scheduling (2026-07-29)
- **Migration checksums must be line-ending invariant.** 28 migrations were applied from a Windows worktree whose on-disk files were CRLF while their git blobs are LF; `schema_migrations.checksum` recorded the CRLF hash, so the first Linux-runner checkout (LF) reported 28 false DRIFTs and failed the chain pre-flight (`migrate.js --verify`) — invisible locally because the local worktree carries the same CRLF bytes the DB recorded. `migrate.js` now CRLF→LF-normalizes before sha256; pre-normalization rows were reconciled by `scripts/analysis/reconcile-migration-checksums.js` (idempotent, per-row checksum-guarded). - **The Supavisor session-mode pooler DROPS startup parameters — verify session-config assumptions LIVE against the pooler.** Both the startup-packet `options` string AND pg's `statement_timeout` config param are silently ignored through `aws-0-*.pooler.supabase.com:5432` (each "worked" locally/direct and failed against the pooler; all three mechanisms were tested live before shipping). Only a session-level `SET` on the established connection sticks. Corollary: the cloud session default `statement_timeout` is **2min** (cluster default, no role setting) — it killed `link_wsib` mid-chain on the first GH dispatch. ## AIC scraper — browser launch + proxy (2026-07-30)
- **Verify against the DB the code will actually use — a local `createPool()` defaults to the LOCAL Docker `buildo` DB while CI runs against cloud Supabase `postgres`.** "I verified there are zero rows" against the wrong database is not verification; this exact mistake burned **three CI cycles** before the target mismatch was noticed. `scripts/lib/pipeline.js#createPool()` with no explicit connection string points at localhost. Before asserting anything about "the" data, print the host+database you connected to (and for cloud, pass `SUPABASE_DATABASE_URL` explicitly). Same class as the CRLF-checksum lesson above: a claim that is true locally and false in cloud is worse than no claim.
- **Decodo (and Smartproxy-lineage) usernames are a hyphen-delimited key-value list that is ONLY parsed when the string starts with the literal token `user-`.** `<account>` alone authenticates; `<account>-session-<id>` is just an unknown username → **407**; `user-<account>-session-<id>-sessionduration-N` authenticates. **Session IDs must be alphanumeric** — a hyphen inside the value makes the parser read `session=<firstword>` and choke on the next token as an unknown key (`buildo-worker-1-<ts>` was ours). And a 407 is INVISIBLE in a browser: Chrome renders "This site can't be reached" for every page, indistinguishable from a network outage — always probe the proxy with curl, never diagnose auth from the browser's error page. Root cause of every proxied request failing (`3583d824`).
- **Chrome cannot authenticate to a SOCKS proxy at all** — it ignores credentials and never fires `onAuthRequired`, so a working `curl --socks5` proves nothing about browser viability; SOCKS needs provider-side IP allowlisting. Related, same provider endpoint: plain-**http**-to-proxy CONNECT tunnels to HTTPS targets were RESET (reproduced with `-k`, so it is the tunnel, not cert validation) while **https**-to-proxy worked. Default to `https` to the proxy and prove the scheme with a live probe before believing any of the three (`ef9bbab2`).
- **A sticky-proxy PORT can pin the exit IP, overriding any per-session username suffix.** On `ca.decodo.com`, 20000 = rotating and 20001-29999 = sticky, one IP per port. All workers pointed at 20001, so the multi-worker design's premise — distinct residential IPs — was silently false while every `-session-` suffix looked correct. Give worker N its own port (`base+N-1`, wrapped inside the sticky band) (`c3dff232`).
- **nodriver's DevTools handshake budget is a hardcoded ~2.25 s with no config knob — do not let it launch the browser.** `core/browser.py`: `sleep(0.25)` then five probes 0.5 s apart, identical in 0.48.1 and 0.50.3. A cold profile on a CI runner spends longer than that just creating its favicon/quota/password-store databases, so the handshake expires while Chrome is booting normally — and the error message names no cause. Three more defects in the same path compound it: it never reads `DevToolsActivePort` (a lost port race leaves it blind to a live browser), it `PIPE`s Chrome's stdio and never drains it (a full 64 KB buffer stalls startup), and it raises from *inside* `start()` so the caller gets no handle to kill the browser it spawned — the orphan then owns the profile and every retry fails identically. Fix shape: spawn Chrome yourself, poll `/json/version` on your own budget, then `uc.start(host, port)` to ATTACH. Corollary: in attach mode `browser.stop()` cannot kill the process (the attach path never sets `_process_pid`, and its fallback tests a typo'd attribute) — pair every stop with a real process-group kill of a pid you own, and supply nodriver's own default flags yourself since attach mode contributes none (`7055ce89`, `733e67c4`).
- **Pin browser-automation libraries EXACTLY, not `>=`.** `nodriver>=0.48` meant CI silently resolved 0.50.3 while every local proof was on 0.48.1 — the cloud was never running the code that was tested, and the version difference is invisible in the logs.
- **An MV3 service worker is EVICTED when idle, so extension-based proxy auth fails intermittently and invisibly.** `chrome.proxy` settings persist after eviction but `onAuthRequired` goes with the worker — the browser keeps routing through the proxy while unable to authenticate. Combined with branded Chrome removing `--load-extension` (137) and its opt-out (142), extension-based proxy auth is a dead end. Prefer a **local unauthenticated relay** (`proxy-chain`) that holds the credentials + a plain `--proxy-server=http://127.0.0.1:PORT`; add `--proxy-bypass-list=<-loopback>` or Chrome's default loopback bypass sends the relay-bound traffic direct. On CONNECT the relay must pipe raw bytes (never mitmproxy, which re-originates TLS and destroys the JA3/ALPN fingerprint a WAF-sensitive scraper depends on) (`19869fc4`).
- **"Is the mechanism configured?" is not "is the mechanism working?" — assert the OUTCOME.** For four months telemetry recorded `proxy_configured=true` while every run scraped direct, because the only check was whether an extension existed, and `assert-network-health.js` gated `proxy_errors` without any notion of whether egress was actually proxied. The durable check is an egress-IP assertion through the browser itself (`verify_proxied_egress`). Two design notes worth reusing: an echo service the BROWSER cannot reach while the HOST just did is evidence **OF** proxying, not grounds to refuse; and any memoized "host baseline" the assertion compares against needs a TTL, or a stale baseline lets an unproxied browser PASS.
- **A working proxy makes the browser's OWN background traffic a billable line item — cap it at the relay, not just with flags.** The first genuinely proxied run billed 1.76 GB to `edgedl.me.gvt1.com` (Chrome's component-update CDN; 62 requests averaging ~28 MB) for ~$6.60, plus translate/autofill/safebrowsing/accounts chatter — against 2.7 MB of actual scraping. 99.9% of spend was Chrome talking to Google. The traffic was always there; it was free only while the proxy was silently broken. Launch flags (`--disable-background-networking`, `--disable-component-update`) suppress it, but a flag that regresses is silent and costs money, so the relay now enforces a **deny-by-default host allowlist** as an independent second layer. Generalizes: when you put a metered link under something chatty, budget for the chatter and enforce the budget at the chokepoint you control.

## Debugging protocol — establish LAST-KNOWN-GOOD from data before diagnosing (2026-07-30)
- **A spec tells you what the system was meant to do; only the data and the code tell you what it ever actually did. For a debugging task, start with the latter.** The 2026-07-29/30 deep-scrapes day was spent fixing a cloud "regression" in a scraper that had **never once worked** — every fix was real, but the framing was wrong from hour one because it came from Spec 115 §2.4's design intent rather than from ground truth. Two queries and one git command would have reset it: `SELECT count(*), max(scraped_at) FROM permit_inspections` (792 rows, newest **2026-03-15** — nothing since) and `git log --all --diff-filter=D -- '*aic-scraper*'` (the rows came from `poc-aic-scraper-v2.js`, a **Playwright** scraper deleted 2026-04-16; the nodriver rewrite that replaced it has produced zero rows, ever). Cost of skipping that: ~13 CI validation cycles, ~$6.75 of residential bandwidth, and a day of re-solving a solved problem.
- **The three ground-truth questions to answer BEFORE forming any hypothesis about a broken pipeline:** (1) *When did this last produce real output?* — query the output table's max timestamp, never a status/verdict column. (2) *What code was running then?* — `git log` the producing script, including deletions and renames; a rewrite is not a continuation. (3) *Is the thing I am "fixing" a regression or something that never worked?* — those need completely different strategies: restore-and-diff versus build-and-prove. This does not weaken CLAUDE.md Prime Directive #10 (read the spec first, never infer from names); it bounds it — the spec is authoritative for **intent and contracts**, the database and git history are authoritative for **what happened**. When they disagree, the spec is the thing that is wrong.
- **Corollary — "it works locally" is a claim about an environment, not a proof of a code path.** Local runs here recorded `proxy_configured=true` while scraping direct from a residential IP, because branded Chrome silently refused to load the proxy extension. Before trusting a local baseline, verify the specific mechanism under test actually engaged (assert the outcome — a different egress IP — not the configuration flag).

## Scheduling, gates and cadence — Phase A deep-scrapes restore (2026-08-05)
- **A platform timeout is not a stop mechanism. A long-running job that can only be ended by the platform ends DIRTY, even when the work itself was healthy.** The deep-scrapes drain was fine — 713 scrapes, zero WAF blocks across ~2,700 requests, ledger 0 write failures — and still produced orphaned `pipeline_runs` rows, stuck `claimed` queue rows and a red verdict on every slice, because the GH step timeout SIGKILLed it mid-scrape. The fix is a SOFT budget (`SCRAPER_TIME_BUDGET_MINUTES`, chain timeout − 10) checked at the top of each claim loop: stop claiming, finish in-flight work, run the NORMAL finalization path, exit 0. The platform timeout stays as the backstop, not the mechanism (`d6eb9f31`). Generalizes to anything with a hard external kill: if the only way your process ends is someone else killing it, every ending is an incident. Corollary from the same day: the mandated SIGINT/SIGTERM handler has now failed to terminalize rows in TWO separate incidents (5 rows total) — an async write racing a SIGKILL is not a reliable cleanup path, so the durable answer is stopping before the kill, not cleaning up after it.
- **Freshness/watchdog windows are COUPLED to cadence — change one and you must move the other in the same commit.** Cutting deep-scrapes from three weekday slots to one moved the newest completion ~6h earlier (last slot 21:00 → 15:00 UTC, completing ~17:35). The Monday freshness window was 72h, sized for the old last slot; against a watchdog that fires at 15:30 UTC and has been observed 1–2h late, that left about **six minutes** of margin — a Monday-morning false red waiting to happen. Widened to 80h/30h in the same commit as the cadence change (`2fa3b2e7`). These are ABSENCE checks ("did anything land at all"), so slack is nearly free while a genuinely skipped run still breaches by hours. Ask on every cadence change: what else was sized off the old schedule?
- **Compute a gate's rate in the GATE'S OWN unit, or you will invent an emergency.** Mid-slice, the anomalous miss rate computed over `permit_scrape_outcomes` rows read 36.7% against a 20% FAIL gate. The real figure was 14.2%, and the run finished at 3.7%. Cause: `no_target_folders` is a *year_seq-grain* outcome, but the ledger writes one row per queued permit sharing that year_seq (one search on `21 157190` → 48 rows), while `classify_miss_rate` divides by `permits_attempted` = one per search. Before reporting any rate against a threshold, read the code that computes the threshold's denominator and reproduce THAT denominator — a plausible-looking number in the wrong unit is worse than no number.
- **A workflow disabled in the GitHub UI cannot be re-enabled by editing its cron.** `disabled_manually` is repo-invisible state: `gh workflow list` shows it, `git` shows nothing, and the committed `schedule:` block reads as live while nothing fires. We disabled `chain-sources` this way on 2026-08-05 pending its Phase B probe. Whoever restores it must flip it in GitHub AND in the cron text — an in-repo change alone produces a schedule that looks correct in review and never runs. Same class as any out-of-band toggle (Vercel env, branch protection, required reviewers): if the repo can't see it, the repo can't be the source of truth for it. **The RULE stands; the 2026-08-05 FACT is stale** — re-verified live 2026-09-03 (WF3 cloud-parity FIX 3.1, `gh api repos/:owner/:repo/actions/workflows/chain-sources.yml --jq '{name,state,path}'` → `{"state":"active"}`) and again 2026-09-03: `chain-sources` is `active`, not disabled (it has since fired scheduled runs, e.g. 2026-08-30). This is exactly why this WF re-verifies the UI state out-of-band rather than trusting the committed `schedule:` block or this lesson's own prose as a current fact.
- **A viability floor on ONE term of a LEAST/MIN leaves the sibling terms free to win with degenerate values.** Phase 1 (2026-08-07) floor-clamped the setback-box dims (`< 3 m → NULL`) and the very first full re-run's (0,10)-GFA gate caught 602 ravine parcels whose −10 m buffer inset had collapsed to 0.01–9.98 m² slivers — the buffer then WON the `LEAST(buffer, box, coverage)` and the sliver was priced. Extends the 2026-05-31 MIN/LEAST-NULL-skip lesson from NULLs to DEGENERATE values: when you bound a min-aggregate, bound every contributing term (box per-axis ≥ floor; buffer ≥ floor²), or the min inherits the artifact.
- **Pre-pin every re-run gate's expected number BEFORE the run, in the gate's own scope.** Phase 1's step-8 gates were pre-computed exactly (corner recovery 6,920/6,947; ravine_constrained 12,968; footprint coverage 94.03%) and the run matched to the row — which is precisely what made the ONE off-expectation number (602 in the (0,10) band) stand out as a genuine sibling bug instead of noise. Three plan-round projections (~4,775 class size, ≥95% coverage, 70% RD absolute) were each falsified by measurement; the pre-pinned expectations, not the projections, were what the gates could honestly be judged against. Corollary from the panel: set-union accounting over reason columns must be NULL-safe (`NOT IN` drops NULL rows three-valued-logically) — a 98.56% headline was really 97.58%.

## An assert must distinguish "the data is wrong" from "I could not check" (2026-08-11, C1/D1)
- **A quality gate that halts on every failure it can detect will eventually halt on one that proves nothing.** `assert-lifecycle-phase-distribution.js` threw on `failures.length > 0` across seven push sites in three semantically different classes. Three of them (`cross_check_*`) mean *"the legacy `enriched_status` column disagrees with the lifecycle columns"* — real drift, worth a FAIL, but it says nothing about whether the assert did its job. The other four (E.5 band violations, the `unclassified_count` hard limit) mean *"I could not verify this data"*. Only the second kind is grounds for stopping a chain. On 2026-08-10/11 a drift breach killed `chain_permits` at step 25/33 and `chain_coa` at 14/16, skipping **10 steps including `backup_db`**; backup age hit **28.58h against a 25h SLA**. **Before writing `throw` in an assert, sort its failures into "the data is wrong" (verdict) and "I could not check" (halt) — and if the file only has one array, that sort has not happened.**
- **Two safe mechanisms can compose into an outage.** The watchdog's backup fallback is suppressed while permits is running (a correct guard against concurrent `pg_dump`s). Permits *was* running, then died before `backup_db`. Guard × halt = no backup by either path, and no alarm naming the backup. **Any fallback gated on "the primary is in progress" is blind to the primary dying after the gate closes but before the work it guards.** Ask it of every fallback you write.
- **When you split a halting condition, the test that must survive is the one that stays RED.** The red-first proof here was two-sided: the case that had to flip green (cross-check-only → exit 0) *and* the cases that had to keep halting (hard limit; armed band violation). The second kind is the load-bearing one — a naive "just drop the throw" satisfies the bug report and silently retires the hard limit, and nothing else would have caught it. A refactor test suite with no assertions that are *supposed* to keep failing has not pinned the thing you were afraid of.
- **A new terminal status is an API change to every consumer that reads status.** C1 made `completed_with_errors` reachable where only `failed` had been. `run-chain.js`'s "was the previous run bad?" check keyed on `'failed'` alone, so without the matching edit the next night would have re-enabled gate-skip and silently skipped the backlog the red run left behind. **Grep every consumer of a status column before introducing a new value into it** — the compiler cannot help you with strings.
- **A count is not evidence of a category — measure the rows, not the tally.** Phase A's C2 was built on *"397 permits spell their base revision `'0'`, so they can never be marked Stalled"*. The count was **correct**; the inference was false — every one of those rows is a `DCs DeferredFees` administrative fee stub that has never held an inspection status, so the "bug" did not exist and the fix would have written scraped statuses onto fee stubs. One extra column in the original query (`permit_type`) would have ended it in ninety seconds. This class recurred **four times in a single session** ("those 1,350 ARE the smear" was the same shape). Before inferring meaning from `COUNT(*) WHERE col = X`, SELECT the rows and look at their other columns. Reviews cannot catch it: four rounds re-read a true sentence and correctly concluded it was true.
- **Derived state is scoped by the row's own status, never by a "canonical" or base row.** `enriched_status` is a per-row refinement of that row's own `status`; every consumer is row-grained and the lifecycle cross-checks count ROWS. A canonical-row rule cannot satisfy a row-grained invariant — it only moves *which* row is wrong. The durable form of the rule: **the writer must use the same predicate as the reader that selected it.** The AIC smear existed because the queue selected on `p.status = 'Inspection'` while the writer wrote on `permit_num` alone — writer and reader disagreed from day one. (Supersedes the retracted "revision-grain" framing: `MIN(revision_num)` picks a non-Inspection row 6,205 times and would resurrect closed permits as under-inspection.)
- **Back up before any destructive NULL-out, and date the backup table if the script can re-run.** *"A destructive NULL-out with no rollback path is not acceptable"* — the Gemini P9 ruling behind `6af3d537`, which bolted a backup onto `wf2-reset-coa-trade-classification.js` **after** it had already shipped without one. The rule lived in two script bodies and one commit message and nowhere else until now. Second half, learned the hard way in C3: `wf2-p13`'s fixed-name `DROP TABLE IF EXISTS … ; CREATE TABLE … AS SELECT` is safe **only for a genuine one-off** — on a re-runnable script, run 2 silently destroys run 1's rollback. Use `_backup_<thing>_<YYYYMMDD>` and print the restore UPDATE.
- **A backup is only a rollback if it is ATOMIC with the mutation.** Under READ COMMITTED every statement takes a fresh snapshot, so a `CREATE TABLE AS SELECT` followed by an `UPDATE` in the same transaction can see *different* row sets: a row entering the predicate in between is nulled **without being backed up** — unrecoverable, and silent. An advisory lock does not help; it serializes the script against itself, not against the pipeline steps that write the same column. Take the count inside the transaction, run at `REPEATABLE READ`, and assert `backupRowCount === updateRowCount` so the failure is loud.
- **An apply-time invariant is not enforcement — it needs a standing audit row.** Migration `138_a` asserted "no administrative row carries a `lead_id`", passed at apply time, and went silently false for months: its trigger was scoped `UPDATE OF permit_num, revision_num`, so a permit reclassified into an administrative type on re-ingest never re-fired it. By the time it was measured, **all 1,190** administrative rows carried one and 171 duplicate `lead_id` groups were live. A one-shot DO block proves a state; only a recurring check defends it.
- **When a metric is expected to be permanently non-zero, it must be WARN with a self-announcing retighten condition — never FAIL.** A FAIL row on a structurally non-zero population is a standing red that operators learn to ignore, which is worse than no gate. Spec 48 §4.9: a relaxation must never be a silent, forgettable bypass — emit the live value every run plus a `<metric>_retighten` companion naming the machine-observable condition, and self-retire at zero.
- **No review pass re-reads the folded corrections against each other, and that is where the worst defects hide.** Eight reviewers passed over one ~150-line backfill plan. The two most consequential findings were not flaws in any single correction — they were **collisions between two corrections folded separately and never cross-read**: "the population regenerates nightly" × "back up using the fixed-name precedent" = re-running destroys your own rollback; "harden the predicate to `IS DISTINCT FROM`" × "the audit row counts `<>`" = a permanent unclearable red on day one. Adding reviewers does not find these. **After folding a panel, re-read the folds as a set before writing code.**
- **An archetype ruling that reorders phases (acquire→write→checks) must re-derive every "before X" guarantee in the step's own spec — Pilot 2 silently retired Spec 59 L7/L8 abort-before-write until the Regression Guardian caught it (Fold C, `e64a5676`).**
- **2026-08-28: a read-only agent stashed a sibling agent's working tree — never remediate a tree you did not author; report to the parent. Doc moves are verified by line-set diff (R-I.4).**
- **`min_migration` is a COUNT floor (P0), never a filename number — the conformance lock now enforces `<=` file count.** `link-wsib.descriptor.json` shipped `min_migration: 243`, the filename of `243_wsib_unlinked_partial_index.sql`, but `assertDbTarget` compares against `COUNT(*) FROM schema_migrations` and the `migrations/` sequence has 4 historical filename gaps (43, 49, 50, 158) — COUNT never reaches a gapped filename, and the step refused to run forever (LW-D8). Set it to the migration's 1-based position in the sorted `migrations/` listing instead.
- **2026-08-28 pilot 4 commit 7: a sub-agent used --no-verify once mid-amend; final tree was re-verified through the hook. --no-verify is never acceptable, including for message-only amends: use `git commit --amend` through the hook or a follow-up commit.**
- **A SQL-rendered descriptor field is parse-tested (LW-D9); a declared tunable is a runtime read, not a text mention (LW-D10).**
- **A check observer's ctx inputs are produced by the library and locked to `STEP_CTX_KEYS` — a test harness may not inject what the runtime never plumbs (LM-D14 class).** `link_wsib`'s `entity_fanin_warn` read a top-level `ctx.fanin` that `scripts/lib/step/index.js`'s `stepCtx` literal never assigns; the WARN always evaluated `{}`/0 against every real run (live invariant 439, reported 0) while the unit suite (`src/tests/steps/link_wsib/violations.test.ts`) stayed green because its own `runCompute` ctx-builder injected `ctx.fanin` directly — a fixture handing the compute something the runner never produces. `entity_fanin_max` was ALREADY on `ctx.matched` the whole time (the step's own `CUMULATIVE_SQL` merges generically onto `matched` post-write, same mechanism `link_rate_warn` uses) — the fix was reading the right field, not adding a new channel. `STEP_CTX_KEYS` (exported, `scripts/lib/step/index.js`) is now the closed list; `step-conformance.infra.test.ts`'s harness-fidelity lock AST-parses every `src/tests/steps/*/violations.test.ts` ctx-builder and fails if it sets a key outside it (LW-D11).
- **A "normalises null → 0" comment citing a real, ratified decision can be citing the WRONG layer — verify the citation's own scope before trusting it as license.** `pipeline.js#emitSummary` coerced `records_total: stats.records_total ?? 0` (both `null` and `undefined` → 0) while `records_new`/`records_updated` used `!== undefined ? … : 0` (preserves an explicit null) — a genuine asymmetry that let a gated-skip's `PIPELINE_SUMMARY` (`records_total: 0`) disagree with the SAME run's `pipeline_runs` row (`records_total: null`, since `ledger.js#finalizeLedgerRow` deliberately carries no COALESCE there). A pinned unit test excused the bug by citing "plan C-11" — but C-11 is `run-chain.js`'s OWN DB-write normalisation for a DIFFERENT, pre-conversion script, not a license for `pipeline.js`'s own emission layer to treat one of three symmetric counter fields differently (LW-D12). Rule: before treating an inline "this is intentional, see ruling X" comment as settled, re-read ruling X's own stated scope — it may govern a different file/layer than the one citing it.
- **A boolean flag that bypasses a GATE is not the same as a flag that suppresses a WRITE — both must be wired, or the flag's contract is only half true.** `link_wsib`'s `--dry-run` correctly bypassed the ledger's gated-skip (`bypassed = dryRun || force_full`) so a dry-run always ran the simulation, but `dryRunArgPresent`'s result was never threaded into `ctx.overrides` or read by the write phase — `runCascadePhase`/`runLinkPhase` then issued every `UPDATE`/`INSERT`/`DELETE` unconditionally. A `--dry-run` invocation on ANY converted LINK/MATCHER step wrote to production tables for real, the exact opposite of the flag's name, silently, since conversion (LW-D15, CRITICAL). The pre-conversion `link-wsib.js` (`5de41cc1`) got this right — read-only COUNT queries mirroring the same predicate, never a real write — and the fix restores exactly that shape rather than execute-then-ROLLBACK (which would still issue the write statement text, failing a "zero write statements" test even though nothing commits). Rule: when a step declares two override semantics (gate-bypass + write-suppression) verify BOTH are wired, not just the one a test happens to exercise — a green differential that only ever runs in non-dry-run mode will never catch the other half missing.
- **A "RE-HOMED to `<path>`" comment is a claim, not a fact — verify the destination exists before trusting it.** `src/tests/db/ledger-gate-callers.db.test.ts` stated link_wsib's ledger-gate coverage moved to `src/tests/steps/link_wsib/ledger-gate.db.test.ts`; that file was never created (`git log --all` on the path is empty), and the real blocker — every converted step's `database.assert_current_database:"postgres"` refusing the testcontainer's `buildo_test` name — was already filed as a MED followup that nobody linked back to the stale comment (LW-D16). A coverage gap that CLAIMS to be covered elsewhere is worse than an admitted gap: nobody goes looking for it. Before believing a "moved to X" / "covered by X" comment, `git log --all -- X` or open X — a five-second check that would have caught this the day it was written.
- **A destructive repair without a row-level before-image cannot be audited (R-M).** `link_wsib`'s LG-16 UPDATE-to-NULL and `link_massing`'s `retract:"all"` DELETE erased rows with no record of what they had contained — if the retraction's own predicate were ever wrong, or an operator needed to know exactly what a repair removed, there was nothing to look at (R-B's `recovery.interrupted` only declares the CRASH-RECOVERY posture; nothing declared or produced the AUDIT TRAIL). Fixed generically (`write.writeBeforeImage`, `scripts/lib/step/write.js`): the SAME `write_discipline.scope` predicate a retraction already binds is re-used, unmodified, as a read-only SELECT mirror — no new predicate to keep in sync, no risk of the audit trail and the retraction silently disagreeing about which rows are in scope. **Also learned the hard way, same commit:** a golden-capture file whose NAME looks like a disposable "extra scenario" (`sources-full-forced-1.json`) can be load-bearing evidence pinned to a specific hash constant in a test (`LM_D13_FIXED_HASH`) — deleting it on the assumption that "coverage didn't require it" broke a DIFFERENT test (#159, "the write path is never exercised") that the R-C fingerprint gate's own coverage check doesn't know about. Before deleting ANY golden capture file as "stale/extra", grep the OWNING step's `violations.test.ts` for the exact filename first — R-C's declared-invocation coverage is necessary, not sufficient, for "safe to delete."
- **A JS string literal silently drops an unrecognized backslash escape — `'\s+'` in JS source reaches Postgres as the 2-character literal `s+`, not the regex whitespace class.** `\s` is not a JS escape sequence, so the parser drops the backslash; only `'\\s+'` in JS SOURCE produces the single backslash Postgres needs. This bit twice measuring LW-D14's baseline: three separate debug scripts written via Bash `-e`/heredoc, each with the plain `'\s+'` form, all reproducibly measured **0.00%** (the split failed on every name lacking a literal lowercase `s`) before a `String.fromCharCode(92)` control test proved a genuine single backslash gives the correct **10.49%**. The SAME regex written directly into a `.json` file (`invariants.json`, edited via the Edit tool, `\\s+` in the file source) was already correct, because `JSON.parse` — not the JS lexer — resolves that escape, and the resulting STRING VALUE is used as-is, never re-embedded in new JS source. Rule (reinforces the existing "use the Edit tool for escape sequences" lesson): any SQL/regex literal containing a backslash must be authored via the Edit tool directly into its target file, never composed through a Bash-invoked `node -e`/heredoc — and when a measurement looks suspiciously round (0.00%, 100.00%) on a regex-splitting query, suspect the escaping before the data.
- **A hand-duplicated SQL string that mirrors a compute function's logic will drift the FIRST time that function changes, silently, because nothing regenerates it.** `docs/reports/golden/link_wsib/invariants.json`'s `wsib_tier3_token_overlap_pass_pct` entry was a separately-authored copy of `tokenOverlapClause`'s predicate (needed because the golden-capture harness reads `invariants.json` independently of the descriptor/compute files). LW-D18 widened the stopword list and added a punctuation strip to the REAL function but never touched this duplicate — the next capture measured 97.99% where the real predicate (independently re-verified: 0 rows disagreed) guaranteed 100%, the exact same failure shape as LW-D14's own COALESCE-vs-OR bug one commit earlier. Fix both times: regenerate the duplicate PROGRAMMATICALLY from the real function (`compute.tokenOverlapClause(...)`) and write the JS string straight into the JSON via `JSON.stringify` (never hand-retype the SQL), then round-trip-verify (`JSON.parse` the written file back and assert the string is byte-identical to what was intended) before trusting a capture. Generalizes: any time a query/predicate exists in TWO places for infrastructure reasons (a runtime compute + a separately-invoked audit/capture harness), treat the second as generated-not-authored, and re-derive it from the first on every change to the first — never hand-edit both in parallel.
- **An aggregate "does the write predicate still hold?" query must mirror the write predicate's actual BRANCH STRUCTURE, not approximate it with a single coalesced field.** LW-D14's `tier3_token_overlap_pass_pct` column first tokenized `COALESCE(NULLIF(w.trade_name_normalized, ''), w.legal_name_normalized)` against the entity name — ONE field, chosen by "prefer trade name if present." But the WRITE side (`buildFuzzyMatchSql`) is a UNION of two INDEPENDENT CTEs, `trade_matches` (checks trade-name overlap) and `legal_matches` (checks legal-name overlap) — a row written via the legal branch can have a non-empty, NEVER-CHECKED trade name that shares nothing with the entity name, and COALESCE always preferred it anyway. Measured 86.2% where the write predicate guaranteed 100%, on a corpus that had already been correctly repaired — the DB was fine, the READ query was wrong. Fixed by `OR`-ing the two fields' overlap independently, exactly mirroring the two-CTE union — and it turned out a SIBLING invariant in the same file (`wsib_tier3_current_predicate_pass_rate_pct`) already used that exact OR-of-two-branches shape, an established local precedent the first draft should have matched instead of inventing a COALESCE shortcut. Rule: when a predicate is written as a union of N independently-conditioned branches, any downstream query re-verifying "did every written row satisfy it" must OR the N branches, never collapse them to one field first — and check for a sibling query in the same file that already got the shape right.
- **Accuracy is a sampled precision/recall number against a before-image, never a link rate (R-O).**
- **A low-precision tier is a candidate signal, never a product-visible boolean.** `link_wsib`'s fuzzy (tier-3, 0.60) matches set `entities.is_wsib_registered` identically to the two exact tiers (20/20 correct) even though a fixed-rule 60-row sample measured only 31.7%-46.7% genuine precision on the fuzzy population — a registration CLAIM shown to a user was, for roughly half of tier-3's rows, more likely wrong than right (LW-D19, operator ruling 2026-08-29). Fixed by restricting the boolean's write scope to the exact tiers only and adding an unconditional per-run self-heal correction (never a one-off FULL) rather than a new column: the low-confidence tier stays a declared candidate signal on its own table (`wsib_registry.match_confidence`), never promoted to a product-visible flag.
- **checks_failed means FAIL; WARN is counted separately — never conflate severities in a counter (LPA-D6).** `scripts/lib/step/verdict.js`'s `buildAuditTable` pushed BOTH a FAIL row and a WARN row's rendered string into the SAME `errors[]` array, and `records_meta.checks_failed` was `errors.length` — so a run with zero FAIL rows and one WARN row (`link_parcel_addresses`'s standing `parcel_fanout_outliers` WARN, measured live) reported `checks_failed: 1`, a false positive an operator scanning for genuine failures would trust. `scripts/quality/assert-data-bounds.js` (still hand-rolled, un-converted) already had the right shape — separate `errors`/`warnings` arrays feeding separate `checks_failed`/`checks_warned` counts — the fix brought the generic library to parity with that established precedent rather than inventing a new one. Generalizes: any counter derived from a row-status list must be a per-severity projection (`rows.filter(r => r.status === 'FAIL').length`), never `rows.filter(r => r.status !== 'PASS').length` dressed up as "the failure count."
- **A step that can skip must persist WHY it skipped — a pre-check is mandatory, enforced by conformance (LPA-D4).**
- **A markdown table row containing an escaped pipe (`\|`) breaks a naive `line.split('|')` parser — it shifts every later column silently.** `defect-ledger.md` rows routinely quote code (`row.status === 'FAIL' \|\| ...`) inside prose cells; a hand-rolled table reader that splits on every `|` reads the WRONG column as "Status" for those rows without erroring — it just returns plausible-looking garbage. `scripts/analysis/step-validate.mjs`'s G6 gate caught its own bug this way (`LPA-D6`'s row, which contains `\|`, initially reported a status string that was actually from a different cell). Fix: split on `/(?<!\\)\|/` (a pipe not preceded by a backslash), never bare `'|'`, for any hand-parsed markdown table.
- **"Do not massage the score" means fixing the heuristic's PRECISION, not its LENIENCY, when a checker over-reports.** `step:validate`'s G8 gate (unexplained golden-capture diffs) first tried matching on a diff key's last TWO path segments to reduce false positives — but generic wrapper names (`records_meta`, `audit_table`, `rows`) appear in every pipeline report regardless of whether the SPECIFIC field was ever discussed, so the looser match silently marked genuinely-undocumented diffs (a real, later-landed `checks_warned` field; a 9→11 `invariants.json` growth from a separate WF3 fix) as "explained." The honest fix was the opposite of loosening: match on the deepest NON-generic field name only, and require a genuinely undocumented diff to be fixed by adding REAL documentation to the report (with the commit that caused it named), not by widening what counts as a citation. `link_parcel_addresses.descriptor.json` declared 15 checks, all `when:"post"`, none `when:"pre"`; the library's gated-skip narrowing (`onlyChecks`, `scripts/lib/step/index.js`) reduces `stepCtx.checks` to the `when:"pre"` set on a SKIP, so the persisted `audit_table` had only the 2 always-present `sys_*` rows and `gatedSkip.reason` was only `log.info`'d, never `records_meta` — a broken always-unchanged gate was indistinguishable from a healthy quiet run (live: `pipeline_runs` ids 1709/1710/1714/1717, `jsonb_array_length(audit_table->'rows') = 2`). Generalizes beyond this one step: ANY archetype whose runner phase can resolve a gated skip (ingest's `preAcquisitionDecision`, cascade/materialize's `ledgerGatedSkip`) needs its own `gate_decision`-shaped `when:"pre"` check, mirrored exactly, plus the library's `records_meta.gate` (rung (d), one shared helper). "Can gated-skip" is a descriptor-level FACT, not an archetype guess — key the conformance rule on `terminals[].kind === "skip_gated"`, which `link_massing` (LINK, tri-state `selectMode`, never a skip) correctly does NOT declare.
- **A "the current run started ⇒ open a ledger row" mechanism and a "detect an interrupted PRIOR run" reader will find each other unless the current run's own row is explicitly excluded — a self-crash-detection loop (R-B / LW-D20).** `staleness.selectMode`'s new `detectInterruptedRetraction` branch queried for a `running`/`crashed` `pipeline_runs` row more recent than the last `completed` one — but `openLedgerRow` already inserts THIS invocation's own `running` row before `selectMode` ever runs, and `finalizeLedgerRow` hasn't stamped it `completed` yet. Every single run detected itself as "interrupted" and forced FULL forever, permanently defeating the incremental/gated-skip path — the first live invocation printed `cascade mode gate: FULL (recover_interrupted_retraction)` as its VERY FIRST log line, before any real work existed to interrupt. Found by a live kill-and-rerun proof against `link_wsib`, not by reading the code. Fix: thread the caller's own `openLedgerRow` return value (`ownRunId`) through to the detector and exclude that exact row id by parameter — never by timestamp comparison alone (the row's `started_at` and the run's own clock reads are two independent `NOW()` calls with no guaranteed ordering). Any future "does an earlier row of MY OWN kind exist" query needs the same self-exclusion the moment the row it's searching for is one its own caller might have just written.
- **A crash-recovery check placed only inside the "what mode do we run in" function is unreachable dead code whenever an EARLIER gate can return before that function is ever called — and the common case is usually the early return.** R-B/LW-D20's interrupted-retraction detector lived inside `staleness.selectMode`, but `runCascadePhase` calls `ledgerGatedSkip` FIRST and returns immediately on SKIP — the ordinary, most-frequent outcome when nothing upstream changed. A second live kill-and-rerun proof (immediately after fixing the self-detection bug above) took exactly this SKIP path and silently skipped past a genuinely stuck prior run. Fix: compute the crash check BEFORE the early-exit gate and fold its result into the SAME `bypassed` boolean `dry_run`/`force_full` already use — never a second parallel bypass mechanism. Generalizes: when a NEW override-shaped condition needs to "always run, never skip," audit every early-return gate between the entry point and wherever the new check currently lives, not just the function whose job LOOKS like it owns the decision.

## A guard comparing a ROUNDED stored column against an UNROUNDED recomputation is not a guard (CC-D3, 2026-08-30)
- `compute_centroids`'s CC-D3 FULL-mode repair guard (`centroid_lat IS DISTINCT FROM ST_Y(ST_Centroid(geom))`) was authored against `centroid_lat`/`centroid_lng`, `NUMERIC(10,7)` columns, compared to `ST_Centroid`'s raw double-precision result. ## A step's declared FULL re-evaluation is a defect-discovery instrument — budget for "the run itself finds a bug" (LP-D9, HIGH, 2026-08-30)

## An all-INFO audit table is a silent PASS — a self-skip needs a declared non-INFO row, not a new verdict value (LG-29, VRD-SKIP, 2026-09-09)
- `deriveVerdict`'s max-lattice (`SEVERITY_RANK={PASS:0,INFO:0,WARN:1,FAIL:2}`, `scripts/lib/step/verdict.js:22`) has no floor other than PASS — ANY audit table whose rows are all `INFO` folds to `verdict='PASS'`, whether that's genuinely "nothing worth flagging" or "zero checks were ever evaluated." `skipRecordsMeta` (`scripts/lib/step/index.js`) built exactly that all-INFO shape for a SELF_SKIPPED terminal (advisory lock contention), so a step that never ran read identically to a step that ran and passed every declared check — live-measured (`pipeline_runs` id=1843, `status='self_skipped'`, `verdict='PASS'`). Fixed by declaring the 'status' row's severity WARN (threshold `'ran'`) instead of inventing a 4th verdict value — Spec 124 §7's ladder Step 2 prefers "a declared check/audit row" (rung b) over "a library change" (rung d) whenever the cheaper rung actually closes the gap; rung (d) here would have needed a Spec 120 §3.2b vocabulary amendment AND still left `FreshnessTimeline.tsx`'s roll-up chip rendering the skip as green (a `'SKIP'` value falls through its `.includes('FAIL'/'WARN')`-else-PASS branches the same way `'PASS'` does). **Sibling check:** any OTHER audit-table builder that can legitimately end up all-INFO (`buildSkipGateRecordsMeta` in `scripts/lib/source-version.js`, measured 2026-09-09 to exhibit the identical defect on its first 1-3 consecutive skips) needs the same scrutiny — "the checks all passed" and "no checks ran" are indistinguishable to a pure severity-max fold unless at least one row's declared severity says so.
- **Checker-scanner false positive, same commit:** `step-validate.mjs`'s `checkNoSecondDerivation` regex-scans EVERY file in `VERDICT_LIBRARY_CORPUS` for the literal text `verdict` followed by `:`/`=` — including inside `/** JSDoc */` comments, which it does not distinguish from code. A docblock phrase like "folds to verdict=WARN" (no space around `=`) is textually indistinguishable from a hand-rolled assignment and gets flagged as an unsanctioned second derivation. Any comment near a verdict-touching function must phrase it as "a WARN verdict" / "verdict of WARN", never "verdict=X" or "verdict: X" — the scanner cannot tell prose from code.

## `git apply` on Windows rewrites touched files with CRLF, and a CRLF line defeats a `//`-comment stripper that anchors on `$` (WD-1 landing, 2026-09-09)
- Landing a worktree diff into the main tree via `git apply` (autocrlf=true) rewrote `scripts/lib/step/index.js` with CRLF. `generate-template-freeze.mjs`'s `extractPhaseOrder` strips line comments with `l.replace(/\/\/.*$/, '')` — on a `\r`-terminated line `.*` stops at `\r` and `$` (no `m` flag) needs end-of-string, so the comment survived and a `// (pipeline.withAdvisoryLock(...)` remark inside `runEnrichPhase` leaked into the extracted phase_order. `template-freeze.infra.test.ts` then reported a "drift" that no code change caused; the pre-commit hook failed once on a clean diff (the git-shown HEAD file is LF, so the same extraction read 7 entries there).
- **Rule:** after any `git apply` / patch landing on Windows, run `git ls-files --eol <touched files>` and normalize `w/crlf` → LF (`sed -i 's/\r$//'`) BEFORE running tests or committing. Followup (LOW): make the extractor's strip tolerate `\r` (`/\/\/.*\r?$/` or `.split(/\r?\n/)`) so a checkout's line endings can never manufacture a freeze drift.

## A "stub preserves the anchor line" move design must special-case its OWN idempotency check, or `--refresh` corrupts on the second run (`spec-split-check.mjs`, WF2 "Specs 122/123/124 grounding + reorg + split checker", 2026-09-10)
- `spec-split-check.mjs`'s move mechanism deliberately keeps a `#`-heading anchor's own line UNCHANGED as the first line of its own stub (so the citation still resolves) and replaces only the body beneath it. The first `locateBlock` implementation determined "has this move executed?" purely by whether `move.anchor` still exists as an exact line — which is ALWAYS true by design once the stub lands, so a second `--refresh` would re-"cut" the stub itself (blank + pointer + whatever line follows), re-hash that as if it were the original content, and silently corrupt both the spec file and the manifest's recorded `content_sha256`. Caught only because `--refresh` was deliberately run twice during authoring to prove idempotency — a self-test fixture alone (which only exercises a single before/after pair) would not have caught it. Fixed by detecting an already-applied stub (`**MOVED to` within a few lines of the anchor) and treating that as "already done," not "block still present." **Rule: any checker that PRESERVES part of what it moves/deletes (a heading, an id, a marker) must explicitly test the SECOND run of its own idempotent operation, not just the first — "found the anchor" and "the anchor's payload is still original" are different questions whenever the anchor itself survives the operation.**
- A second, smaller bug found the same way: the citation-census exporter (`collectCitations`) captured `specId` from its regex match but forgot to also capture `number` (the section token) — every real citation in the corpus then read as unresolvable (`c.number` was `undefined`, never matching any heading's `number`), producing ~1,300 false-positive "dangling citation" reports on the very first `--check` against the real tree. A self-test built entirely from hand-constructed fixture objects (which happened to always set `number` explicitly) never exercised the code path that actually derives it from a regex match. **Same rule, different angle: a self-test fixture that hand-builds the data structure a real code path DERIVES will not catch a bug in that derivation — run the real derivation function against at least one real input before trusting the self-test's green.**

## A cloud dispatch against a branch, not a pinned commit, can silently run stale code (EP-D13 re-attribution, 2026-09-08)
- GH run 34231689122 was dispatched to grade the converted `enrich_parcels` runner, but `origin/wf2/deep-scrapes-restore-l0` was 191 commits behind local at that moment (`3322be5c`) — the run's checkout carried a `converted.json` with no `enrich-parcels.js` entry at all, so it silently graded the LEGACY 2,153-line script instead. The 300-min budget failure was real, but every hypothesis built on top of it (a txn-shape change "the conversion introduced") was reasoning about code that never executed — caught only because the operator independently checked `origin/...`'s SHA against local after the fact, not by anything in the run's own output (a legacy-script run and a converted-runner run produce an identically-shaped "step X failed" verdict with no marker distinguishing which code path ran). **Rule: before any cloud dispatch that is meant to grade a specific local commit, assert `gh run view <id> --json headSha` (or the dispatch's own resolved SHA) equals `git rev-parse HEAD` for the intended branch — and push the intended commit FIRST, always, never dispatch against a branch whose remote state hasn't been freshly confirmed.** A workflow dispatch targets a BRANCH NAME, not a commit; the two silently diverge the moment local has unpushed work, and nothing about a cloud run's pass/fail output says which SHA it actually ran.

## 2026-09-14 — Vitest worker cap + `vitest related` scope (Spec 124 R-AG hooks)
- `VITEST_MAX_WORKERS` is NOT read by vitest (2.1.x, default `forks` pool). The real cap is `VITEST_MAX_FORKS=N` (or `--poolOptions.forks.maxForks=N`) — and on this 12-CPU host it MUST be paired with `VITEST_MIN_FORKS=1`, because vitest derives its default minForks from the CPU count and throws "minThreads and maxThreads must not conflict" when the cap is below it (measured: `VITEST_MAX_FORKS=2` alone ran zero tests with an unhandled RangeError). Every "capped" run today ran uncapped; a 4-fork full suite next to Docker was OS-killed for memory. **STALE as of 2026-09-16 (`review_followups.md` HIGH row, `.husky/pre-push` + `src/tests/step-conformance.infra.test.ts`) — corrected 2026-09-21:** `VITEST_MAX_FORKS=2` no longer completes the full suite at all (a `[vitest-worker]: Timeout calling "onTaskUpdate"` RPC timeout in `step-conformance.infra.test.ts`, not a real test failure, but `exit 1`); both `.husky/pre-commit` and `.husky/pre-push` now pin `VITEST_MIN_FORKS=1 VITEST_MAX_FORKS=1`, locked by `hooks-composition.infra.test.ts`. - `npx vitest related <file>` on a NON-source file (package.json, *.md, *.json) does not skip — it falls back to a wide run of unrelated suites. Only pass `src/**` / `scripts/**` `.ts|.tsx|.js|.mjs` paths; the pre-commit hook filters for exactly that and skips otherwise.
- POSIX `sh` hooks: never expand a multi-path variable unquoted (`$STAGED_FILES` word-splits on spaces); pipe one path per line through `xargs -d '\n'`.

## 2026-09-21 — A test that shells out to `git` inherits the SESSION's `GIT_*` env, and can author commits as someone else
- A test spawning `git commit` in a throwaway repo runs under whatever `GIT_AUTHOR_NAME` / `GIT_AUTHOR_EMAIL` / `GIT_COMMITTER_*` / `GIT_DIR` / `GIT_INDEX_FILE` / `GIT_WORK_TREE` the surrounding session exported. The visible symptom is a REAL commit in the REAL repo authored by the test's identity — `git log` on this branch carries several commits authored `capture-guard-test <test@example.invalid>` because a hook-exercising suite's identity leaked into the working tree's own commits.
- **Rule:** any test that shells out to `git` must (a) SCRUB every `GIT_*` variable from the child's env — allowlist, never denylist, since `GIT_DIR`/`GIT_INDEX_FILE`/`GIT_WORK_TREE` redirect the operation itself — and (b) FAIL CLOSED on a throwaway-repo guard: assert the target directory is the temp repo the test created (not `REPO_ROOT`, not an ancestor of it) BEFORE running any mutating `git` command, and throw if the guard cannot be evaluated. Commit `a0aee5ce` promised both arms; this lesson is the standing rule they encode.
- Related: the same scrub applies to any child process the suite spawns that may itself invoke `git` (hooks, `npm run` wrappers) — the leak travels through the environment, not the command line.
