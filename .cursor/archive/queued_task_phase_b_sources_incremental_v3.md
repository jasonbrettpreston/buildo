## Operator rulings
* **D1′ — REVISED on evidence (supersedes D1-A). Use `parcels.massing_enriched_at TIMESTAMPTZ`, compared against `parcel_buildings.linked_at` via `EXISTS`** — not a TEXT version column. Reason: **there is no massing version to store.** `load-massing`'s `records_meta` carries no dataset version, no `last_modified`, no hash, and `massing-full-gate.js:11-12` states this in prose. A TEXT column would be constant, making the gate constant-false (never fires — today's blindness) or constant-true (full 486K recompute every run) — the exact "watermark written but never read" failure B8 was going to record as a lesson. `parcel_buildings.linked_at` already exists, is NOT NULL and is indexed. This also mirrors the zoning pattern at `enrich-parcels.js:179-182`, removes the B5-before-B2 ordering dependency, and avoids the multi-GB invalidation UPDATE that the server's 2-min `statement_timeout` would cancel anyway.
* **D2′ — NO SPLIT** (operator revoked the split 2026-08-05 after the panel priced it). One `sources` chain; the quarterly full pass is a **variant of that same chain** — same id, same slugs, same consumers — with `timeout-minutes` raised toward the 360-min platform ceiling plus an explicit `--force-full` channel. Bi-weekly steady state is 30-45 min against a 180-min ceiling, so only the quarterly and worst-case runs ever needed more room. Dropping the split collapsed 2 BLOCKERS + 1 CRITICAL + ~30 consumer edits, preserved `run-chain.js`'s stop-on-first-failure guarantee (enrichment never runs against a failed load), and preserved Spec 58's FROZEN §9 assertion that `load_zoning` and `enrich_parcels` are in the same chain. **Contingency:** `enrich_parcels --full` has never been observed to finish (killed at 123 min), so if one measured quarterly run exceeds a single job, the split returns — decided on a measurement, not an estimate.
* **D3 — two-tier metadata→content-hash. MECHANISM CONFIRMED, SAVINGS CORRECTED.** CKAN polled 2026-08-05: address-points `last_modified 08-05T11:43`, property-boundaries `08-04T03:59` — **both moved within 48h while the last run changed 0 rows**. So tier-1 will report "moved" nearly every run and **tier-2 carries all the weight: the ~185 MB + ~327 MB downloads still happen.** Only parse+upsert is saved. **Realistic floor ≈ 30-40 min/run, not the report's 20-25.** The hash tier is nonetheless vindicated: `load_centreline` produced an identical content version across two runs 5h apart despite daily regeneration. Add an HTTP `Range`/`Content-Length` tier-1.5 before committing to a full download. **Stated assumption:** when `last_modified` is unchanged we never download or hash, so a content change without a timestamp change is missed — accepted, and now explicit.
* **D4′ — REVISED. Drop the spatial radius entirely; scope by DIRECT decision→parcel joins, and include `comp_count = 0`.** Three panel findings force this: (a) pass 4 is subject-driven kNN with **no radius cutoff in the code at all**, so D4 was new spatial-join work, not a parameter; (b) `comp_count IS NULL` is **0 rows** across all 440,267 eligible parcels, making the v2 predicate a **no-op on day one**, while **88,524 parcels (20.1%) sit at `comp_count = 0`** and would go permanently un-retried; (c) `parcels` has a geometry GiST index only, so `ST_DWithin(geom::geography,…)` cannot use it and seq-scans a 3.6 GB heap. **New scope: `comp_count IS NULL OR comp_count = 0 OR parcel_id IN (permit_parcels ∪ coa_applications.zoning_dominant_parcel_id for decisions landed since the last completed run) OR parcel in the pass-3 temp table.`** The last clause is required because **passes 4/5 key only on their own NULL markers and are NOT fed by the 1→2→3 cascade**, so a massing-driven pass-3 rewrite otherwise leaves `comp_build_ratio_p50`/`comp_fsi_p50` pinned to the old footprint forever — 89.5% of parcels are already in that never-refreshes state.
* **Prior rulings unchanged:** full architecture only · bi-weekly cadence · quarterly safety pass (**conditional — see B0**) · no sources rerun before this lands · `chain-sources` is `disabled_manually` and B6 must re-enable it in GitHub as well as in cron text.
