## Design decisions (Spec 124 §7 ladder, rung (a) throughout)

* **`invariants[]` and `plausibility[]` are two new top-level descriptor categories** (19th/20th, alongside the existing 18), both declarative-SQL, both executed generically by the library with zero hand-written compute:
  * `invariants[]` — single-table, single-step-scoped (the step's OWN writes; e.g. `parcel_buildings` uniqueness for `link_massing`). Shape: ~~`{id, sql, bound, severity, blocking, why, last_measured:{value,at,commit}, retighten_when?, frequency}`~~ **[Fold B correction — schema grows again]** `{id, sql, bound, severity, blocking, why, when: "pre"|"pre_write"|"post" (Fold B-2, required, default "pre"), source: "check"|"invariant"|"plausibility" (Fold B-3, required, closed), last_measured:{value, at, commit, cost_ms, sample_n (Fold B-1), source_run (Fold A-4e)}, retighten_when?, frequency}`. **`frequency: "every_run" | "validate_only"`** (closed enum, new field, required — see the Per-run cost section below: this is the direct schema response to that section's measured-cost finding, not a separate idea). `every_run` entries hook into the library at `:1834` on every pipeline execution; `validate_only` entries execute only from `step:validate --write`. A `bound.value` alone never implies cost — `frequency` is declared explicitly per invariant, defaulted from measured cost at migration time (commit 3/4: any candidate whose measured single-query time exceeds ~2 s is `validate_only` by default, overridable with a stated `why`). `bound` reuses `checks[].limit`'s grammar (Ask 2). `retighten_when` is a machine-readable STRING naming the condition (mirrors R-H's language, e.g. `"zero rows"` or `"population < N"`) — it does NOT replace the existing `<metric>_retighten` companion-audit-row convention (`scripts/lib/accepted-baseline.js`'s `acceptedBaselineRows`, Spec 48 §4.9): a WARN-severity invariant with `retighten_when` set gets its companion INFO row emitted by the SAME executor via that existing helper, reused not reinvented — `retighten_when` is the descriptor-side declaration, the companion row is the runtime-side emission, same pairing `link_massing`'s own `step_completeness_retighten` precedent already uses (Spec 48 §4.9's own worked example).
  * `plausibility[]` — cross-field/zone-aware, may span tables the step doesn't itself write (e.g. a `link_massing` plausibility check against `parcels.centroid_lat` populated by a DIFFERENT step). Same shape plus optional `zone_by`. **Reuse target is `parcel-sanity-audit.js`'s ENGINE (`statusFor`, `verdictCascade`, the single-scan `count(*) FILTER` fold pattern), NOT its `CHECKS[]` entries** — measured (re-verified this session via `CHECKS` array parse, `scripts/analysis/parcel-sanity-audit.js`): **42 checks** total (corrects an earlier 38-count typo in this same pass), 100% scoped to `enrich-parcels`/`compute-parcel-cost-estimates` output columns (bylaw/cost/opt_* fields on `parcels`), zero `centroid`-named check among them (`grep -n centroid parcel-sanity-audit.js` → 0 hits) despite `compute_centroids` writing exactly the field this file's own domain (`parcels`) contains — see the `compute_centroids` archetype-table row below, not "zero overlap" in the domain sense, but zero overlap in what's actually CHECKED.
