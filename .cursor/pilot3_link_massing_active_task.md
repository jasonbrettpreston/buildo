### ⚠️ The six findings that shape this whole plan (measured, not inherited)

1. **The step has NO library path.** `scripts/lib/step/index.js` `isIngestStep` requires `inputs.reads.externals[].url` to be a non-empty string. `link_massing` reads no external — it is a pure DB→DB join. So under today's library it falls to the **pilot-1 (ASSERT) path**: `compute(ctx)` iterates `ctx.checks` and the library writes nothing. **A LINK's join and write have no home.** `index.js`'s own header schedules the wave — *"`invalidation + counters scoped by writes.key` → **LINK/MATCHER**"* — but the write phase itself is INGESTOR-gated. **Ask A-1.**
2. **⛔ `guard_columns: "all_declared"` is a chain-scale regression, and it is the single most dangerous line in this conversion.** The live upsert (`scripts/link-massing.js` `flushInsertBatch`) guards on **exactly four** columns — `is_primary`, `structure_type`, `match_type`, `confidence` — and deliberately **excludes `linked_at`**, even though `linked_at = EXCLUDED.linked_at` is in the SET list. `scripts/lib/step/write.js` `resolveGuardColumns` expands `all_declared` to *every step-written column except the key*, which **includes `linked_at`**. `EXCLUDED.linked_at` is `RUN_AT`, so it is distinct on every run ⇒ **every one of the 520,492 rows updates every run**, and because `enrich-parcels.js buildMassingScopeWhere` re-scopes on `pb.linked_at > p.massing_enriched_at`, the next `enrich_parcels` run re-enriches **all 485,135 linked parcels** instead of 1,395. Measured `enrich_parcels --full` cost from `43_chain_sources.md`: ~46–53 min. **The descriptor MUST declare `guard_columns` explicitly.** This is the plan's #1 regression risk and gets a both-directions lock.
3. **Spec 122 §8.2's write-class label for this step (`F link_full_retraction`) does not survive re-derivation** — exactly the failure §1.4 warns about (*"the port must be verified per step, not trusted"*). Measured, this step performs **three disciplines to ONE table in sequence**, and none of them is a departure delete: **(W1)** a FULL-mode **step-scoped mass DELETE** of every link for centroid-bearing parcels (`DELETE FROM parcel_buildings WHERE parcel_id IN (SELECT id FROM parcels WHERE ${baseFilter})`), **(W2)** a **batch-scoped UNGUARDED `UPDATE … SET is_primary = false WHERE parcel_id = ANY($1) AND is_primary = true`** — class **G** `set_based_scoped` hiding inside a "link" step, **(W3)** a **batch-scoped guarded upsert** — class **A**. There is no `<> ALL($1)` departure delete and no zero-match delete anywhere in the file. **Incremental mode never retracts anything.** §1.4's per-target form is what makes this expressible; §8.2's scalar label is what concealed it.
4. **The write key is COMPOSITE and the generator refuses composite keys BY NAME.** `parcel_buildings` unique key = `(parcel_id, building_id)` (`parcel_buildings_parcel_id_building_id_key`, live catalog). `scripts/lib/step/write.js buildWritePlan` throws: *"composite keys are not supported by the generated class-B write … declare a single-column key or extend write.js first."* The schema ALLOWS an array key (`definitions.write.key` is `anyOf: [columnName, array]`); the generator does not. **Hard blocker for any library-owned write.
