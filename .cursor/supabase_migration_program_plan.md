## Key Decisions (v2 — panel-folded)
* **D1 — Philosophy A:** Next.js = single API gateway; `supabase-js` for AUTH ONLY; pipeline + admin keep raw `pg`; no PostgREST for pipeline; clients keep `{ data, error, meta }`.
* **D2 — TLS:** one shared `scripts/lib/ssl-config.js`, CA-pinned `verify-full`; `rejectUnauthorized:false` BANNED (harden `client.ts`). **Environment-aware:** `SUPABASE_CA_CERT_PATH` env var; local `supabase start` + CI containers = local no-TLS/own-cert mode; cloud = pinned Supabase CA. CA-rotation safety: cert expiry check in `ai-env-check.mjs` + documented rotation runbook (cert is fetchable from dashboard/API at any time). **CI also runs one TLS-required Postgres container test exercising the helper's verify-full path** (not only the no-TLS local mode) — R2-panel fold.
* **D3 — Pooler routing:** pipeline/migrations/seeds → direct (IPv6) or session pooler 5432; Vercel serverless → transaction 6543 with pinned low pool `max` (G7). Per-surface table in infra spec.
* **D4 — PostGIS into `public`** (matches 220 migrations; non-relocatable; rewrite not worth it). **Pin the PostGIS/GEOS version** in the infra spec; record `postgis_full_version()` on both sides of every load (G10 geometry gates).
* **D5 — One migration engine:** `migrate.js` stays authoritative. Supabase CLI = local stack ONLY. **Schema-altering CLI commands (`db push`, `db reset`, `db remote commit`) are forbidden** — documented in infra spec + guard: fail `ai-env-check`/pre-commit if `supabase/migrations/` contains files. Infra spec records the stronger DB-level guardrail (dedicated `migration_runner` role holding DDL privileges, developer roles DML-only) as a post-launch hardening option — deferred while solo-dev.
* **D6 — uid→uuid + FKs (10 tables per G9), per-FK `ON DELETE` evaluation** (panel: no blanket CASCADE): CASCADE for user-owned rows (`lead_views`, `lead_view_events`, `device_tokens`, `subscribe_nonces`, `tracked_projects`, `notifications`, `notification_dispatches`, `user_profiles` PK); **SET NULL/RESTRICT for `admin_watchlist.admin_uid` + `admin_audit_log.admin_uid`** (audit trails must survive account deletion — align with the P24 RTBF scrub pattern: scrub PII, keep the row). Supersede ADR-006; delete `purge-lead-views.js`; retire `firebase_uid_max` from `_contracts.json` + `mobile/src/constants/contracts.ts` + `factories.ts` + `contracts.infra.test.ts` same-commit. **Phase 1.4 pre-condition: re-verify all 10 tables are 0 rows on the ACTUAL target DB at execution time; any row count > 0 HALTS the migration** — HALT procedure: dump the offending rows, human signs off on delete-or-keep, then re-run the gate (never a blind `--force`).
* **D7 — Auth posture:** asymmetric JWT keys day-one; `getClaims()` hot paths / `getUser()` for revocation-sensitive ops — **S3 spec defines the criteria concretely** (money movement, account mutation, admin writes ⇒ `getUser()`; read paths ⇒ `getClaims()`); admin authorization = server-side `profiles.is_admin` check inside `verify-admin.ts` (Custom Access Token Hook DEFERRED — over-engineering for a server-gated admin; revisit only if claims needed inside JWTs); TOTP MFA for admins WITH break-glass (R2); custom SMTP / raised email rate limits before test provisioning; `@supabase/ssr` `getAll`/`setAll`; `route-guard.ts` kept verbatim; all three DEV_MODE call sites preserved (G2). `X-Admin-Key` CI bypass re-evaluated in Phase 1.3 (scope to CI IPs / replace with service-role + IP allowlist).
* **D8 — Scheduling:** **Compute backend named (R2 fold): the GitHub Actions RUNNER executes `run-chain.js` directly** against Supabase (6-hour job limit accommodates 90-min chains; a Vercel function cannot — 800 s cap). `CRON_SECRET` (Vault, constant-time compare) still guards any HTTP trigger surface.
