## Questions for the operator (y/n, one recommendation each)

**Q1.** Should we add one new archetype for steps whose output is an outside side effect rather than rows? It would cover dispatch_notifications (push to users) and backup_db (off-site dump).
- It would require a kill switch or injected transport, an exactly-once ledger or manifest, and a G8 that never contacts the real service.
- It needs a Spec 122 §1.10 ruling and a schema re-freeze.
- **Recommend y.** None of the 8 archetypes describes these two steps. Forcing them into one would make the required fields wrong (RECORDER means writing state into a table).

**Q2.** Should observe_chain become a `runner_owned` exemption? That means adding observability to the RUNNER concerns in Spec 122 §7.3, so that R-AP covers it.
- run-chain.js spawns it after the chain finishes (scripts/run-chain.js:1353).
- It is in no chain and writes only a report file.
- **Recommend y.** This matches how reconcile is handled. R-AP today only lists concerns that §7.3 names, so the ruling is needed.

**Q3.** Should we retire reclassify_all, removing it from manifest.scripts, instead of converting it?
- It is in no chain, and amnesty.json calls it one-off maintenance.
- classify_scope and classify_permits already do the same work with `--full`.
- **Recommend y.**

**Q4.** For the three paid-API enrichers, should G8 replay from recorded Serper and website responses rather than making live calls?
- **Recommend y.** Live replays cost money and never repeat exactly.

**Q5.** Should backfill_realtor_permit_trades leave the daily permits chain if one current run inserts 0 rows?
- Its own header calls it a one-time ride-along, and classify_permits already appends realtor rows live.
- **Recommend y**, after that one measured run.

**Q6.** Should close_stale_permits be folded into load_permits' declared `retract`?
- It writes the loader's own `status` column, so it is really the permits feed's retraction.
- **Recommend n for now.** load_permits is in the middle of wave 4. Instead, convert it as its own ENRICHER-shaped step and have load_permits' descriptor name it as its retract partner. Revisit after wave 4.

## Findings, logged as PINs and not fixed here

- **F1.** classify_permit_phase (:56) and classify_inspection_status (:83, :109) bump `permits.last_seen_at`. That is the column close_stale_permits uses to detect that a permit has left the feed, so bumping it can hide a disappearance.
- **F2.** close_stale_permits reads the wall clock (CURRENT_DATE :130, NOW() :150) instead of the run's timestamp, so G8 replays will drift.
- **F3.** link_similar and classify_scope (:534-536) both copy BLD scope onto companion permits, with different rules: one merges tags, the other overwrites. link_similar never removes a tag.
- **F4.** compute_timing_calibration_v2 only upserts, so phase pairs that stop occurring keep their old rows.
- **F5.** enrich_web_search and enrich_wsib write their own `pipeline_runs` rows, which is a RUNNER concern. The conversion removes these.
