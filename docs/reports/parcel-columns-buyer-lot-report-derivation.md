# Parcel Column Derivations — Buyer-Facing Lot Report

**Purpose:** read-only research explaining how `parcels` table columns are derived, to support a buyer-facing lot report ("what can a buyer do with this lot"). **Source of truth for the column list:** `src/lib/db/generated/schema.ts` (`export const parcels = pgTable(...)`, lines 733-900) — every column below was generated by walking that table definition top-to-bottom, so nothing in the live schema is skipped. Writers traced via `scripts/*.descriptor.json` outputs.writes, `scripts/lib/compute/enrich-parcels.js`, `scripts/lib/optimal-config.js`, `scripts/lib/max-build.js`, `scripts/lib/parcel-cost.js`, cross-checked against governing specs (`docs/specs/01-pipeline/55/58/59/61/62/65/78/88_*.md`) and `tasks/lessons.md`.

Within each group, fields are ordered **most buyer-decision-relevant first**, then supporting inputs, then provenance/basis/audit fields last.

**Confidence-rating scope:** all confidence ratings in this report are calibrated for **detached and semi-detached residential lots** (zoning `RD`/`RS`) — the buyer-report target audience. This matters concretely, not just as a caveat: `scripts/lib/build-norms.js#parcelFamilyFromZoningCaseSql` pools `RD`+`RS` into a single `'detached'` cohort because it is the family with the deepest permit/CoA sample size citywide — several fields below (notably Group 12's `realized_fsi_p90`/comp stats) are *only* grounded in market-realized data for this family; townhouse (`RT`) and multiplex (`RM`) are thin cohorts kept on by-law numbers instead, and would rate lower than shown here.

**Advertising slots are intentionally excluded** — no schema exists for that feature yet (confirmed with requester 2026-09-28). See note at the end.

**Confidence methodology (revised):** an earlier pass in this report conflated "NULL/sparse" with "medium confidence." That's wrong for a directly-joined authoritative field — a NULL bylaw cap does not mean *we're unsure of the number*, it means *no numeric rule is on record for this attribute in this zone*, which is itself a fact, not an uncertainty. This report now rates every field on three separate axes, and states which one(s) actually apply:

1. **Value confidence** — when the field IS populated, how much do we trust the number? Direct spatial/attribute joins against an authoritative source (bylaw tables, ravine/heritage registers, `permits`/`coa_applications` records) are **High** whenever populated — there is no estimation step. A number produced by a formula/heuristic on top of those joins (empirical percentiles, imagery measurement, flat modeling assumptions, retired/known-wrong methods) is genuinely **Medium/Low**, because the uncertainty lives in the *method*, not in missing data.
2. **Applicability / coverage** — does a rule or record even exist for this parcel? A NULL here (e.g. `bylaw_max_coverage_pct` on ~37% of parcels) is a fact about the bylaw or the match, not a confidence downgrade on any number — it is reported separately, and only becomes a real quality issue when a *downstream fallback* (e.g. a zone-class default) has to stand in for it, which is a Value-confidence question for that fallback specifically.
3. **Inference / discretion gap** — for CoA and "market-realized" fields, even a High-confidence historical statistic (real approvals, real permits) carries an irreducible "past outcome ≠ guaranteed future outcome" gap, because CoA decisions are discretionary case-by-case. This is not a data-quality problem and no amount of sample size closes it.

| `bylaw_min_area_sqm` | Base `area_min_sqm`, MAX | |
| `bylaw_standard_setback_m` | Base `standard_setback`, MAX | This is the FRONT setback when present; side/rear/flankage always use the zone-class default table (no source field for those). **Externally verified against By-law 569-2013 (2026-09-28):** unlike coverage, setbacks are NOT overlay-map-dependent — the by-law defines them as universal formulas directly in the RD (§10.20.40.70) / RS (§10.40.40.70) zone text: **rear = greater of 7.5m OR 25% of lot depth** (our flat 7.5m constant matches only the floor — understates the true requirement for any lot with `depth_m > 30`); **side = tiered by lot frontage** (0.6/0.9/1.2/1.5/1.8/2.4/3.0m bands; our flat 0.9m matches only the 6–12m band — understates the true requirement for any lot with `frontage_m ≥ 12`). **Front = flat 6.0m ONLY as a baseline — CORRECTED, 2026-09-28: §10.5.40.70(1) "Front Yard Setback Averaging" (Chapter 10.5 general provisions) supersedes the flat 6.0m whenever a qualifying neighbour exists** — if an abutting lot's building fronts the same street within 15.0m, the required front setback becomes THAT neighbour's actual front setback (or the average of both neighbours', if between two qualifying lots). **Confidence: High across the entire group, when populated** — but "NULL" has two genuinely different causes here, worth telling apart precisely rather than waving at "sparse by design":
- **`bylaw_max_fsi`:** NULL is a real applicability fact — the dominant zone's own FSI cap field is legitimately absent for that zone category in Toronto's base zoning dataset (not merely unmapped elsewhere).
- **`bylaw_max_coverage_pct`: CONFIRMED against Toronto's actual by-law text (external web search, 2026-09-28) — this is a genuine applicability fact, not a data-ingestion gap.** By-law 569-2013 §10.20.30.40(1)(B) (RD) and the identical §10.40.30.40 (RS) state verbatim: **"if a lot is not in an area with a numerical value on the Lot Coverage Overlay Map, no lot coverage applies."** This is unambiguous: for an unmapped lot, there is no legal coverage restriction at all — not an unreachable real number, a genuine absence of the constraint. **State this plainly, not hedged: for these parcels, `bylaw_max_coverage_pct = NULL` should be read as "confirmed unlimited by this provision — not capped." That is the reality, verified at the source, not an inference or a data gap.** (Wrinkle: §10.20.30.40(1)(D) says if the Overlay value IS present but below 45% and the lot has a houseplex/secondary suite, the effective cap becomes 45%, not the mapped value.) This means `COVERAGE_DEFAULTS` (Group 5) is **not** approximating a real hidden by-law number — it is a defensive engineering guardrail against the `LEAST()` NULL-skip bug (the original ~67%-coverage incident), invented precisely because no legal number exists to read for these parcels. Practical implication: for an unmapped RD/RS lot, the true as-of-right footprint may legitimately exceed 33% coverage (bounded only by setbacks/height/FSI) — the system's default is conservative, potentially under-stating buildable potential, not over-stating a real cap. **Verified directly for all four residential families — RD, RS, RT, RM all confirmed "no lot coverage applies" when unmapped (see the full verified matrix below).**
- **`bylaw_max_height_m`:** ~10% null, closer to the FSI case (a real applicability gap on the height-overlay layer specifically, ~89.8% populated).
Reading any of these NULLs as "medium confidence in a fuzzy number" is a category error — there is no number to be unsure of in any of the three cases; the difference is only in *why* there's no number (bylaw-silent vs. source-layer-gap). The one place this group's confidence genuinely drops on a *populated* value is `zoning_is_ambiguous` (`share<0.60`, ~0.2% of parcels) — a boundary lot split across zones where the dominant-zone precedence rule itself becomes a judgment call.

**Confidence: split by field, not one blended number — applying the 3-axis framework above matters most in this group, because it's the first place raw bylaw joins get *combined* with geometry and estimates:**
- **`max_buildable_footprint_sqm`, `max_build_width_m`/`_length_m`: correction — NOT cleanly High even when coverage is populated.** `bylaw_standard_setback_m` (`STAND_SET`, same base layer as coverage) behaves identically to coverage: High when populated, and when NULL the FRONT setback falls back to `SETBACK_DEFAULTS` (a zone-class estimate, e.g. 6.0m for RD/RS/RT/RM/R) — `max_build_setback_basis` records which case applies (`'bylaw'`/`'zone_default'`). **But per Spec 65 MB-4, `side`/`rear`/`flankage` setbacks have NO source field in Toronto's published dataset at all — they are ALWAYS the hardcoded `SETBACK_DEFAULTS` estimate, for every parcel citywide, unconditionally, regardless of whether front-setback or coverage data is present.** So even a parcel with `max_build_setback_basis='bylaw'` AND `bylaw_max_coverage_pct IS NOT NULL` still has 3 of the 4 setback directions feeding its footprint/width/length from the estimate table. **Externally verified (2026-09-28, see Group 2): unlike coverage, this is NOT because no rule exists — the by-law defines real, universal, deterministic formulas for rear (greater of 7.5m or 25% of lot depth) and side (tiered by frontage) directly in the RD/RS zone text, no overlay dependency.** Our flat-constant approximation is accurate only within specific bands (depth ≤30m for rear; frontage 6–12m for side) and **understates** the true setback — hence **overstates** the modeled footprint/width/length — outside those bands. The honest confidence ceiling for these three fields is therefore **Medium for the geometry itself** (real polygon + real coverage/front-setback where available, but a band-limited flat-constant approximation for side/rear/flankage with a known, checkable divergence on wide/deep lots), not High — `max_build_setback_basis='bylaw'` only certifies the front dimension, not the whole shape. The `COVERAGE_DEFAULTS` zone-median (RD/RS/RT≈33%, RM≈30%, R≈35%) is Medium for the same reason as the setback defaults: inferred from other parcels, not this one — check `max_build_coverage_binding_count` for whether it was actually load-bearing on a given row.
- **`max_buildable_gfa_sqm`, `max_build_stories`, `max_build_stories_basis`: capped at Medium even on a `'high'`-confidence row**, because GFA multiplies footprint by storeys, and storeys is a 3-way fallback (`bylaw_max_stories` → empirical pocket `storeys_p50` → `height/storey_height`) that is only genuinely High when `max_build_stories_basis='bylaw'`; `'pocket'`/`'derived'` are estimates, not by-law numbers.
- **`max_build_confidence` (the stored label) is narrower than "the whole envelope is solid":** per the CASE above, `'high'` certifies lot geometry + real bylaw setback + FSI-or-height presence — it does **not** certify non-defaulted coverage or a bylaw-sourced storey count. Treat a `'high'` row's footprint/dims as trustworthy, but still check `bylaw_max_coverage_pct IS NOT NULL` and `max_build_stories_basis='bylaw'` independently before calling the GFA number itself High confidence.
- **`envelope_constrained`/`envelope_constraint_reason`/`max_build_basis`/`max_build_fsi`: High** — these are direct, deterministic reads off the already-computed fields above, not independent estimates.

### Coverage vs setback — the report shows both (operator 2026-09-29) — MORE RESEARCH REQUIRED

* **Operator challenge (2026-09-29):** a coverage percentage gives a maximum footprint, but the owner must still meet every setback. The coverage-implied footprint may not fit inside the setbacks, so the real maximum may be set by the setbacks.
* **Where the model already agrees:** EF-2 takes `LEAST(buffer, box, coverage_cap)`, so setbacks win whenever they are smaller. V25 shows the real setbacks plus the NF-11 depth cap deciding (≈573 → ≈312 m²) with no coverage term.
* **Decision: show both, not one number.** NF-17 (setback-only footprint) and NF-18 (coverage-only footprint) are exposed side by side, and NF-19 names the one that binds. EF-2 (the headline footprint) is unchanged here.
* **MORE RESEARCH REQUIRED before implementation:**
  * **R1 — zone-median coverage default.** `scripts/lib/compute/enrich-parcels.js` computes `coverage_cap = COALESCE(bylaw_max_coverage_pct, zone median)`. On NF-8 `'unregulated'` lots the by-law applies no coverage limit, yet the median still enters EF-2's `LEAST` and can bind. The median was added (comment at the `coverage_cap` CTE: "else LEAST drops the term and the footprint balloons to the setback box (~67% coverage)") when setbacks were flat 0.9 / 7.5 m with no length/depth caps. Whether it retires once NF-1..4, NF-10 and NF-11 land needs a Reality-Check measurement (how often the median binds today, and by how much) and a Regression Guardian fence ruling.
  * **R2 — coverage-only fallback (EF-11).** When width/length is NULL the footprint is coverage alone, with no setback check. Decide what the report shows; interim: NF-17 NULL and NF-19 `'coverage_only_unchecked'`.
  * **R3 — shape feasibility.** A footprint inside both limits can still be unbuildable (minimum dwelling width, irregular polygons); the buffer's minimum-dimension floor is the only current guard.
  * **R4 — binding distribution.** Measure, per zone on real lots, how often setback vs coverage vs the length/depth caps bind before choosing any headline rule.

**Soft vs hard, in plain language (derived from the ledger):**
* **Landscaping** is trees, plants, decorative stonework, retaining walls, walkways and similar elements. Driveways and parking areas are never landscaping (L1).
* **Soft landscaping** is landscaping minus the hard-surfaced parts: stonework, retaining walls, walkways (L2). The by-law never defines "hard landscaping" (L3). In this report "hard" means landscaping that is not soft, which is a derived term.
* **Front yard, two steps:** first, a minimum share must be landscaping, set by frontage (L5 under 6.0 m, L6 50%, L7 60%). Second, at least 75% of that required landscaping must be soft (L8). If there is **no** permitted front-yard driveway, at least 75% of the **whole** front yard must be soft (L8). A driveway removed under the zone-chapter conversion rule still counts as a driveway for this test (L18).
* **Rear yard, one step:** a direct soft share (L10). Pool water surface counts as soft for the rear-yard rule, not the front-yard rule (L14). A garden suite (L20) or laneway suite (L21) replaces the rear rule.
* **Decks/porches:** where a platform encroaches into a required setback as allowed by 10.5.40.60 (L23), that area is excluded from the landscaping calculation (L13(A)(i)).

**Worked example (computed by the generator):** the front yard is 10 m frontage × 6 m deep = 60 m². 10.0 m is in the 6.0 to less-than-15.0 m tier, so 50% must be landscaping (L6).
* **With a 3.0 m private driveway** (within L15(C)'s 6.0 m cap, and at least one 2.6 m parking-space width, L25): driveway = 3.0 × 6 = 18 m², which is neither soft nor hard (L1). Landscaping ≥ 30 m² (L6). Soft ≥ 75% × 30 = 22.5 m² (L8). Up to 7.5 m² of the required landscaping may be hard (derived, L2/L3). The other 12 m² is unconstrained by 10.5.50.10 but may not be a parking space (L16).
* **With no driveway:** landscaping ≥ 30 m² (L6), but the no-driveway branch requires soft ≥ 75% × 60 = 45 m² (L8), so the soft rule governs. At most 15 m² may be non-soft.

### Building type and current-stories — corrected: NULL-default input fields, not propagated (2026-09-28)

**Correction to the prior round's proposal:** propagating `permits.building_type` onto the dominant parcel was the wrong approach — permits are only a subset of parcels (most lots have no permit history at all, and an old permit may describe a demolished building), so propagation would leave most parcels NULL anyway while risking stale data on the rest. The right approach for both fields:

1. **`parcels.building_type`** — new column, **NULL by default**, populated only by manual/future input (not auto-derived from `permits.building_type`, despite that field being real, natively-ingested Toronto data — it's simply the wrong population to draw from for a per-parcel default). Needed because the RT/RM side-setback and RM height formulas are building-type-dependent (detached/semi-detached/townhouse/apartment *form*, not `zoning_class`).
2. **`parcels.current_stories`** — new column, **NULL by default**, substantively the same concept as the already-existing, already-retired `existing_stories` column (Group 10) — currently permanently NULL because the only automated source (massing/tree-canopy estimation) was proven unreliable. A manual-input field lets a human override that broken estimate, a genuinely strong fix to this report's single largest previously-identified remaining gap.

**Both are a UI capture/override mechanism, not a backend pipeline formula** — different Domain Mode (Admin/Cross-Domain, per this project's Domain Rules) from the setback/height/coverage work above (Backend/Pipeline). No existing "manual override" input pattern was found elsewhere in this schema to model it on; this would be new UI/product design, not a research finding pulled from existing code. Recommend scoping as its own WF1 (new feature), separate from the by-law-formula WF2, since it has a different domain declaration, a different consuming surface (buyer-facing UI, not `enrich-parcels.js`), and a different kind of "input" (viewer-supplied, not by-law-derived or propagated).

## FUTURE CONSIDERATION — a `bylaw_provisions` reference table (2026-09-28, not scoped into the WF2 above)

Raised during this research: instead of (or in addition to) hardcoding the newly-verified formulas as JS constants (mirroring the existing `SETBACK_DEFAULTS`/`COVERAGE_DEFAULTS` pattern), store each by-law provision as data — citation, verbatim text, applicable zone(s), and the structured rule — in a dedicated table.

**This connects to an existing, already-accepted DEFER item**, not a new idea invented here: `docs/reports/review_followups.md` (LOW, coverage-default WF3) already states *"Max-build geometry defaults are JS constants, not admin-tunable... Revisit as ONE task externalizing all three geometry-default families to `logic_variables` + the control panel."* This proposal is the richer version of that same deferred work — `logic_variables` handles flat scalars well, but the newly-verified rules (frontage-tiered bands, building-type branches, the front-yard-averaging cross-parcel lookup) need more structure than one name→one number, plus the citation/verbatim-text traceability this report has been building by hand throughout this research.

**Why it matters beyond tidiness — two distinct benefits, not one:**
1. **Maintainability:** by-laws get amended (this report already found a live example — the 2025 draft amendment to the garden-suite rear-yard term, noted in `optimal-config.js`'s `BYLAW_VERSION` stamp). A citation-and-rule table makes a future amendment a data update with an audit trail, not a code deployment with the citation buried in a source comment.
2. **Direct buyer-facing product benefit (raised during this research):** if the citation/verbatim text lives in the same table that computes the number, **the buyer report can show its actual legal basis next to each figure** — e.g. "Rear setback: 7.5m — By-law 569-2013 §10.20.40.70(2)" with the verbatim clause available on demand — instead of a bare number with no way for a buyer (or a skeptical agent/lawyer) to verify where it came from. With the current hardcoded-JS-constant approach, that citation text would have to be separately duplicated into UI copy, disconnected from the value it describes and prone to drifting out of sync when the formula changes. This is a direct instance of this project's own stated goal (trustworthy data, understandable without forensic queries) — it turns this report's own citation-ledger discipline into something the end user benefits from directly, not just an internal audit trail.

**Scope boundary, stated honestly:** this is bigger than the WF2 above and should be a separate, follow-on decision — closer to a WF1 (new architecture) than fixing already-identified wrong formulas. This codebase already has precedent for structured jsonb rule storage (`zoning_overlays`, `variance_context`), so a `bylaw_provisions(citation, zone_scope, verbatim_text, rule_definition jsonb, source_url, effective_date)` shape is architecturally consistent, not a foreign pattern — but designing the rule-evaluation engine (reading a jsonb rule and producing the same SQL a hardcoded `CASE` would) is real, additional engineering scope. Recommend: land the WF2 fixes above first (as verified, already-scoped hardcoded formulas), then treat migrating them into a `bylaw_provisions` table as the first content for this follow-on, rather than blocking the setback/height/coverage fixes on a larger redesign.
