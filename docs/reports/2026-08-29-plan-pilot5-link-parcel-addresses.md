### The six findings that shape this whole plan (measured, not inherited)

A parcel boundary correction (subdivision, consolidation, a Toronto Open Data re-survey) or an address-point coordinate correction can silently invalidate an already-written `parcel_address_points` row — `ST_Within(ap.geom, p.geom)` no longer holds — and class D's `ON CONFLICT (parcel_id, address_point_id) DO NOTHING` (`:176`) has no mechanism that ever re-evaluates or removes that row (`grep -c "DELETE" scripts/link-parcel-addresses.js` → **0**). `scripts/link-parcels.js:282` states the reliance explicitly, in-file: *"parcel_address_points guarantees the AP geom is INSIDE the parcel."* Strategy 1a (confidence 0.97) and Tier 1a (confidence 0.95, `link-coa-to-parcels.js`) both trust this guarantee unconditionally. **Measured live exposure TODAY: `SELECT COUNT(*) FROM parcel_address_points pap JOIN parcels p ON p.id=pap.parcel_id JOIN address_points ap ON ap.address_point_id=pap.address_point_id WHERE NOT ST_Within(ap.geom, p.geom)` → 0 of 511,224 rows (~~2.0s, this session~~ **AMENDED (Fold B, 2026-08-29): re-run this fold at ≈1.4s — the query cost is session-variable (table statistics, cache warmth), not a fixed figure; trivial either way against the ~200s step**).** Per Spec 123 §3's PIN-vs-FIX ladder: this is a **DEFECT** (a spec/consumer asserts the opposite of what the code guarantees) with **zero measured current blast radius** — the textbook case for §3.1's rule: *pin the non-retraction as-is, convert, prove bit-identical output, then decide the fix in a separate ruling* (this pilot's A-1, below — not bundled into the conversion commit).
