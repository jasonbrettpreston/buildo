- **[HIGH]** (line 75–76): Finding (b) iterates `commits` (built only from `git log HEAD` at line 29) and filters by `rangeShas`. Any commit in `--range` that is *not reachable from HEAD* (e.g. `--range HEAD..somebranch`, `--range otherB..HEAD` when `otherB` has side commits, or a tag pointing elsewhere) is in `rangeShas` but never visited. The loop silently checks nothing and the summary prints `range: 0 commit(s)` even though `rev-list` returned N. This is a silent false negative: the tool claims it checked a range it did not. Fix: enumerate the range directly with `git rev-list <range>` → `git rev-list --format`/`git show --format` per sha, or at minimum assert every `rangeSha` was seen in `commits` and exit 2 otherwise.

- **[HIGH]** (lines 65–84 combined): The primary check is largely toothless against the realistic violation. Finding (a) is skipped whenever `newest.has(t.id)` is true (line 65) — i.e. whenever *any* commit in all of HEAD history ever carried `Task: task-N`. But the normal lifecycle gives a task RUNNING-era trailer commits while it is being built. Scenario: commit1 `Task: task-2` while status RUNNING; commit2 flips status to BUILT with **no trailer**. (a): `newest.has('task-2')` → skip. (b): commit1 was RUNNING → `continue`; commit2 has no trailer so it is never examined. Result: 0 findings, yet the closing commit has no `Task:` trailer — exactly what the check exists to catch. The check never ties the *status transition* to a trailer on the same commit. Fix: require that the newest commit touching the task file (or the commit that set BUILT/DONE) carries the trailer, not that *some* historical commit does.

- **[HIGH]** (lines 42–43): When `origin/wf1/mb-rulings` is absent (fresh clone, CI checkout without that remote ref, non-standard remote name, shallow clone) `range` falls back to `HEAD` (line 37), and finding (b) scans **entire** history. Combined with line 82 (`newest.get(id) === c.sha`) every historical BUILT closing commit that is no longer the global newest (tasks reopened, follow-up commits, cherry-picks) becomes a `FAIL`. In CI this turns "clean" into a wall of false positives, and it also spawns 2 git processes per trailer commit over full history (line 52/56) — minutes on a large repo. Fix: require an explicit `--range` when the base ref is missing (exit 2 or a loud WARN), and/or bound the default to `HEAD`'s recent history only.

- **[MED]** (lines 68–69): Docs-only classification uses `git diff-tree --root --no-commit-id --name-only -r <last>`. For a **merge commit**, `diff-tree` emits *no* output without `-m`/`-c`, so `files` is empty, `!files.some(...)` is true, and a code-bearing merge is downgraded from `FAIL` to `WARN`. Same downgrade on any `diff-tree` error (stdout empty). Fix: detect merge parents (`%P` has >1) and handle them explicitly (FAIL, or diff against first parent with `-m --first-parent`), and check `git diff-tree` exit status before trusting empty output.

- **[MED]** (lines 82, 34–35): `newest` is the global first-seen trailer commit across all of `HEAD`, not scoped to the range and not topology-aware. Two failure modes: (1) With a bounded `--range a..b`, a task whose BUILT closing commit is at `b` but which has a *later* trailer commit outside the range is flagged `FAIL` ("was BUILT at that commit, not RUNNING") even though, in that range, it *was* the closing commit. (2) `git log` orders by committer date; after a rebase/merge a side-branch commit can carry a newer date and be chosen as "newest" over the true tip. Use `--topo-order` and compute "newest" within the same commit set being evaluated (or note the limitation).

- **[MED]** (line 82): Any commit that re-states `Task: task-N` after the task is already BUILT (follow-up fix, doc touch that keeps the trailer, cherry-pick) becomes the new "newest", demoting the real closing commit to "not newest" → `FAIL`. The docs-only WARN exemption in (a) does not apply here. Real-world false positive on any reopened/re-touched BUILT task. Fix: allow BUILT/DONE on *any* commit that is not followed (topologically) by a RUNNING-era trailer, or restrict the "own closing commit" test to status transitions.

Overall verdict: the happy path and the author's own test cases are solid, but the check measures the wrong thing for its headline rule. Finding (a) only fires when a task was *never* named by any trailer, so the realistic violation — a RUNNING-era trailer exists but the BUILT/DONE transition commit lacks one — passes silently (HIGH). Finding (b)'s `--range` support is only partially real: commits outside HEAD's ancestry are dropped without notice, and the "newest trailer commit" is computed globally over date-ordered `git log` rather than topologically within the evaluated set, producing both false positives (bounded ranges, re-touched BUILT tasks, merge/clock-skew ordering) and false negatives (merge commits downgraded to WARN). The default-range fallback to full history when `origin/wf1/mb-rulings` is missing is the most likely production failure mode — it will generate piles of false FAILs and run slowly in any CI checkout lacking that ref. The exit-code contract is mostly honored, but a missing git binary or bad `--root` yields a clean exit 0, and a parseFM throw masquerades as a FAIL (exit 1) with no FAIL line. Fix the status-transition/trailer binding, scope "newest" to the evaluated commit set with topo order, reject/guard the no-base-ref case, and harden the git wrapper's error handling before wiring this anywhere near a push gate.
