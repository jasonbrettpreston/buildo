- **CRITICAL** (`project.ts:freshnessOf`, cited as "the miss rule rests on it" — lines defining `moved[]`): `settings_sha` is selected by `ROWS_SQL` but **never compared**, and `evaluator_version` is selected by `STAMP_SQL` but **never compared**. The only checks are `layer2_table_version`, `catalogue_sha`, `switchboard_sha`. doc-16 §4 (which the whole lens rests on) says the record is stamped with "table_version, evaluator_version, settings sha", and the lens promises "a stale record is a miss and no legacy value appears anywhere in the payload". A settings change — i.e. the exact thing that changes a lot's numbers without touching the code — produces `verdict: 'current'` and **serves a stale Max-build to a customer**. `settings_sha` being selected-but-unused is the visible seam of the unfinished rule. Fix: add `rows.some(r => r.settings_sha !== current.settings_sha)` and `rows.some(r => r.evaluator_version !== stamp.evaluator_version)` to `moved[]`, extend `SeedShas` accordingly, and delete any column you're not checking (dead SELECT columns read as "done").

- **HIGH** (`project.ts:freshnessOf`, the `if (stamp?.lot_gate)` branch): `gated` short-circuits *before* the `rows === null` and rows-length checks, and `pageForVerdict` serves `stored.response` for `gated`. So a lot with `lot_gate` set and (a) an absent scenario table, or (b) stale rows, is served a page. The comment claims "a gated lot is a deliberate all-not-evaluated page" — but nothing in the diff proves `projectStoredPage` blanks values when `rows` is `null` or stale in the gated path; the projection is handed the stale rows as-is. If it doesn't blank them, a gated lot renders stale numbers — the one thing the lens forbids. Fix: prove it with a test that a gated lot with stale/absent rows yields all-not-evaluated, or move the gate check after the freshness computation and return the projection built from `rows: null`.

- **HIGH** (`report-page.ts +26,37`, `readCustomerPageResponse`): `null` is overloaded to mean four different things — switch off, parcel not found, `out_of_date`, `not_stored` — and the module's own comment says LOAD.1 "reads [null] as compute". So with `MAXBLD_WEB_LIVE` false, the very next task in the chain still reads "compute", which means the switch does not actually pin anything off once LOAD.1 lands; and a lookup on a **nonexistent parcel** (or a mistyped one from a search suggestion) starts a producer job for a lot that doesn't exist. Return a discriminated result (`{kind:'page', page}` / `{kind:'miss', reason:'switch_off'|'not_found'|'stale'|'not_stored'}`) so the consumer cannot conflate them.

- **HIGH** (`project.ts:freshnessOf`, `r.layer2_table_version !== stamp.table_version` and the two sha comparisons): these compare columns from **two different tables** with no type normalisation. pg returns `int4` as `number` and `int8`/`numeric` as `string`; `character(n)` returns **blank-padded**. `"7" !== 7` and `"abc        " !== "abc"` both evaluate true → every lot is permanently `out_of_date` → every lot is a miss → the feature silently never serves a single page, forever, and "miss" is the pre-existing normal state so nothing alarms. It's fail-safe (never a false `current`) but operationally fatal. Verify now: `SELECT data_type, character_maximum_length FROM information_schema.columns WHERE (table_name='bylaw_resolution_lot_stamps' AND column_name IN ('table_version','evaluator_version')) OR (table_name='parcel_maxbld_scenarios' AND column_name IN ('layer2_table_version','catalogue_sha','switchboard_sha','settings_sha'));` then normalise both sides. And add one integration test against a real DB — a `logic.test.ts` with a fake `Queryable` returning JS numbers can never catch this class of bug.

- **HIGH** (`read-stored.ts`, the `PARCEL_SELECTED` guard + module-init `throw`): the guard runs at **import time**, and this module is imported by the customer report route. So (a) a legitimate new `parcels:`-sourced page field takes down the report route on every request — *including with `MAXBLD_WEB_LIVE` false*, falsifying the "pinned off = zero blast radius" claim; and (b) the allowlist is hand-maintained while the comment claims it's derived: `PARCEL_SQL` already selects `zoning_zn_string`, `address_number`, `linear_name_full`, yet binding `parcels:zoning_zn_string` throws `MB-93: ... is not in the static parcels read` even though it plainly is. Fix: derive `PARCEL_SELECTED` from the same declaration the SQL is generated from (or assert in a unit test / `--check` generator, not at module init), and reconcile the alias set (`address` is a computed alias, not a column — the guard can't see that).

- **HIGH** (`read-stored.ts:readStoredPage`, 4 sequential `await db.query` calls; `ROWS_SQL` has no `LIMIT`): the customer lookup hot path went from *zero* DB round trips to four sequential ones per request, with no transaction, no statement timeout, and no row cap. A single lot with a corrupted/duplicated backfill (`parcel_maxbld_scenarios` with 10 M rows for one `parcel_id`) materialises the whole set into memory inside the API process. Concurrency: a writer bumping the stamp between the stamp read and the rows read is fail-safe (mismatch → miss), but it costs an extra recompute each time. Fix: fold into one query with a `LATERAL`/CTE + `LIMIT`, set `statement_timeout`, and memoise the `TABLE_SQL` probe. Add the pool/HPA sizing note — this route is now the DB's biggest per-request consumer.

- **HIGH** (deploy/rollout, `read-stored.ts:readStoredPage(db, parcelId, current = CURRENT_SEED_SHAS)`): the seeds are a compiled-in constant, so a seed bump (`catalogue_sha` moves) invalidates **every row in the table at once**. The first search after that deploy is a miss for every lot simultaneously → every lot recomputes → thundering herd, no back-pressure, no staged rollout, no way to serve "previous-but-known-good". This is the classic watermark-drift failure mode. Fix: name the rollout in the plan (bulk pre-recompute before the flip, or a `previous` seed set with a grace window), and read the seeds from a settings row rather than a default argument — a test-shaped default argument is how production config drift gets invisible.
