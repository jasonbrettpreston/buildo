## Findings

- **[CRITICAL]** (≈L205, *"mkdir lock + atomic write"*): There is no stale-lock recovery. If the claiming process is killed (SIGKILL, OOM, Ctrl-C, laptop sleep then reboot) between `mkdir` and the unlock, the lock directory persists with no owner, no TTL, and no documented way out. Every subsequent claim on that host fails until a human `rmdir`s it. There is no `--break-lock`, no lock-mtime staleness check, and no test that kills a writer mid-write. Why it matters: this is the one failure mode guaranteed to happen (GD-1 already showed the module is fragile at the fs layer), and its blast radius is "all parallel lanes stop, silently". Fix: lock is a directory containing `{pid, host, started_at}`; a lock older than N minutes or whose pid is dead on the same host is reclaimable and the reclaim is logged; add a `--break-lock --force` CLI verb; add a red test that forks a child, kills it inside the critical section, and asserts the next claim succeeds and says it broke a stale lock. Also: fsync the registry file **and** its parent directory after rename, or a crash can leave a zero-byte registry.

- **[CRITICAL]** (≈L204, test list: *"claim then overlap refused naming the holder; release; expired claim ignored; check and owner answer; symlinked path resolves to the same claim; same JSON shape; registry path by env"*): Not one of these six tests requires two processes. The module is a mutual-exclusion primitive; its entire value proposition is unproven by single-threaded unit tests. "Overlap refused" can pass trivially with a pure in-memory fs mock while the real lock is a no-op. Fix: add an integration test that spawns N=8 child processes claiming the same path in the same tick and asserts exactly one exits 0 and seven exit nonzero naming the winner; add a second where two children claim enclosing paths simultaneously. Without this, TS-1 (missing red tests) is not actually closed — it's restated in a nicer font.
