Written literally, the accessor on typeahead rows is `undefined` → "no direction" → the "any row has no direction → unchanged" branch fires on **every** typeahead result, so the guard is a silent no-op on exactly the `exact empty → typeahead` path the case table budgets a test for ("typeahead narrowing"). If the third lot is in fact the E lot with the suffix missing from `linear_name_full`, the user is handed the wrong lot with no confirmation — the exact defect class this task exists to fix, inverted. Same problem when a `multi_parcel` map case narrows to a single row and becomes `unique` (user never sees the map). Fix: carry null-direction rows through the narrowing as unclassifiable members (so ≥2 rows → `classifyRows`, map preserved), or bail to "unchanged" whenever the pre-guard set had >1 row and any row lacks a direction. Verify first: `SELECT address_number, count(*), count(*) FILTER (WHERE linear_name_full ~* '(N|S|E|W|NORTH|SOUTH|EAST|WEST)$') FROM parcels GROUP BY 1 HAVING count(*) > 1` — if mixed-direction groups are common, this is not a corner case.
