- **[HIGH]** (semi-question.tsx ~55-58, `continueToReport`): The Continue path caches and navigates on **any 200**, not just on a produced report. `fetchParcelLookup` only throws on non-2xx/envelope/schema errors; a `202`-ish outcome — `not_produced` (`page === null`), a `multi_parcel` lot map, candidates, or a dangling id — returns 200 with a payload that is not a report. The code does `setQueryData(...)` → `redirectedRef.current = true` → `router.replace(route)` unconditionally. Result: the user is pushed into the report screen with a non-report payload in the report's cache key. The lot isn't *counted* (the server's `not_produced` branch holds), so this is a robustness/UX bug rather than a double-charge, but it's exactly the "navigate after a non-successful call" case the lens asks about. **Fix:** inspect the result before writing/navigating (e.g. `if (!result.page) { setSubmitError(new Error('report not produced')); return; }` / branch on the lot-map kind), and route to the map/candidates state instead.

- **[HIGH]** (semi-question.tsx ~78 `push`, ~56 fetch): Nothing in `continueToReport` (or in the wiring) checks that `selected !== null`. The answer is never sent to the server (O-12: the pipeline never reads the override), so `semi: 'answered'` is a claim the client makes on **Continue alone**. If the surface renderer can ever emit `push` without a prior `select` — a state-machine bug, a deep link, a future descriptor change — the lot is counted with no answer, violating "counted after the answer." Verify `buildSemiQuestionSituation` only offers `push` when `selected` is set; regardless, add a cheap `if (!selected) return;` guard at the top of `continueToReport`. This is the one place where the invariant is actually enforceable, and it isn't enforced.
