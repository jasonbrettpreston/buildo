### 1. False candidates: short street names + exact house number is an unguarded collision factory
- **[HIGH]** (`src/lib/admin/parcel-lookup.ts:297`): `levenshtein(normalize_address(street_name_normalized), normalize_address($2)) <= threshold` with the house number held **exact** and no length/prefix guard. `enrich_heritage_address_levenshtein_threshold` is tuned for the permit pipeline, which compares a *whole normalized address* (~20+ chars); here the operand is a bare street token (~5–10 chars). Levenshtein distance is absolute, not relative, so the same threshold is roughly twice as permissive in relative terms on this operand.
  Concrete failure: threshold 3 → `MAIN`/`ELM` distance 3, `OAK`/`OAKS` distance 1, `PINE`/`PINEHURST` distance 4. Query "1 Oak Road" and you will be offered 1 Elm Road, 1 Oaks Road, 1 Pine Road — **same house number, wrong lot, one click away in the candidates list**. The `ORDER BY` puts the best first but does not remove the wrong ones, and there is no confidence floor (`near.length > 0` at :302 accepts whatever survives).
  Why it matters: this is the exact failure the lens calls out. A wrong lot in the cost tool means a wrong report for a real address.
  Fix: make the bar relative and structural — `levenshtein(...) <= LEAST(threshold, GREATEST(1, ceil(length(normalize_address($2)) / 4.0)))`, plus a hard requirement that the first 1–2 characters match (or `similarity()` via `pg_trgm` above ~0.5). Also consider `levenshtein_less_equal(...)` so rows past the threshold exit early.
- **[MEDIUM]** (`:297`): suffix/plural/directional differences are *not* mis-typings. `OAK ST` vs `OAK AVE` after `normalize_address` is a small distance and will be offered as a candidate. Different street type, same number = different lot. Fix: compare the street *type* separately (equal or excluded), and treat a suffix-only difference as a non-match unless the bare name matches exactly.
- **[MEDIUM]** (`:293`–`:299`): no jurisdiction/suburb filter. If `parcels` spans more than one locality (or has duplicated street names across suburbs), the same number+similar name in a different suburb is a wrong candidate. Fix: constrain by the parcel table's locality/state columns, or document that `parcels` is single-jurisdiction and assert it.

### 2. `truncated` is silently dropped on the fuzzy path
- **[HIGH]** (`:303`): the early `return` sets `{ match, candidates, resolution, lotMap }` — **no `truncated`**. Every other branch is explicit about it (the route's direct-id literal at `route.ts:~99` sets `truncated: false`). So when the matcher hits `LIMIT 10` (`:299`), the response can never say "there were more". Two consequences: (a) the user gets a silently clipped candidate list and no "refine your search" affordance; (b) the response shape diverges from the other `text_candidates` producer — if the client zod-parses the envelope with `truncated` required, this is a parse failure rather than a degraded UX.
  Fix: `truncated: near.length >= 10` (and verify how the typeahead branch computes it so the semantics match exactly).

### 3. No error isolation: a matcher failure 500s the *common* path
- **[HIGH]** (`:293`–`:301`): the new read is unguarded, and it introduces three new runtime dependencies on the consumer connection — `levenshtein()` (needs `fuzzystrmatch` installed in a schema on the search_path), `normalize_address()` (migration 170 — claimed to exist, but the diff adds **no migration**, only a regenerated ledger JSON), and the `logic_variables` table. If any of those is absent, this throws for **every search miss**, which is the ordinary case, not an edge case. Previously a miss was a clean `no_match`.
  Fix: verify in CI against a real DB that the extension + function + table exist on the *consumer* connection (the permit pipeline may well be a different database); wrap the read in try/catch and degrade to `no_match` with a logged warning, so a search-miss never becomes a 500.
- **[LOW]** (`:298`): a missing/renamed variable yields `NULL` → no rows → feature silently off with no telemetry. The comment rationalises this ("no literal fallback"), but nobody will notice the feature is dead. Log once per process when the variable is absent.

### 4. Threshold comparison is untyped and unguarded against multi-row
- **[HIGH]** (`:298`): `levenshtein(...) <= (SELECT variable_value FROM logic_variables ...)`. `variable_value` on a generic key/value table is usually `text` (or `jsonb`). `integer <= text` has no operator in Postgres; you either get a plan-time `operator does not exist: integer <= text`, or you're relying on a cast that only exists in assignment context. Nothing in this diff proves the column type, and **the tests cannot catch it** because `dbQuery` is fully mocked (see §7). Fix: `<= (SELECT variable_value::int FROM ...)`, and assert the type in a migration/integration test.
- **[MEDIUM]** (`:298`): the scalar subquery assumes `variable_key` is unique. Without a unique index, a duplicated key raises `more than one row returned by a subquery`. Fix: `LIMIT 1` with a deterministic `ORDER BY`, or rely on a documented unique constraint and say so.
- **[NIT]** (`:297`, `:299`): `normalize_address($2)` is a constant recomputed per row, and `levenshtein(...)` is computed twice per row (WHERE + ORDER BY). Hoist `normalize_address($2)` into a CTE/`CROSS JOIN` and/or sort by the selected expression. On the miss path it's tolerable; combined with §5 it isn't free.

### 5. Unbounded scan on an unauthenticated route
- **[MEDIUM]** (`:296`–`:297`): the exact path is indexed on `(addr_num_normalized, street_name_normalized)`; the fuzzy condition is **not sargable**, so for a common house number (`1`, `2`, `100`) the planner reads *every* parcel with that number and runs `levenshtein` on each. `q` is capped at 120 chars, so an attacker can send `?q=1+<117 chars>` repeatedly and force a wide scan + per-row function calls per request. The commit message's "hot path is unchanged" is true for hits and false for misses under load. Fix: prefilter by street prefix (`street_name_normalized LIKE left($2,1) || '%'`) or a trigram index, and confirm the route is rate-limited.

The exact-query evidence suggests it is bare, but that's inference. Add a comment-backed assertion (or an integration test) that pins the column's shape; otherwise a future normalizer change silently breaks the matcher's calibration.
