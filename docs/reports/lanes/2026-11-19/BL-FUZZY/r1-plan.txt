## Findings on the plan

- **[CRITICAL]** (plan step 2, the SQL literal): `levenshtein(...) <= (SELECT variable_value FROM logic_variables WHERE variable_key = '...')`. `logic_variables.variable_value` is not shown to be `integer`; the seeds are JSON (`scripts/seeds/logic_variables.json:6656`), so the column is almost certainly `jsonb` or `text`. `integer <= jsonb/text` has no operator; the statement either raises `operator does not exist` on every no_match, or (if `text`) does a **lexicographic** comparison — `"10" <= "2"` is true — silently inverting the threshold. The plan's "Missing variable = NULL = no rows" reasoning only holds for a numeric comparison. **Fix:** verify the column type (`information_schema.columns`), then read the value once in JS, coerce with `Number(...)`, validate `Number.isInteger` and `> 0`, and pass as `$3::int`. Do not put the subquery in the hot SQL.

- **[CRITICAL]** (plan step 2 + "Module home" paragraph): AC#1 says "no second matcher"; the plan says "no second matcher, no new home needed" and then **writes the matcher SQL a second time** inside `src/lib/admin/parcel-lookup.ts`. `scripts/lib/compute/enrich-heritage.js:121` contains that SQL as a JS string; copying the text is by definition a second home and the two copies will drift at the first threshold/normalization change. The "module is the DB function" argument is false — there is no named DB function today, only SQL text plus `normalize_address()` plus a config row. **Fix:** add a migration defining `find_fuzzy_address_candidates(p_num text, p_street text, p_limit int) RETURNS SETOF …`, have `enrich-heritage.js` and `parcel-lookup.ts` both call it. That is the only way AC#1 is literally satisfiable.

- **[CRITICAL]** (plan step 2, `ORDER BY ...`): the plan leaves the ordering as a literal ellipsis. `LIMIT 10` with **no `ORDER BY`** is non-deterministic: the candidate set the user sees for the same query changes across plan/scan order, and the test asserting "text_candidates" with row contents will be flaky. **Fix:** specify `ORDER BY levenshtein(normalize_address(street_name_normalized), normalize_address($2)), street_name_normalized, addr_num_normalized, parcel_id` (add id as the final tie-break) before implementation.

- **[HIGH]** (plan step 2, `$2`): the plan never defines what `$2` is. The pipeline matcher compares `normalize_address(parcel_address)` to `normalize_address(point_address)` — **full addresses**. The search SQL compares `normalize_address(street_name_normalized)` to `normalize_address($2)` — presumably a street-only token. Two problems: (a) if `$2` is the raw user input ("41 Derwin Road"), the distance to "DERWIN" is ~6 and nothing ever matches; (b) the seed threshold 2 was tuned for full-address comparison, not 6–12-character street names, so transferring it is unvalidated. **Fix:** state `$2` = the street token from `parseFreeTextAddress`, and re-derive the threshold against street-name-only distances with real data (see verification queries).

- **[HIGH]** (plan step 2 vs Grounding §"the web's TS mirror"): the plan routes the query through `parseFreeTextAddress`/`address.ts` first, then normalizes **again** with SQL `normalize_address()`. Two different normalizers ("mirror of `scripts/lib/address-normalizers.js`" — a mirror is not the same code) sit on the two sides of the Levenshtein. Any drift (abbreviation table, punctuation, suffix order) inflates distance and silently kills matches, or makes the exact probe and the fuzzy probe disagree. **Fix:** pass the *raw* parsed street token to SQL and normalize only in SQL, or prove the TS mirror byte-identical to `normalize_address` with a table-driven test.

- **[HIGH]** (plan step 2, "Uses idx_parcels_address (num first)"): the selectivity claim is wrong in spirit. `addr_num_normalized = '41'` matches house number 41 on **every street in Toronto** — hundreds to low thousands of rows. The index gives you that scan; it gives you *nothing* for the `levenshtein` filter, which is evaluated row-by-row on every one of them, on the **no_match hot path** of every search. A user hammering mistyped addresses is a cheap CPU amplification. **Fix:** add a cheap prefilter that is indexable — `street_name_normalized % $2` with `pg_trgm` + GIN, or `soundex`/`metaphone` equality, or at minimum first-letter equality (`left(street_name_normalized,1) = left(...,1)`) — before the `levenshtein` predicate. Benchmark before and after with a realistic street name.

- **[HIGH]** (plan step 2, `SELECT parcel_id, address`): "Returns candidates in the existing shape" is asserted but the SELECT list is only two columns. The existing candidate shape (the unlinked probe / the candidates page renderer) almost certainly carries more (ward, lot, address components, whatever B.1 renders). Returning a narrower row will produce `undefined` in the UI or a type error, and AC#3 says the copy is unchanged — so nothing on the page will be adapted to hide the gap. **Fix:** copy the exact column list and row-mapper from the existing unlinked probe; add a test that the fuzzy candidate object is `deepEqual`-shaped to an existing candidate.

- **[HIGH]** (plan step 2, `addr_num_normalized = $1`): the fix only rescues **street-name** typos. "14 Derwin Road" (wrong house number) still `no_match`. The task title is "mis-typed address", the acceptance criterion names a street typo, but the operator's words (RR-0277) are general. If the house number is exact-matched, this is a silent scope narrowing that will generate the next operator ticket. **Fix:** either state the boundary explicitly in the plan and in a dated note, or drop the number equality and let the street match drive candidate resolution (with the number shown to the user so they can self-correct).

- **[HIGH]** (plan step 2, config variable): reusing `enrich_heritage_address_levenshtein_threshold` couples search sensitivity to heritage-enrichment tuning. Someone fixing a heritage false positive by lowering the threshold silently changes the customer-facing search candidates. It is also a hidden second source of truth (the search now depends on a pipeline seed row existing in every environment). **Fix:** introduce a `search_address_fuzzy_threshold` variable, or document the coupling as an explicit, reviewed decision — and note the tension with AC#3 "No new field" (a config row is arguably not a *field*, but say so out loud).

- **[HIGH]** (plan step 2, error handling): the plan does not say whether the new probe is wrapped in `try/catch`. A DB error (missing `fuzzystrmatch` in a test/CI environment, bad config cast, missing function after a heritage migration rollback) will propagate out of `resolveAddress` and turn every legitimate `no_match` into a 500. **Fix:** wrap the probe, log at WARN with the query and parsed inputs, return zero rows. The search must degrade to today's behaviour, never worse.

- **[HIGH]** (plan step 2, "Missing variable = NULL = no rows (no literal fallback)"): silent disable with no observability. If the seed row is absent in staging/prod, fuzzy matching is off and nobody knows; the routing test (if it seeds the variable) still passes. This violates the project's own "observability" principle. **Fix:** emit a counter/log line when the variable is absent or non-numeric, and assert presence in the test setup.

- **[HIGH]** (AC#3 not covered by the plan): the plan has three steps, none of which regenerate the parity lock and goldens "by the repo scripts". If the candidates route now fires for a previously-`no_match` address, any golden keyed on that address changes. **Fix:** add step 4 — run the repo's parity/golden regeneration scripts and commit the diff; name the scripts.

- **[HIGH]** (plan step 1 test strategy): `search-routing.logic.test.ts` is a *logic* test — task-318's report says "no routing code changed" and red was proven by mutating `classifyRows`. The new behaviour lives in `parcel-lookup.ts` and needs a database. The plan does not say how the test reaches the SQL: pg-mem (which will not have `fuzzystrmatch` or `normalize_address`), a container, a seeded fixture DB? Without this, step 1 is not implementable and the "red first" claim is unprovable. **Fix:** name the test harness and where the extension/function/seed-variable come from; if pg-mem, the cheap-prefilter suggestion above becomes mandatory because pg-mem likely can't run `levenshtein` at all.

- **[HIGH]** (plan step 2, `$2` length): user input is unbounded. fuzzystrmatch's Levenshtein variants truncate/limit around 255 bytes and are O(n·m); a 10 KB pasted string on the no_match path is a cheap CPU burn and can return silently wrong distances on truncated input. **Fix:** reject/truncate `$2` to a documented maximum (e.g. 120 chars) before the query, and return `no_match` for over-long input.

- **[HIGH]** (Grounding §): the operator's words are "the **permit pipeline** - address spec". The plan grounds the reused matcher in **Spec 61 heritage properties**, after arguing the permit/60 link_coa tiers are equality-only. The argument is plausible, but it means the thing being reused is not what the operator named. Per RR-0190 (orchestrator recommendations must cite or be marked UNVERIFIED), this interpretation must not be presented as settled. **Fix:** mark the heritage-matcher choice UNVERIFIED in the plan, and state in one line why the permit address spec cannot resolve DERWIN/DERWYN — or raise it to the operator.

- **[MEDIUM]** (plan step 2, `normalize_address()` dependency): `normalize_address()` is defined in `migrations/170_create_heritage_tables.sql:21`. Using it from the search path creates an undeclared cross-module dependency: rolling back or renaming a heritage migration breaks search. Also verify `provolatile = 'i'` — if it is `STABLE`/`VOLATILE` it cannot be used in any functional index and cannot be constant-folded, which affects your perf story. **Fix:** add the function's volatility and ownership to the plan's assumptions; if it is not IMMUTABLE, make it so in the same migration that defines the shared matcher.

- **[MEDIUM]** (plan step 1, boundary test): "a nonsense street gets no rows" is not a threshold boundary — nonsense is distance ≫ 2. Test the actual boundary: a street at distance exactly 2 matches, distance 3 does not. Otherwise the test passes even if the threshold is ignored entirely (e.g., if the predicate is dropped and any row with number 41 is returned).

- **[MEDIUM]** (plan step 2, semantics): with `LIMIT 10`, a fuzzy hit on **one** parcel still sets `resolution = text_candidates`. The user is sent to "choose your lot" for a single near-miss. - **[MEDIUM]** (plan step 2, ambiguity of the rescue): a fuzzy hit can also mean the **exact matcher is broken** (abbreviation/suffix normalisation bug), not that the user typo'd.
