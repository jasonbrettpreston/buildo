## 1. What LOAD.1 is, at its smallest
When a user picks a lot (GET /api/parcels/lookup?parcelId=...), the route first asks W for a stored page (route.ts:134). LOAD.1 adds ONE step after that: if W answered "miss" and the session is allowed (the gate, section 3), the route computes the lot's report numbers in memory by calling the same pure core the pipeline step uses (materializeRows, L3CORE:651, exported :731), projects the computed rows through the shared projection (projectStoredPage, src/lib/report-projection/project.ts:188) with the lot stamp from the same batch row, applies the SAME miss rule W applies (`pageForVerdict`, report-page.ts:37), and hands the result to the existing mobilePageView (route.ts:135). The chain, once: batch row -> materializeRows -> StoredRow mapping -> projectStoredPage -> pageForVerdict -> mobilePageView. The freshness verdict is derived from the rows and stamp passed in (project.ts:172-184), not from the database, so a freshly computed lot is `current` (its rows carry the stamp's table version and the seed shas CURRENT_SEED_SHAS twins; the page is not turned into a miss by `not_stored`; test C9). No write, no record, no table, no new response key.

Call site as it is now (src/app/api/parcels/lookup/route.ts):
- :134 `const pageResponse = await readCustomerPageResponse(parcelRef);` the one slot. LOAD.1 changes this one expression to "stored page, else computed page".
- :135 `const page = pageResponse === null ? null : mobilePageView(pageResponse);` unchanged.
- :137 readLotForm (semi) unchanged. :153 strict body parse runs before the meter, unchanged.
- :163-:166 the meter branches in order: not_evaluated (legacy parcel payload has no evaluated option), semi_pending (unsure lot and semi != answered), not_produced (`body.page === null`, :165), else openReport (:166-:168). Unchanged: a computed page is a produced page, so it reaches openReport exactly as a stored one does.
- :199-:201 the catch: any throw is internalError (500), before the meter.

What is computed: all building-type rows of the lot as the step computes them (325 rows, six card types plus the garden-suite split; storage-ondemand REPORT.md:35-37). What is returned in `page`: the same ReportPageView the app already renders (types.ts ReportPageViewSchema), built by MF-57's core from {page, values, hidden, not_evaluated}. The admin lineage the projection also returns is dropped. The response contract does not change (page stays nullable), so mobile files do not change.

How W and LOAD.1 fit (task text: "no read first"): that sentence predates W. Today W is read first, and the BL-W plan says "W's null is the signal" (BL-W/PLAN.md:39). Measured correction: W's null is NOT one signal. It is returned for four causes: switch off (report-page.ts:54), no such parcel (read-stored.ts:49), no stored record (report-page.ts:44, `not_stored`), stale record (:42, `out_of_date`). Only the last two mean "compute". So the compute function checks the same switch itself as its first statement (MAXBLD_WEB_LIVE, maxbld-web.ts:19, literal false) and answers null when off. W stays untouched except that `pageForVerdict` is exported so the compute path applies the SAME current/gated/miss rule (report-page.ts:37, one place, plan D2). A re-open recomputes (no record is written), as the ruling says: ST.P1 (task-265, push 12) adds the write and read-before-compute (decision-79 text, task-325 description item 4).

## 7. Rollback per failure mode
- Before any gate admits a session: nothing runs (the literal switch is false, maxbld-web.ts:19); reverting the one commit removes dead code.
- Image-load failure (core does not load): the lazy import throws inside the route's try, a 500 for a gated session only, nothing metered; roll back by setting the session gate to false (or reverting the one route expression); W's stored read is untouched.
- Event-loop block: gate off as above; no data is written, so there is nothing to clean.
- Wrong or empty page: the page is never persisted; revert; the next open recomputes.
