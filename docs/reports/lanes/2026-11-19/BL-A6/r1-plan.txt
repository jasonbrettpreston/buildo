## CRITICAL

- **[CRITICAL]** (§STEP B (3), "Null cases"/fallback paragraph; §Operator list item 3): The plan *knows* the reset date is wrong for a daily window and ships it anyway. Verbatim: "resetsOn is a UTC instant; the function writes the UTC calendar date, so a period end between 19:00 and 24:00 Toronto time would show one day later than the Toronto calendar date." With EST that window is 00:00–05:00 UTC daily, i.e. *every* user whose Stripe billing anchor lands in that 5-hour band, permanently, on a date the customer will compare to their card statement. The task's *only* new rendered value is this date; "UNVERIFIED how often" is not an answer when the fix is deterministic and free. DST is never mentioned at all (the window is 4 h in EDT, 5 h in EST — so even a hand-rolled offset is wrong half the year). **Fix:** format in `America/Toronto` explicitly (Intl with an explicit timeZone, or a static UTC-offset routine with a DST boundary table) and add the four DST/EST boundary cases to `formatResetDate`'s test set. Do not defer this to an operator question — the operator is not going to prefer a wrong date.

- **[CRITICAL]** (§STEP B (3) fallback paragraph, citing `index.ts:542-548`): The claim "It cannot show a wrong date by itself" is false for the exact mechanism described. `reportPeriod` "stepped in whole months from current_period_end" is month arithmetic; a period end on the 29th/30th/31st overflows when stepped across a short month (31 Jan + 1 month = 3 Mar in naïve `Date` arithmetic), and stepping is unbounded when `current_period_end` is stale/superseded (a lapsed subscription whose row was never updated will be stepped forward month by month to "now"). The plan's own test list contains "a date near a month boundary" — but that test targets `formatResetDate`, which "does no date arithmetic", so it tests the wrong function and cannot catch this. **Fix:** verify `reportPeriod` clamps day-of-month (min(anchorDay, daysInMonth)) and caps iterations; add a test that a 31 Jan anchor renders 28 Feb, not 3 Mar. ## Verdict

The dependency story also contradicts itself: the plan declares no MF-47 coupling while depending on migration 322 for the allowance, with a silent-WARN failure mode and no alert. Fix the date (Toronto time, clamped month stepping), bind `reportsLimitReached` for the shown-rule, localise the absence rule, put one execution-level test in the gate, and verify the gate's static preconditions in this section — then this is a small, clean task.
