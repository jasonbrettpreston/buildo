## CHK.7 / `idLedgerErrors` — adversarial review

Scope: the new `idLedgerErrors` + `headingCounts` in `mcbylaws-queue-check.mjs` (new-file lines ≈249–325) and the two call sites in `gate.mjs` (≈264–268, 283).

---

- **[HIGH]** (queue-check ≈275–276, 303): The docstring promises "never an id in prose, a dated note", but nothing in `headingCounts` enforces that — it hands *every* non-fenced line to `headingBody` and counts whatever comes back. If `headingBody`'s contract is "line starts with `**PREFIX-nn`" (which is what the doc comment "`**MB-nn` lines" implies), then a queue edit that adds a dated-note line beginning with an existing id — e.g. `**MB-42** (2026-11-06) re-opened after the regression.` in the notes section — raises `cur[42]` from 1 (the existing `**MB-42 — Title**` heading) to 2, `c > 1`, and the commit is rejected with `FAIL:Q:id-duplicate:MB-42`. Same for an indented markdown lazy-continuation line (`  **MB-42** was fixed`) if `headingBody` allows leading whitespace. And for an id that is *new* to the file, a note line like `**MB-77** — deferred, see note 12` trips the `n >= next` branch instead → `id-unclaimed`. The comment and the code disagree; the comment is not the guarantee. Fix: match only the exact heading shape (column 0, `^\*\*(MB|MF)-(\d+) — .+\*\*$` or equivalent), or parse headings with the same canonical parser `queueCheck` uses and restrict to the heading region of the file.

- **[HIGH]** (≈300, 304): The `Next free id` regex is the one thing `headingCounts` was careful to avoid: it is *not* fence-aware and *not* anchored. `new RegExp('Next free id:\\s*\\*\\*MB-(\\d+)\\*\\*').exec(now)` takes the **first** match anywhere in the file. If the queue documents its own format in a fenced sample above the real line (`Next free id: **MB-1**`), every real new heading (say `**MB-120**`) is `< 1`? no — `120 >= 1` → `FAIL:Q:id-unclaimed:MB-120` on a perfectly correct commit. Invert the sample (`**MB-999**`) and real unclaimed ids silently pass. Same regex fails to match any of the normal formatting variants — `**Next free id:** **MB-120**`, `Next free ID:`, `Next free id` without bold, a wrapped value — and then `next === null` sets `undecided` for *every* introduced heading (≈304), so the whole commit dies on `cannot-decide` with no file named. Fix: iterate `now.split('\n')` with the same fence state as `headingCounts`, anchor `^\s*Next free id\s*:`, and tolerate bold on the label and optional leading zeros.

- **[HIGH]** (≈308, 315): Migration renames are a complete hole, and a rename performed as add+delete is a self-inflicted false positive. `added` filters `e.status === 'A'`, so `git mv migrations/0007_a.sql migrations/0042_b.sql` (status `R0xx`) introduces number 0042 with **no duplicate check and no row check** — a rename to a fresh number bypasses CHK.7 entirely. Conversely, when rename detection misses (rename-with-edits below the similarity threshold, or `diff.renames=false`), the same move shows as `D 0007_a.sql` + `A 0007_b.sql`; `0007_b.sql` is in `added`, and `held` looks at `tracked`, which still contains `0007_a.sql` → `p !== file` is true → `FAIL:Q:id-duplicate:mig-7:migrations/0007_b.sql` for a file that is just the old one moved. Same for a `C` (copy) status. Fix: build the check against the *post-commit* tree — `(HEAD ∪ {A,R-new,C-new}) \ {D,R-old}` — and run the number check on every new path that matches `MIGRATION`, regardless of status letter.

- **[HIGH]** (≈293, 298): `readAt(cwd, '', file)` is load-bearing and its semantics are asserted only in a comment ("Reads the index"). If empty-rev `readAt` resolves to `git show :path` you're fine. If it reads the working-tree file, the hook's verdict depends on **unstaged** content: stage a duplicate `**MB-42**` heading, then delete that line in the worktree without re-staging — `cur` is computed from the worktree, sees one copy, passes, and the commit lands with two. That's a trivial bypass of the entire feature. It also misjudges `git add -p` partial stages in both directions. Verify `git-util.mjs` before trusting this; if it *is* filesystem-backed, `headingCounts` must be fed `git show :path` / `git cat-file blob :path`.

- **[MEDIUM]** (≈316): The row-claim regex is far too permissive. `\bmigrations?\b[^\n]{0,60}?\b0*${n}\b` matches any line that says "migration(s)" within 60 chars of the bare number `n`, anywhere in either queue, fenced or not. Concrete: a queue line `- See migrations notes, §7.` makes an unclaimed `migrations/0007_x.sql` pass as "named by a row". `MB-88: adopt the migrations plan, phase 7` does the same. It also can't match a legitimate multi-line table row — `| MB-31 | migrations |` / `| | 0007_foo.sql |` — because `[^\n]` forbids crossing the newline, so a correctly-claimed migration fails `id-no-row`. Fix: require an actual reference shape (`migrations/0*N_`, or the id token on the same line as the file name) and parse out of fences.

- **[MEDIUM]** (≈305): "Claimed" is defined as `n < nextFree`, which means the `Next free id` bump must land in the *same staged diff* as the heading. The normal workflow passes (`MB-50` + bump to `MB-51` → 50 < 51). But splitting the bump into a follow-up commit — or staging the heading with `git add -p` and leaving the bump unstaged — gives `next = 50`, `n = 50`, `50 >= 50` → `id-unclaimed` on a legitimate id. The check encodes a same-commit invariant nobody wrote down. Fix: accept `n <= nextFree` when the diff also contains the bump, or read the ledger/next-free from `HEAD` as the *lower* bound and require the new id to be exactly the old next-free.

- **[MEDIUM]** (≈269–273): Fence tracking is `^\s*```` toggling on every line, which is fragile in the direction that silently *disables* the whole check. A 4-backtick fence wrapping a sample that itself contains ```` ``` ```` toggles twice early and leaves `fenced === true` for the rest of the file → every real heading after it is skipped → duplicate and unclaimed ids pass (false negative). `~~~` fences are never recognised, and a stray line that begins with ` ``` ` in prose flips the state permanently. Fix: track the opening fence run length and only close on a fence of ≥ that length; recognise `~~~`; reset at EOF.

- **[MEDIUM]** (≈275, 322–324): `headingBody` is used but never defined or imported in this diff — the only new import is `listTracked`. If it isn't already in this module's scope (i.e. `queueCheck` happened to use a different helper name), the `ReferenceError` is swallowed by the blanket `catch { return [CANNOT]; }` and every commit that stages a queue file fails with `cannot-decide` and zero diagnostics. The blanket catch also converts *any* future logic bug into a policy `FAIL` that blocks developers with no stack trace. Fix: confirm `headingBody` is in scope (and add a unit test that calls `idLedgerErrors` with a real queue fixture), and narrow the catch to the git/IO calls so programming errors surface.

- **[LOW]** (≈269, 275): `text.split('\n')` leaves a trailing `\r` on CRLF files. If `headingBody` uses an end-anchored pattern (`...\*\*\s*$`), a CRLF queue yields **zero** headings for both `was` and `cur` → nothing is ever introduced → all checks silently pass. Same class of bug on any file where an editor rewrote line endings. Fix: `split(/\r?\n/)`.

- **[LOW]** (≈292): The queue loop keys on `e.path === file` and `e.status !== 'D'`. This inherits whatever shape the `--name-status -z` parser produces. If a rename entry carries only the old path in `.path` (new path in a separate field), a renamed queue file is skipped entirely — same class as the migration rename hole. Also, the check only covers `ID_QUEUES` (two paths); if `FE_REGISTER` or a per-lane register also carries `MF-nn` headings, new duplicates there are unchecked. Fix: assert the `entries` shape in a test, and derive the path set from both sides of each rename.

- **[LOW]** (≈310, 315): `listTracked(cwd, '')` — if the empty rev resolves to `HEAD` rather than the index, two migrations with the same number staged *together* (`A 0008_a.sql`, `A 0008_b.sql`) are invisible to each other and both pass, while the `D`+`A` self-duplicate above becomes a false positive. The verdict flips entirely on that one function's semantics. Also `MIGRATION` is `^migrations/...`; if `listTracked` returns `./`-prefixed paths, `held` is always false and duplicate migrations pass silently. Fix: pin the semantics (and strip a leading `./`).

- **[NIT]** (≈305, 317): The `id-unclaimed` and `id-duplicate` messages don't print the current `Next free id` or the colliding path, so the operator has to go find out why. Include `next=<n>` and, for `held`, the other file.

- **[NIT]** (gate.mjs 265, 268, 283): The fast path now returns `idLines` (possibly `[CANNOT]`) where it used to return `[]`, so a doc-only commit can be blocked by queue-file formatting it never touched — assuming the queue is staged, which it is whenever a queue file is in the diff. On the slow path, `if (tracked === null) return ['FAIL:H:cannot-decide']` **drops** `idLines` entirely; the two paths disagree about whether ledger findings are reported. Hoist the `listTracked` guard or compute `idLines` after it.

---

**Verdict:** The idea is sound and the fence-skipping in `headingCounts` shows the author was thinking about the right failure mode, but the implementation's two load-bearing assumptions are unenforced: (1) that `headingBody` matches *only* a heading and never a note/prose/list-continuation line beginning with the bold id, and (2) that `readAt(cwd, '', …)` reads the index, not the working tree. Neither is tested in this diff, and both turn into either routine false passes on legitimate queue edits or a one-line bypass of the whole check. The migration half is qualitatively weaker than the queue half: it only sees `A` status, never `R`/`C`, will self-report a rename-with-edits as a duplicate of the old path if `listTracked` is HEAD-based, and its "named by a row" regex is loose enough that a stray `§7` in a docs line satisfies it. Add fixtures for the exact strings above (dated note, fenced sample, CRLF queue, rename-with-edits, multi-line table row) before wiring this into a pre-commit hook, because a hook that both misses real duplicates and blocks valid commits is worse than no hook.
