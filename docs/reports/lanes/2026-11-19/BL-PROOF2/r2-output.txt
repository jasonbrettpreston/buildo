## Findings

- **[CRITICAL]** (lines 67–68, `commandRow`): **PASS is the default for exit 0.** The only thing that converts a green command row into NOT BUILT is an opt-in `waits` string that the *check itself* must print. Nothing in `checkSpec` requires `waits` on any argv row, and nothing asserts the command did anything. Concretely: `chk3-nothing-new` and `chk5-mcstorage` both spawn `node scripts/analysis/policy-checks.mjs --all`. If that script exits 0 while implementing CHK.1 and CHK.2 only, both rows print PASS. Worse, the sentinel has a bootstrap problem — a not-yet-written CHK.3 check cannot print `WAITS CHK.3` because it doesn't exist, so the row that exists specifically to prove CHK.3 is *most* likely to be the one that silently passes. And because both rows share one command, a `policy-checks.mjs` that prints `WAITS CHK.3` but nothing for CHK.5 gives you NOT BUILT on chk3 and PASS on chk5, with CHK.5 possibly not existing at all. **Fix:** invert the polarity. Require positive proof of execution — every argv check must emit a machine-readable line (e.g. `CHECK RAN <id> checks=<n>`), and `commandRow` returns GAP, not PASS, when it is absent. Absence of a "not built" marker is not evidence of a run.

- **[HIGH]** (line 78, `suiteRow`): **PASS without evidence the listed suite files ran.** The green condition is `field('sha') === head && field('RESULT') === 'PASS'`. `row.suite.suite_files` appears only in the proof string (`covers: ...`, line 72) — it is never compared to the pass file. Any pass file from any suite run on the current HEAD turns this row green, including a run of an unrelated subset. That is exactly the lens failure: PASS with the check not having run. **Fix:** the pass file must carry the file list and per-file result; match it. Or store a stable hash of the sorted `suite_files` in both the JSON row and the pass file and compare.

- **[HIGH]** (line 76, `suiteRow`): **First-match regex over a pass file that can hold multiple runs.** `new RegExp('^sha:\\s*(\\S+)', 'm').exec(body)` and the same for `RESULT` return the *first* occurrence. If the station pass file is appended across runs (the natural thing for a log), a stale block whose sha happens to equal HEAD and whose `RESULT: PASS` sits first masks a later FAIL for the same sha — e.g. a re-run after a flake fix regressed. Green on stale evidence. **Fix:** parse the *last* run block, or reject files containing more than one `^sha:` line as ambiguous (GAP).

- **[HIGH]** (lines 66–67, `commandRow`, ordering): **The `waits` test runs only after the exit-code test.** A not-built check that honestly exits non-zero (a stub `process.exit(1)`, or a check that throws "not implemented") is reported **FAIL** — exit 1 — not NOT BUILT, exit 3. That's the mirror of the lens question and it matters operationally: exit 1 is "the tree is broken", exit 3 is "not built yet", and the caller (PROOF.S, task-268) will react differently. It also trains the JSON author to make unbuilt checks exit 0 so they're classified correctly — which pushes them straight into finding #1. **Fix:** evaluate `waits` against the output *before* branching on `res.status`, or accept either status for the sentinel path.

- **[MED]** (line 41, `checkSpec`): **`waits` is validated as a string and nothing else.** It is silently ignored when the row kind is `suite` or `notbuilt` (`suiteRow` never reads it; the notbuilt branch never reads it). An author who writes `{"suite": {...}, "waits": "WAITS X"}` gets PASS from a pass file, not the NOT BUILT they asked for, with no validation error. **Fix:** `if (r.waits !== undefined && r.argv === undefined) problems.push(...)`.

- **[MED]** (lines 34–47, `checkSpec`): **Unknown keys are never rejected, so a typo silently converts to PASS.** `"wait": "WAITS CHK.3"` (singular), `"Waits"`, or `"waits "` all pass validation untouched, and `commandRow`'s `row.waits` is `undefined` — the row can never be NOT BUILT, it's PASS-or-FAIL only. Fail-closed shape validation is the whole point of `checkSpec`; it currently fails open on the one field that governs the lens. **Fix:** whitelist keys per row kind (`id/proof/timeoutMs` + exactly one of `argv|waits`, `suite`, `notbuilt`) and push a problem for anything else.

- **[MED]** (lines 66–68 vs. the three golden rows): **The golden-capture rows have no minimum-count assertion.** `search-goldens` / `lotmap-goldens` / `semi-goldens` claim "10 states", "11 states", "8 states" in prose only. If `scripts/surfaces/*-golden-capture.ts` finds zero goldens (directory renamed, glob broken, `--check` short-circuits on an empty set), it exits 0 and the row prints PASS — a vacuous pass, which is the canonical "PASS without having run its check". Same for `surface-validate`. **Fix:** make the counts data, not prose (`"expect": {"comparisons": 10}`), require the check to print the count, and fail when it doesn't match.

- **[MED]** (line 92, `runSlice`): **Exit 0 is structurally unreachable for slice `S`,** so the tool's green signal is dead and callers will learn to ignore exit 3 — which is precisely how a fake PASS gets waved through later. Nine rows are hardcoded `notbuilt`, including `mobile-jest` with `blockedBy: []`. A row with no blocker can never be unblocked; it is permanently NOT BUILT *by authorial decision*, not by dependency, and the table renders it as "unblocked by `-`". That is a fourth state ("this tool does not cover it") being smuggled into the third ("blocked"). **Fix:** give it its own status and exit code (e.g. `UNCOVERED`, exit 4) or drop the row; and stop the tool promising `exit 0 every row PASS` in the header when no slice can reach it.

- **[MED]** (line 44, `checkSpec` — crash, not validation): **`"notbuilt": null` throws.** `kinds` counts `notbuilt` because `null !== undefined`, then `const b = r.notbuilt.blockedBy` throws `TypeError` on null. - **[LOW]** (line 19–20 / `realIo`, `head`): **A failed `git rev-parse HEAD` is swallowed.** `spawnSync(...).stdout.trim()` yields `''` on failure, not an error, and `suiteRow` then compares the pass file's sha against `''`. - **[LOW]** (`proof-slices.json`, `chk3-nothing-new` / `chk5-mcstorage`): **The same command is spawned twice** for two rows, at up to 120 s each, writing two evidence files from two independent runs. ## Verdict

The tool is honest about *blocked* work and dishonest about *absent* work. Every mechanism it has for distinguishing "the check ran and passed" from "the check isn't there" is opt-in, supplied by the check under suspicion: the `WAITS` sentinel for command rows, the bare `RESULT: PASS` + sha for the suite row, and exit-0 for everything else. That inverts the burden of proof in the one place you cannot afford to invert it — `chk3-nothing-new` passes unless someone edits a file that doesn't exist yet to say it doesn't exist. The suite row is independently broken in the same direction (`suite_files` is decorative), and the exit-code ordering actively rewards authors for making unbuilt checks exit 0. Fix the polarity (require positive proof of execution, default to GAP), bind the suite row to the files it names, and reject unknown/ignored keys in `checkSpec`, and the lens question becomes answerable. Until then, no row in this output is a claim you can rely on.
