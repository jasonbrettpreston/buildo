The test cannot detect a wrong base because it feeds in whatever base it then asserts. If the app ever passes the real `/parcel-tool` from `parcelSearchRoute`, every expected string here is wrong but still green. **Fix:** assert against the literal the production caller actually uses (import/derive it from the same constant), and drop the route-group segment unless it is genuinely part of the URL.

## Overall verdict

The test is well-intentioned and the DB-by-statement mock is a reasonable pattern, but it substantially overstates what it proves. The base path is circular and likely wrong (`(app)` is not a URL segment), the semi-redirect — the entire point of the "semi" cases — is verified only by a local reimplementation plus a substring scrape that would pass on a comment or a negated guard, and the real routing binding (`parcelSearchRoute`) is explicitly not exercised. Several assertions would stay green under genuine bugs: candidate `parcelId` is unchecked, `resolveLotMap` is fed a canned payload ignoring its arguments, the unlinked pin is never asserted, and the "two lots at one address" distinction is never probed. As a regression net for SRCH.ROUTE this is closer to documentation than verification; the highest-value fixes are to drive the real `needsSemiQuestion`/`parcelSearchRoute`, assert the base path the app actually uses, and tighten the param- and arg-level assertions.
