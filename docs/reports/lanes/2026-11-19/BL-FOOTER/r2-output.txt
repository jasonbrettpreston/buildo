# Adversarial review — BL-FOOTER (MF-91 / task-332)

### Static byte-identity (lens 3) — broken in three independent ways

- **[HIGH]** (footerNode.ts:47-62 vs the deleted `footerNode` at StaticBinding.tsx:173-180):
  **The static footer output is not byte-identical.** Three concrete divergences, all reachable with today's content files:
  1. **Empty links group.** The old builder *always* emitted the links `Group` (`node('Group', {key:`${s.id}-links`, className:L.links}, s.parts.filter(...))`) — a footer section with zero link parts rendered an empty `<div>`. The new builder emits the Group lazily (`if (links === null)`), so a link-less footer loses a DOM node.
  2. **Order.** The old code did two independent `filter`s — *all* links first (in one Group), *then* all legal texts. The new builder preserves part order and reopens a Group after every non-link part. Any static footer whose content orders `legal` before `link`, or interleaves them, now emits a different DOM order.
  3. **Roles that used to be dropped now render.** The old code rendered only `link` and `legal` and silently discarded everything else. The new builder throws for unknown roles — but `line` and `copyright` are *known* roles, and `STATIC_FOOTER` supplies both (`line: L.legal, copyright: L.legal`). So any static footer part carrying role `line` or `copyright` now prints text that did not exist on the page before.
  *Why it matters:* the lane's acceptance criterion is byte-identity; items 1 and 3 are silent content/layout edits to live pages. *Fix:* diff the emitted tree for every static footer content file before/after (`staticWebTree` JSON snapshot), and if `line`/`copyright` were ever present, either delete those parts or accept the change explicitly.

- **[HIGH]** (StaticBinding.tsx:176-180 + the untouched static content files):
  **Nothing in this diff makes the static footers use the same links, texts and order as the search and report footers.** The *builder* is shared; the *data* is not. Static footers still read `href`/`content` from their own content files, none of which this patch touches. If those files say `/support` rather than `/help`, or `© 2026 MaxBLD` rather than `© MaxBLD`, or link in a different order, lens item (1) fails while the code review looks clean. Grep every static footer part (`"role": "link"`, `"role": "legal"`) and diff the strings against `SEARCH_FOOTER` and `ReportFooter` before claiming the footer is "the same on all three pages".

### Required-prop / failure-mode regressions

- **[HIGH]** (ReportPage.tsx:401, StaticBinding.tsx:437, report-preview/page.tsx:50):
  **`footer` became a required prop on the shared `ReportPage` and only two call sites were updated.** Every other call site (tests, storybook, the `STATES` branch of the preview page if it renders `<ReportPage>`, any admin preview) either fails the build or — if it passes through JS / a spread / `as` — reaches `pickFooterText(undefined)`, which throws `TypeError: Cannot convert undefined or null to object` from `Object.hasOwn`, not the named FE-18 error the design claims. *Fix:* guard first — `if (!footer) throw new Error('ReportPage: no footer text')`.

- **[HIGH]** (StaticBinding.tsx:339 `footer?: FooterText` + :392 `footerOf2`):
  **`StaticReport.footer` is optional in the type but mandatory at runtime.** Any producer of `StaticReport` that omits it (the `/help` page's embedded sample, preview fixtures, tests) compiles cleanly and 500s on render. This is a type hole dressed as safety. *Fix:* make `footer` required when `sample` is present (discriminated union, or `footer: FooterText` on a `{sample: PageView}` variant), so the compiler enforces what `fail()` currently enforces at request time.

- **[HIGH]** (maxbld-landing.ts:147):
  **`pickFooterText(SEARCH_CONTENT)` throws eagerly inside `readLanding`, defeating that function's own degraded path.** `readLanding` is explicitly written to degrade (`const state = lines.length ? 'static' : 'degraded'`), and `picture`/`demo` are conditionally spread precisely so a missing piece is omitted. A renamed or dropped `footer.*` key in a *different surface's* content file now turns the marketing landing page into a 500 instead of a degraded render. *Fix:* compute the footer only when the sample is actually renderable, and omit the `ReportPage` node (as `picture` is omitted) when it is not.

### Silent skips (lens 4)

- **[MEDIUM]** (ReportPage.tsx:252-266 `ReportFooter`):
  **The report view's own `copyright` part is now silently discarded** — the old code rendered `one(s, 'copyright')`; the new code renders the caller's `footer.copyright` and never looks at the part. Worse, any *other* part in the report footer section (a `legal`, a second `line`, a renamed role) is ignored with no error, because the parts array is hand-built from `one(s,'sources')`/`one(s,'change')` only. This is exactly the "nothing skipped silently" rule the builder enforces for its own data and the report renderer does not. *Fix:* assert the report footer section contains only the roles you consume (throw otherwise), or keep `s.copyright` and treat the shared string as a fallback.

- **[MEDIUM]** (footerNode.ts:24-32 + SearchBinding.tsx:139 / StaticBinding.tsx:389-434):
  **FE-18 is enforced on one of three surfaces.** `renderFooter` in ReportPage throws on an unknown text key; `pickFooterText` throws on a missing key. But the search and static bindings resolve `{content: key}` through their own content maps, whose failure mode this diff does not change or show. A missing `footer.terms` will throw a named error on the report and can render blank/raw-key on the other two. Share the ref-resolution (or at least the throw) across the three renderers.

- **[MEDIUM]** (ReportPage.tsx:240-250 `renderFooter`):

**Verdict.** The architecture is right — one builder, three thin renders, refs only, roles closed with a throw — and that part is genuinely better than the two footers it replaces. But the change is not landed: the static surface is *not* byte-identical (lazy links group, part-order instead of links-first, and `line`/`copyright` parts that used to be dropped now rendering), the static content files were never updated so the "same links and texts on all three pages" claim rests entirely on the builder being shared rather than on the data matching, `ReportPage`'s new required prop turns every un-updated call site into a runtime TypeError, `StaticReport.footer?` is a compile-clean path to a 500, `readLanding` throws away its own degraded path over a string in another surface's content file, and the report renderer discards test ids and the view's own copyright part without a word — which is precisely the silent skip the module's own docblock forbids. Fix the byte-identity diffs and the failure modes first; the naming and layout-slot nits can wait.
