### C2.5 Alternatives and what a person or the data would see
1. Keep the 500 (the recommendation). Person: search error "Couldn’t reach the lot service" on the typed address, or "Could not load this report. Try again." on the report; up to four compute reruns first. Data: no row written, no meter. Costs: leaves two dated notes contradicting; P4 stays unbound by the build.
2. Route catches a compute error and returns a 200 with the closed not_evaluated:<reason> (P4 as written). Person: sees an evaluated-looking page with a reason; no meter charge (hasEvaluatedOption false -> meter not_evaluated, route.ts:181). Data: a systematic failure would read as "not evaluated" for every lot (hides an outage; the 500 is louder, and logged via internalError). Needs a new closed reason (none exists for "compute error"; doc-16:33 names "<reason>" without a value), a code change in a 1·B file, and the lifecycle `error` word in the same sentence is the 500 path, so P4 itself is internally ambiguous ("closed not_evaluated:<reason> (lifecycle `error`)").
3. Keep the 500 and ask the operator the LD-1 sentence inside LOAD.4 (front-end scope, RR-0233), and amend P4's failure clause or Spec 100:123 so only one text remains.
4. Amend P4 on the STN1 branch before it lands so the failed-compute clause reads as the route's 500 plus the lifecycle error frame (the half of P4 that is built), moving the closed-reason half to L.13. (A docs change; not built or proposed here beyond the listing.)
