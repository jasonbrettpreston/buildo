### C1.3 "Nothing reads as zero today": checked
True for the two omitted keys. But what keeps it true is a code reading, not a lock: no lock compares the ENTRY's ctx to the runner's. customer-report-compute.logic.test.ts C2 (:145-166) compares the computed page with W's projection of the same rows; C7 (:250-263) checks that the entry names the core's exports. The core's own tests (src/tests/steps/compute_m*/runtime-loader.logic.test.ts:120,160,203-221 and runner-plan.logic.test.ts:115) also call materializeRows with a hand-built `{ config, lookups }` (no run_at, no descriptor). So the core is locked only with the two-key shape: if materializeRows ever reads c.run_at or c.descriptor, those tests build the same hand-made ctx and would not see a zero while the runner passes four keys and the ENTRY two. That is core.10's "A hand-built ctx in a test can pass while the real run reads zeros", at the core's tests as well as at the ENTRY.

### C1.4 Is a parity check buildable? Does a mechanism already give the route the runner's ctx?
- Existing mechanism: none that returns rows to a caller. The ctx literal at index.js:3472 is inline in materializeRowsArm (not a function); `runMaterializePhase` (exported, index.js:7921) writes the rows (A/F/G targets) and returns matched/written, not rows; `dry_run` (index.js:3398, :3487 `if (dryRun) continue;`) "reads and computes, issues no DML" but discards the rows. `git grep "materializeRows("` over src and scripts: index.js:3472, report-compute.ts:96, and tests only. So "call through the runner's dispatch" needs a new export (a one-batch read-only entry or a ctx builder) in scripts/lib/step/index.js, a RE-FREEZE-class file (124a R-EW (iii): "Compute-side only: no change to `scripts/lib/step/**`, so no RE-FREEZE and no `lib_fingerprint` move" is the reason R-EW avoided it). Which gates a new export trips: UNVERIFIED.
- A parity check is buildable: the repo already drives the real arm with a spy compute (src/tests/materialize-rows.logic.test.ts:114-143, a materializeRows spy reading `ctx.lookups`, runMaterializePhase driven with stubbed writes; step-library.logic.test.ts:6966-6990 "a spy shapeRecord receives {geojson, config, run_at}" is the same method for another phase). A test of that shape can capture the key set the runner passes (config, run_at, descriptor, lookups) and compare it to the key set the ENTRY passes (spy on the core's materializeRows through the lazy import). It proves key-set equality and the lookup columns; it does not prove value equality (run_at); and today it fails by design on run_at and descriptor unless the ENTRY adds them or the test lists them as declared-unused. A test that lists run_at and descriptor as allowed omissions is a closed exception list (memory rule: no exception paths in step conversion; the step is still pending conversion).
- Alternatives and which rule each satisfies:

### C1.5 What a person or the data would experience
Nothing visible differs between the answers today: the compute is dark (MAXBLD_WEB_LIVE false, maxbld-web.ts:19), and when it runs the page is the same bytes whether or not run_at and descriptor are passed, because neither is read. The difference is future risk: if the core ever reads run_at or descriptor, the route would compute with undefined (a TypeError or a silently different value per use), so the customer page could 500 or differ from the record the step would store (ST.P1), and the 25-lot parity tests would not show it because they build the same two-key ctx.
