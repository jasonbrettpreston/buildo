## Appendix §A26 — Compute purity: Rule 2 as closed-answer gate codes (R-BZ, R-CA) (2026-10-11)

Spec 124 Rule 2 says compute is only compute; the 2026-10-10 inventory found SQL, ledger reads, DDL, transactions, DB clocks and verdict decisions inside compute modules, together with undeclared relations and swallowed errors. The gate was green throughout, because gate E ([`compute-literals.mjs`](scripts/analysis/gates/compute-literals.mjs), fast invariant #32) banned only *literals* and had no vocabulary for any of it. This appendix turns that finding into standing, closed-answer codes; it does not re-inventory. Per Spec 124a R-T, a cross-cutting promise is declared data, generated and gated, and is never re-discovered by a manually commissioned inventory — this gate is what makes the next inventory unnecessary. The ruling ids are R-BZ (purity as a closed answer, incl. witness attribution) and R-CA (the compute-layer corrections to reality); the codes judge the parse tree and the AST, never keyword-matched prose.

### Answer set

Every site answers exactly one token: `PASS | FAIL:<CODE>:<file>:<line>`. `<CODE>` is a row's rule id below; `<file>:<line>` is the judged site (for SQL codes, the call line — e.g. the `pool.query(` line — with the literal resolved from that line or the two lines that follow). Site counts are never written in a spec: counts are generated by `compute-purity.mjs --list` and `compute-literals --list`.

### Ledger key and locks

- **Key grammar:** SQL codes — `<rule>@<fp>#<ordinal>`, where `<fp>` is the literal's libpg-query fingerprint and the ordinal counts that `<rule>@<fp>` in source order within the step. A literal that does not fingerprint uses `<rule>@unparsed:<line text>#<ordinal>`. JS codes keep the existing gate-E key `<rule>@<trimmed line text>`.
- **Unparsed SQL (not a code, a closed set):** literals that do not parse go into a closed set generated by the gate's own `sql-lineage.mjs` render (with a retry), never hand-listed — the `CLOSED_INTERPOLATED_SET` precedent. Unparsed sites get the lexical classes; a new unparsed literal is RED, and a listed literal that now parses or is gone is RED (orphan). This adds no ledger rows. Every row carries `why`.
- **Collision lock (C2):** two violations sharing one key with one ledger row is RED. `scripts/analysis/gates/ledger.mjs` `matchLedger` consumes each key once, so one row covers one violation only — it no longer lets one row cover N same-key violations.
- **Expiry tripwire (C3):** scoped to rows whose `closing_brief` is exactly a `programme-items.json` id (the R-BZ purity rows). Such a row is RED when that item's `status` is `BUILT` or `SUPERSEDED`, or when the id is missing (reason `item_missing`); green while `NOT_STARTED`/`PARTIAL`. It is keyed to declared programme data (Spec 124a R-T), never to `lib_fingerprint`. Rows that close on the existing chain_sources-completion text are untouched. R-BA's closing clause and its hard stop are amended for the purity codes only, on a closed step list (Q6(A)); any code on any other post-2026-09-26 or future conversion stays hard stop, and no row is filed against the Q2 WF3 site.

### Witness attribution (A3, amends R-BG)

The caller (`step-validate`) builds `runnerFingerprints` from the derived runner closure and passes it to `witness.mjs`, which stays pure ESM with no fs. Interpolated runner templates become a closed set of trace fingerprints, each with a runner `file:line` cite. `excluded[]` is judged at **table level** against the declared reads/writes, and the answer token is the existing grammar `FAIL:WITNESS:<slug>:a:<table>.*`. There is **no fallback** to the old blanket exemption: an empty `runnerFingerprints`, or a trace statement with no fingerprint, is RED. These FAILs are **report-only** until the #44 flip at `max(S1 landing, P1-C9)`; `witness.mjs`'s `hardStop` stays P1-C9's to change, so this adds no second owner of that rule and no edit to Spec 122 §6.6.1.

### Proof of no runtime change

The landing changes gates, ledger rows and specs only — no runtime code. `git diff --stat <main> -- scripts/lib scripts/*.js scripts/quality/*.js scripts/steps/_schema/step.schema.json` is empty; `computeLibFingerprint()` is equal before and after; `step-validate --all --fast` differs only in the #32 lines (any `## Validation scorecard (generated)` block that moves is regenerated in the same commit).

## Appendix §A27 — Conversion traps checklist (H6 + cross-step audit, 2026-10-16)

Every new step and every conversion walks this list before its first capture. Each line names the rule that governs it and what enforces it. "Live only" means only a real run against the dev DB catches it, so run the step once before capturing.

1. **Net-new steps stay `pending`** (Spec 124 R-CS). `cutover.mjs` also needs a pretty-printed census row and a `registers_at` naming commit ③ or ⑨ (`convertedAtFor`).
2. **RLS:** every write target on an RLS-enabled table declares `rls_bypass_or_policy`, and a new table's migration enables RLS (Spec 124 R-CT; Spec 114 §2).
3. **Bind limit:** rows × bound columns per upsert ≤ 65,535 (Spec 124 R-CU). Live only for fan-out targets.
4. **Invalidators:** an `outputs.invalidates` row is declared by the column's WRITER (#44 arm). `by:"trigger"` means a trigger that NULLs the column, checked in the live function body (MQ-D3, live only); a trigger that deletes rows is a presence-only `guards.requires` (Spec 124 R-CR).
5. **Emits:** every key the compute emits is a declared `emits[]` entry (gate C, measured at capture).
6. **`explained-diffs.json`** exists; `{"contract_version":1,"diffs":[]}` for a net-new step (#40; load_coa_notices precedent).
7. **Finish the descriptor, notes and compute before capturing.** Any edit stales `source_fingerprint` (#44 STALE, G8) and forces a recapture. A recapture over a loaded target needs the step's own reset or force path to produce a nonzero capture (#38; coa `.forced.json`). Superseded for empty targets by Spec 124 R-DD: every source-version skip probes the first write target, and an empty target LOADs with reason `target_empty`.
8. **The harness overwrites only tracked goldens:** stage the previous capture by path before `--overwrite`.
9. **Runbook stop bounds quote the governing spec's population** (Spec 65:302 bounds residential lots, not all parcels).
10. **Host:** local Supabase DSM `mmap`; worktree DB env via `DOTENV_CONFIG_PATH` for one process; `db:generate` on a restored DB is spliced, not taken whole (`docs/runbook/dev_host_setup.md` §4).
11. **A recapture repeats the original capture's flags.** A capture records its own `invariants_file`; retaking it without `--invariants=<that file>` falls back to the descriptor's invariants and drops the rest, which G8 reads as unexplained diffs (refresh_snapshot, H6 A2, 2026-10-16). Read `invariants_file`, `chain` and `args` from the previous capture first.
12. **A recapture also replays what the capture does not store in `args`** (V3 fleet night, 2026-10-16). (a) Harness projections: a `table_specs[].columns_source`/`order_source` of `"arg"` means the original passed `--table-columns`/`--table-order`; rebuild them from the previous capture, or the descriptor default re-hashes clock columns (`updated_at`, `last_seen_at`, `linked_at`) and G8 fails (`capture-step-golden.js:487-498`). (b) Brackets: a nonzero capture taken inside a perturbation bracket (`ingestor-forced-cohort.js`, the `*-cohort-differential.js` scripts, `link-massing-healing-cohort.js`) is replayed through that bracket with its committed cohort, never as a plain run (#38). (c) Inputs: a filesystem-source step needs its file in this worktree's `data/` (gitignored; clone it in with `cp -c`), or it skips with `no_source_file`. (d) A fleet night runs only `node scripts/analysis/capture-step-golden.js --replay-all` output, executed as printed (Spec 124 R-CZ); a capture a plain harness call cannot retake has an entry in `docs/reports/golden/<slug>/recapture.json` naming every flag, and #38 is RED without it. (e) A recapture regenerates traces under the G9–G11 resolver (Spec 124 R-DG, #44); declare any new ORDER BY / DISTINCT ON read the same night, never a ledger row.
13. **A test that needs Postgres is `*.db.test.ts`** (McDonald's Airtight V3, B5, Spec 124 R-DH, 2026-10-17): under `src/tests/db/`, or beside its step under `src/tests/steps/<slug>/`. `npm run test` excludes `**/*.db.test.ts` and `npm run test:db` runs `.db.test.ts`; never a per-file package.json list (`step-conformance.infra`).
