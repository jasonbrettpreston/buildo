# Mobile Audit — Specs 77, 90–99 (2026-07-10)

**Scope:** all 11 specs in `docs/specs/03-mobile/` (77, 90, 91, 92, 93, 94, 95, 96, 97, 98, 99 — no numbers missing; Spec 77 lives in 03-mobile) audited against the live tree, the live dev DB, the mobile test suites, and 11 DeepSeek-R1 adversarial spec reviews (all farmed via `npm run review:deepseek`, triaged: kept findings verified against code, hallucinated ones discarded with reasons). Method: 5 parallel audit agents + central DB/coherence verification. READ-ONLY audit; this report is the only artifact. NOT committed — orchestrator reviews first.

**Confidence convention:** every claim below is file:line-backed unless marked otherwise. Items marked *(medium confidence)* are static-analysis-only (not runtime-verified).

## 1. Executive Summary

The mobile app is **substantially built and internally healthy — but broken at exactly one seam that matters most, and stale at the spec layer.**

1. **The app exists and is disciplined.** All 11 specs have real implementations: 20 screens, 11 hooks, 8 Zustand stores, a Zod boundary, MMKV persistence, 28 green Jest suites (405 passed / 0 failed / 4 documented skips), a spec-matrix checker that passes, and 12 Maestro flows. Spec 99 (state architecture) is best-in-class and the code demonstrably follows it — two lint tests (`spec99.mandates.lint.test.ts`, `routerHygiene.lint.test.ts`) mechanically enforce its mandates.

2. **HEADLINE DEFECT — the feed→detail/save `lead_id` seam is broken (Spec 91 INTEGRATED = FAIL).** The feed emits `lead_id = permit_num || ':' || LPAD(revision_num,2,'0')` (`src/features/leads/lib/get-lead-feed.ts:120`, e.g. `24 101234:01`), but both the detail route and the save route parse only the `num--rev` form (`src/lib/leads/parse-lead-id.ts:37-41`; `src/app/api/leads/save/route.ts:105-113`). Mobile passes the feed's `lead_id` verbatim (`mobile/app/(app)/index.tsx:133`; `mobile/src/components/feed/LeadCard.tsx:114`), so **tapping a feed card 400s ("Lead not found") and the feed's save-heart optimistically fills then rolls back on a 400**. Every test gate is green because each side tests its own invented format (`mobile/__tests__/useLeadFeed.test.ts:15` uses a shape the server never emits; `src/tests/api-leads-save.infra.test.ts` uses hand-made `--` fixtures). The flight-board path is unaffected because it composes `num--rev` from parts everywhere. This is the single highest-priority fix and needs a cross-contract regression test that pipes a *server-emitted* id into the parsers.

3. **The monetization loop does not close at either end.** Checkout cannot complete in-repo: `subscribe_nonces` are written by the session route but **read by nothing** — no nonce-exchange endpoint or web checkout page exists, and the webhook's `metadata.user_id` contract depends on that missing page (the webhook itself is real and hardened). And deletion never cancels Stripe — `delete/route.ts:44-45` is a deferred comment, so **a paying user who deletes their account keeps being billed**; the PIPEDA purge script (`scripts/purge-expired-deletions.js`) does not exist and the entire Delete-Account UI has zero mobile callers. Separately, **manufacturer accounts are hard-broken**: `get-user-context.ts:76-83` 401s any NULL/empty `trade_slug`, and the spec-mandated `trade_slugs_override` fallback has NO reader anywhere in the codebase.

3b. **Several user journeys dead-end.** ToS resume wedge: `terms.tsx:73-76` re-PATCHes a fresh `tos_accepted_at` that the server's TOS_IMMUTABLE guard 400s (`src/app/api/user-profile/route.ts:216-235`) — a user who drops off between the ToS PATCH and completion PATCH is permanently stuck. Backup email captured at sign-up is never persisted (`sign-up.tsx:156-172` — Spec 93 §3.3 recovery is fiction today). `first-permit.tsx` is a stub even though `SearchPermitsSheet` now ships in flight-board. Spec 92's `NEW_HIGH_VALUE_LEAD` push — the flagship engagement notification — has zero server-side implementation, the "Maybe Later → enable via Settings" path doesn't exist, and Android-13's channel-before-permission ordering is unimplemented (the permission dialog may silently never appear on Android 13+).

4. **Specs have rotted behind the code — and Spec 97 is the extreme case.** The dominant pattern is stale-spec-vs-healthier-code: Spec 91 §3 describes payload fields that are emitted nowhere (`lifecycle_seq/group/block/stage`), a `?sort=` param that doesn't exist, and a `'realtor'` lead_type that is actually `'builder'`; Spec 93 §3.4 contradicts the shipped (and correct) MMKV-clear behavior; Spec 90 §7 claims a `packages/shared-types` monorepo workspace that does not exist (schemas are hand-duplicated); Spec 94's trade list predates the Spec 80 35-trade fold; Spec 95/97 still describe JSONB notification prefs that mig 117 flattened. Spec 97 reads as complete while roughly half of it is unbuilt (entire deletion UI, CSV export, most settings rows, OS-permission-denied state). 5 of 11 specs lack the CLAUDE.md-mandated `## Operating Boundaries` (77, 90, 91, 92, 98) and effectively none have `## Known Failure Modes` despite hard-won incident fixes living only in code comments.

5. **Pipeline-compat is mostly clean, with three seams to decide on.** The single-trade consumer model is natively respected everywhere (single-select onboarding, one `trade_slug`, server 403 on mismatch). The is_active demotion flows through the feed correctly (`get-lead-feed.ts:276-277` gates on `is_active = true AND confidence >= 0.5`), BUT (a) the feed reads `attachment_basis` nowhere, so **inference rows rank identically to evidence rows — the "served-but-ranked-below-evidence" contract is not honored consumer-side** (and post-P16 inference rows outnumber evidence rows); and (b) detail + flight-board join `trade_forecasts` unconditioned on `permit_trades.is_active`, so feed and detail can disagree about whether a permit is "for" the user's trade. CoA-to-consumer is consistently fenced today (feed arm behind `LEAD_FEED_DISABLE_COA`, save rejects coa, board filters permit-only) but flipping it requires a coordinated mobile WF — the permit assumption runs deeper than the routes: `lead_view_events` PK has no coa identity, the trial/paywall counter only counts permits, notification types and deep-links are permit-shaped. Supplier-type users have **no mobile account story at all** — `account_preset` is `('tradesperson','realtor','manufacturer')`, `supplier_trades` (mig 213) is disconnected from `user_profiles`, and any NULL-trade profile 401s on every leads route — a spec gap across 93/94/95 to resolve before Spec 87 v2.

6. **Parcel-cost-model (PCM) forward-compat: no blockers, no slots.** Nothing structural prevents the mobile PCM feature, but nothing exists for it either: no consumer address-lookup endpoint (the admin one at `src/app/api/admin/parcels/lookup/route.ts` is `verifyAdminAuth`-guarded), no parcel linkage in any consumer payload (`FlightBoardDetail` and `LeadDetail` carry no parcel id), the onboarding address flow uses the device geocoder + 500m snap (never touches `address_points`, can't yield a parcel), and Spec 99 has no query-key/store/schema rows for it. The architecture extends cleanly (new §3 row + Zod mirrors + a tab/stack entry); the one real dependency is a consumer variant of the Spec 89 lookup + cost-menu read, which needs its own spec.

**Bottom line:** roughly **85% built, ~60–70% working end-to-end** (the feed seam poisons the two most-travelled journeys; the money loop doesn't close; manufacturer accounts are locked out), **spec accuracy ~60%**. The code is better than the specs. The right sequence (§8): fix the seam and the dead-end wedges first (days), close the money loop, harden the contract seam, then the spec-truth pass, then the CoA/supplier/attachment_basis decisions, then PCM as a properly-specced new workstream.

## 7. Synthesis — State of the Mobile App

**How much is built:** ~85% of the spec'd surface exists as real, disciplined code (the exception is Spec 97, which is roughly half fiction — the entire deletion/offboarding UI, CSV export, and most settings rows are unbuilt while the spec reads as complete). **How much works end-to-end:** ~60–70%.
