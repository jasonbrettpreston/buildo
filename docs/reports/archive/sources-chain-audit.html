§ 03

A manifest pin disables an existing incremental path

enrich-parcels.js already implements incremental mode:

const incr = full ? '' : 'AND sp.comp_count IS NULL';

But manifest.json pins it full for this chain, and the script consumes the flag as a bare OR with no gate:

"enrich_parcels": { "chain_args": { "sources": ["--full"] } }

const full = process.argv.includes('--full')
          || process.env.ENRICH_PARCELS_FORCE_FULL === '1';
ModeRows the comps pass touches
--full (what the pin forces)426,732
incremental0
The nuance that changes the fix

Incremental mode selects only comp_count IS NULL, and every eligible parcel already has one — so it would write nothing, ever. --full is currently the only refresh mechanism; removing the pin would freeze comps permanently.

The defect is that only two behaviours exist: rewrite 426,732 every run, or never refresh.

An earlier draft carried “~351,899” from review_followups. That figure is wrong — the executed count is 426,732.

The fix is already proven in-repo, on the sibling step

link_massing had the identical defect. P11-2 (scripts/lib/massing-full-gate.js) made --full permit rather than force, using a data signal (corpus count vs last completed run) and a code signal (LINK_MASSING_CODE_VERSION) — because a pure data gate would have silently skipped the b16c036 predicate flip. enrich_parcels is the second of exactly two --full pins; the other was gated a month ago.

The obvious-looking alternative — adding an IS DISTINCT FROM guard to the comps write — is wrong: it suppresses writes inside a full pass that should not be running full. Fold D declined that guard correctly, but on counter-honesty grounds, and never examined the pin above it.

§ 4.3

Three structural inconsistencies

  • Dual ledger rows. Four steps call pipeline.run() and hand-roll their own running row. Only load_wsib has a try/finally. The other three strand on any throw — this is B6.6's strand factory, and 3 of its 6 named scripts live in this chain.
  • Gating is ad-hoc — four mechanisms, no shared interface. source-version.js tiers · a bespoke version-compare in enrich_centreline · massing-full-gate.js · B3's runLedgerGateDecision. A new step has no obvious pattern to copy.
  • Two --full pins, only one gated.

Verification is strong and layered — 5 assert steps in-chain, a workflow-level verdict check, plus the freshness watchdog. Observability is genuinely uniform at 27/27. Error handling is the weak axis: only 5 of 27 scripts carry any try/finally, and pipeline.run() protects the other 22 — which is exactly why the hand-rolled rows are dangerous. They sit outside the protection everything else depends on.

§ 05

Phase B premises refuted by grounding

Three premises, all carried forward v3 → v4 → v5 by reference (“As v4”, “As v3”) without re-verification.

B4 — the “zero-intersection floor” is legitimate by design

Spec 62 :374 states the version signal reads “the run row, never the per-parcel column (which carries a legit-NULL zero-intersection tail)”; :375 names “a permanent ~14.5K” tail costing “seconds, not 92 min”. It is already instrumented (L21) and its gate passes at 2.98% against a 10% WARN threshold. Stamp-with-defaults would destroy the signal the incremental design depends on.

Measured independently: 14,510 stuck parcels — p50 41.7 m, p90 112.5, p99 335.5, max 2,047 m. A smooth continuous tail, so widening also fails on its own terms: 30 m converges 30.5%, 50 m only 64.7%.

B5 — scope premise false, and not a performance step

Only load-zoning.js:362 fetches package_show. Of 8 CKAN loaders, 1 resolves at runtime and 7 are pinned; load-neighbourhoods (two pinned UUIDs) was omitted from B5's scope entirely. A version gate is not resource resolution — the HEAD-gated loaders check a pinned URL and would still 404 on rotation, so resolve must precede HEAD. B5 saves zero minutes; it prevents a break.

B6.6 item (b) — superseded

A self-expiring TTL inside the B3 gate contradicts E-R2, which pins that a stranded row must keep forcing RUN, and is locked by a db test. Items (a) and (c) stand.

§ 06

Citation rot has a predictable pattern

Citations decay specifically where the plan's own earlier steps edit the file. The force-full argv target went stale twice: v3 said :1317, a fold corrected it to :1378, and it is now :1668 — because B2 added 389 lines after the correction landed.

Also stale: two .tsx files cited under src/components/admin/ live at src/components/; the stats-route IN-list is :326 not :321; the 192h constant is :344 not :338.

Mechanism: cite by greppable anchor — a function or constant name — not a line number.
