## rc#1 MED: the plan never says how a person reaches the Searching state, and the real path is narrow
Plan: Settled by reading (1) and "What the page shows per state" say the page waits forever offline and show "Searching". They do not say who gets there or whether anyone waits the full 60 s.
Evidence: the only caller that opens the semi page is mobile/app/(app)/parcel-tool/[parcelId].tsx:27, `useSettledRedirect(ask && parcelId ? semiQuestionRoute(parcelId) : null, isFetching)`. It redirects only after the same key ['parcel-lookup', parcelId] has settled data. The semi page reads that same key (semi-question.tsx:28), and queryClient.ts has gcTime 86_400_000 (24 h). In normal use the semi page therefore opens with data already cached, shows the question at once, and never reaches "Searching". The empty-cache case is a cold entry (deep link, a restored route after the cache is gone), a cleared cache, or a first fetch that hangs without an error. fetchWithAuth has no timeout, so a hung request does wait. While offline the OfflineBanner (useNetInfo) is on screen, so the person is not told nothing. The paused fetch also resumes on reconnect and, in the plan's design, data then replaces the error (T2).
Fix: add one sentence to Settled by reading (1): the wait is rare (cold open or an empty cache only), the page shows "Searching" under the offline banner, and the 60 s limit is a backstop, not a common wait. This is the answer to "would a person wait 60 s": almost never from a cached route; the limit matters for a cold open, an offline cold start and a hung request.
