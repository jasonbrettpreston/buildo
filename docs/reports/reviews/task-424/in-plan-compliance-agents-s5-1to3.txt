### 5.1 Compliance (spec → code)
**Question:** *Given a spec and the implementation, does the code SATISFY every clause of the spec's Behavioral Contract + Auth Matrix?* Item-by-item, spec-clause → code-line, PASS/FAIL.
**Substrate:** DeepSeek CLI at plan altitude (`spec <path>`), or a `general-purpose` agent for the code diff.
**Distinct from A3/A5 because:** Code Reviewer asks "is the code good?"; Integration asks "does it match the *codebase*?"; Compliance asks "does it match the *spec*?" — a clause the spec mandates but the code omits (e.g. Spec 21 §6's phantom `stripe_cancel_failed` directory filter, which the spec promised and the code never built) is a Compliance finding no other role owns.
**HARD DEPENDENCY:** Compliance is only meaningful if the spec is TRUE. Run **Ground-truth (§5.2) FIRST**; a stale spec makes compliance-checking a check against fiction (manual §8.3).

### 5.2 Ground-truth (reality → spec)
**Question:** *Is the SPEC still true?* For each load-bearing claim in the spec, verify it against the live code / DB / behavior; report every drift as "spec §X says A; reality is B."
**Substrate:** `general-purpose` (main tree + live DB) — it needs to read code AND query the schema/data.
**Absorbs "spec-freshness enforcement":** you do NOT need a separate up-to-dateness agent — spec drift IS this agent's primary output. Enforcement = (a) Ground-truth runs at the START of any WF that touches a spec-governed area, and (b) a **standing periodic Ground-truth sweep** (a scheduled routine — see §7) that diffs high-traffic specs against reality and files drift to `review_followups.md`. This directly serves CLAUDE.md Prime Directive #10 (spec-first, no assumptions).
**Why:** the manual's single most-cited failure (§8.3) is planning against a stale spec. Spec 20 described unbuilt routes; Spec 95/97 described a retired immediate-cancel design after the period-end ruling. Ground-truth is the antibody.

### 5.3 Round-2 adjudication — FORMALIZE the existing practice
**Substrate: DeepSeek CLI produces the pass; Integration (`general-purpose`, main tree) is its grounder** — already practised, now stamped (§A/§B).
Not a new agent — a **mandatory second pass**. After the panel returns findings, run **DeepSeek + Integration against the *proposed findings/changes*** (not the code): for each finding, is the premise true, is the ruling already settled, does the fix cost less than the risk? This operationalizes manual §6.3 (⅓ false premises). Rejected findings are written to the plan *with reasons* so they don't return every round (§8.8). Round-2 is cheap (DeepSeek) and catches the eager-fix (§8.4).

#### 3. Design

**Where the list lives: `.husky/pre-push-checks.sh`**
- `.husky/*` is in the `protected` list (mcbylaws/protected-paths.json:51) and `.husky/**` is in HARD_FLOOR (pre-push-summary.mjs:9). `globToRegExp` turns `*` into `[^/]*` (paths.mjs:90-92), so the new file is matched.
- An edit to the list therefore keeps the protection the checks have today: shown at push, owner y.
- Putting it under unprotected `scripts/hooks/` would weaken that, and changing the policy file is MB-67's job (policy $comment).
- git runs only hooks with known names, and the H6 test checks only the four hook names (hooks-composition.infra.test.ts:434-455). So an extra file in `.husky/` is inert.

**Why a shell script:**
- The hook is already `#!/bin/sh`, and the station's `step()` is shell.
- A node runner would add a process layer and would have to re-implement passing stdin to the gate.
- The script stops at the first failure through a single `&&` chain. Its exit status is the chain's.

**Exact text of `.husky/pre-push-checks.sh`:**
```sh
#!/bin/sh
#### task-424 (RR-0370, option C): the ONE list of the non-interactive pre-push checks, in order; stops at the first failure.
####   push                      .husky/pre-push. The McBylaws gate reads git's ref pairs on stdin and may ask the operator (its --push arms).
####   station <base> <run-dir>  the push station. The gate judges <base>..HEAD (--ci, never asks); each step's output goes to
####                             <run-dir>/<name>.log, one line per step to <run-dir>/steps.log, the test report to <run-dir>/suite.json.
#### The mode changes the gate's mode and where output goes; never which checks run or their order. Fork cap: R-CQ (see
#### .husky/pre-push); scripts/analysis/step-validate.mjs parses it from THIS file, so no comment here may carry a fork assignment.
mode="$1"; base="$2"; run="$3"
case "$mode" in
  push) ;;
  station) [ -n "$base" ] && [ -d "$run" ] || { echo "pre-push-checks: station needs <base> <run-dir>" >&2; exit 2; } ;;
  *) echo "pre-push-checks: usage: push | station <base> <run-dir>" >&2; exit 2 ;;
esac
step() {
  name="$1"; shift
  if [ "$mode" = push ]; then echo "== $name"; "$@"; rc=$?; echo "   rc=$rc"; return $rc; fi
  echo "== $name" | tee -a "$run/steps.log"
  "$@" > "$run/$name.log" 2>&1; rc=$?
  echo "   rc=$rc" | tee -a "$run/steps.log"
  return $rc
}
mcbylaws_gate() {
  if [ "$mode" = push ]; then node scripts/analysis/mcbylaws/gate.mjs --push; else node scripts/analysis/mcbylaws/gate.mjs --ci --base "$base"; fi
}
full_suite() {
  if [ "$mode" = push ]; then set --; else set -- -- --reporter=default --reporter=json --outputFile="$run/suite.json"; fi
  VITEST_MIN_FORKS=8 VITEST_MAX_FORKS=8 npm run test "$@"
}
step mcbylaws-gate mcbylaws_gate &&
step step-validate-staged node scripts/analysis/step-validate.mjs --staged --fast &&
step step-validate-all node scripts/analysis/step-validate.mjs --all --fast &&
step spec-split node scripts/analysis/spec-split-check.mjs --check &&
step typecheck npm run typecheck &&
step suite full_suite
```
