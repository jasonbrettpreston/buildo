plan-error-paths#1	BUG severity=HIGH — plan Step 3 "The lookup route calls `readSearchSettings()` after the parse, before the rate limit (keeps 401 first)." — the settings read now sits ahead of the limiter, so when that read throws (missing row, DB blip) the request 500s before the counter is touched and the throttle is never applied, so every retry (the phone already retries on failure) re-runs an uncounted DB query and amplifies load exactly when the DB is unwell. — keep the rate-limit check first and read the settings for the limit value ahead of it from a short last-known cache, or bound the failing path so a settings read failure cannot bypass the window.
plan-error-paths#2	BUG severity=MED — plan Step 4 "SearchBinding: `export const SEARCH_CANDIDATE_LIMIT = sliceNumber(SEARCH_SLICE, 'candidate_cap')`." — the new key is read at module scope, so on any build whose generated slice predates the key (a stale fixture, a partial regenerate, a reverted descriptor) the import throws before React mounts and the search screen shows nothing at all rather than its error state; the store read at step 4 has the same shape. — read the two values inside the function/selector and pin them with the conformance test, or make the slice read return a validated constant the build step fails on, not a runtime throw.
plan-error-paths#3	DEFER severity=MED — plan (B) facts "`ON CONFLICT (variable_key) DO NOTHING`; `--only` skips the loader (:23, :326)" — the apply is idempotent on a re-run, but that same keying freezes a wrong default, bound or description inserted on the first run, and the card rules out the migration that would correct it. — c3 must compare each of the six rows' value, min and max against the intended values, not just presence, and report any mismatch as a stop before the operator GO.
plan-error-paths#4	DEFER severity=MED — plan Step 5 "L8: export `writeOutputs(root)`, which writes and then unlinks GEN-STRAY files." — the unlink runs after the writes, so a second concurrent emit, or a file another process removed, throws ENOENT after the outputs are already replaced, leaving a failed job on correct output and a rerun with nothing left to delete. — tolerate ENOENT on each unlink and treat "already absent" as success.
plan-error-paths#5	DEFER severity=MED — plan (E) "Whether the unlinked read's `LIMIT 11` (:426) is the cap or its own window." — the plan converts every LIMIT 10/11 to `cap`/`cap+1` while admitting it has not established what :426's 11 is, so if it is its own window a change of the cap silently changes how many rows feed the "is there more" decision. — resolve :426's role before the conversion and leave its number typed or give it its own key if it is not the cap.
plan-error-paths#6	DEFER severity=MED — plan Step 5 "L4: the check at :51 skips `v < ENTRY_FROM[k]`." — the plan does not say what ENTRY_FROM[k] is when a number key has no allOf `if.properties[k].minimum`; if it comes back undefined the skip never fires and a 0 is rejected (AC#2 red), and if it defaults to 0 a 0 is emitted with no entry, which is the empty path this finding was meant to close. — treat a missing minimum as "no rule" explicitly and fail the emit with the key named, rather than comparing against an undefined.
