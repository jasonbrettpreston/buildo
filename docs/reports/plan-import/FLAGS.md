## Findings that change the plan (read first)
1. **Backlog's auto_commit messages are refused by the real commit-msg hook.** With `auto_commit` on, a drag (HTTP PUT to `/api/tasks/<id>`, what the board sends) committed with the message `Update task TASK-7`. Other messages Backlog writes: `Create task TASK-19`, `Update task TASK-19`, `backlog: Add document doc-3`, `backlog: Add decision decision-2`, `backlog: Add milestone m-2`, `DRAFT-3 - Create draft DRAFT-3`, `backlog: Archive task TASK-19`. The repo chain `.husky/commit-msg` ran on `Update task TASK-7` (scripts in `runmsg.sh`, real scripts from the worktree at e9bd70288): `validate-commit-msg.sh` exit 1 (`Required: type(NN_spec): description`), lesson-routing 0, spec-diff 0, integrate-verification 0, `gate.mjs --commit-msg` 0. So with `bypass_git_hooks: false` every board drag and CLI write fails its commit. With a refusing hook (stand-in), `task create` exited 1 after 3 attempts (`Git operation 'commit task file ...' failed after 3 attempts`), and the task file was removed again (18 files before and after, `git status` clean). Consequence for plan section 4: Backlog's own auto_commit cannot be the commit path unless `validate-commit-msg.sh` gains an exemption for Backlog's forms on a backlog-only diff (a hook change that needs its own ruling); the plan's fallback (a launchd job that runs `git add backlog && git commit` with a conforming message `docs(137_mcqueue): ...`) works with the unchanged hook. The loader's own commits are written by hand, so they are unaffected.
2. **A root `backlog.config.yml` REPLACES `backlog/config.yml`, it does not layer over it.** With a root file holding only `auto_commit: true`, `default_port: 6499`, `project_name: "rootcfg"`, `backlog config list` showed `projectName: rootcfg`, `defaultPort: 6499`, `autoCommit: true` and the DEFAULT `statuses: [To Do, In Progress, Done]`. So an untracked root override for the board checkout works only if it is a full copy of the committed config with `auto_commit: true` changed, and it drifts when the committed config changes. Given finding 1, the override path is not needed if the commit job (finding 1) is used.
3. **`backlog decision create` takes only a title and `-s`.** `--body` and `--description` are refused (`error: unknown option`). The file it writes has empty `## Context`, `## Decision`, `## Consequences` sections. The loader must write the decision body (verbatim quote, cite, text, `source: operator`, `kind: ruling`) into the file after `decision create`. Extra front matter keys (`source`, `kind`) survive `decision edit -s` (status line only is replaced) and `backlog doctor` stays clean.
4. **`task list --json` has no `dependencies` field.** It has `isReady` (true for every non-final status whose dependencies are all in the final status DONE, false otherwise). `backlog task view <id> --json` carries `dependencies` and `dependencyGraph`. `backlog-next.mjs` must read the task files' front matter (or `task view --json`), not the list JSON, for its MERGED-target and FROZEN rules.
5. **`--ready` semantics measured** (item 11): a dependency counts as satisfied only when its status is the configured final status (DONE). A task depending on a MERGED, BUILT or FROZEN task is `isReady: false`. Non-final tasks such as BUILT, OPERATOR, RUNNING, MERGED, WAITS with no open dependency are ready. A dependency on a draft is accepted and keeps the task not ready. The plan's `backlog-next.mjs` is still needed (it adds the MERGED-target rule, `when:` ids and the due list).
6. **A bare number is ambiguous once a draft shares it.** `--depends-on 1` exited 1: `Dependency ID 1 is ambiguous; 2 files match` (draft-1 and task-1). The loader must always pass the full id `task-N`.
7. **`zero_padded_ids: false` is read as NaN** (`backlog config list` printed `zeroPaddedIds: NaN`). Use `zero_padded_ids: 0` (printed `(disabled)` / `0`, ids `task-21`). With `3`, the next id was `task-020` (file `task-020 - Padded-id.md`, id `TASK-020`). The plan's table says `zero_padded_ids: false`; it must say `0`.
8. **`-m "<unknown milestone>"` is accepted and stored as the literal text** (`milestone: Nope`, no refusal). A known title is stored as its id (`-m "F Foundations"` -> `milestone: m-0`). The loader must check milestone existence itself.
9. **`--ref` splits on commas** (`--ref "a.md#L1 sha256=1,b.md#L2 sha256=2"` gave two references). Refs are `<path>#L<n> sha256=<12>` with no commas, which is safe, but a path with a comma must be refused or renamed.
10. **Every created task gets the config `definition_of_done` items as unchecked boxes** (two items from the test config appeared on all 20 tasks; `--dod` adds a task item on top, `--no-dod-defaults` exists). With ten rules in the config each of the 319 tasks carries ten DoD lines, as the plan intends.
11. **Dates in the files carry no seconds** (`created_date: '2026-11-19T04:19:00Z'`), cosmetic only.

## The pilot's auto-board parser against a `task-N` token in a queue head
Read-only: a copy of `~/Buildo-scratch/backlog-pilot/export-status.cjs` (the parser `auto-board.zsh` runs) in `build-r1/ep/`, run against a one-commit throwaway git repo holding five synthetic queue heads (the pilot folder, its board and its launchd jobs were not touched). The parser takes the id from the heading line with `ID = /\b(MB-\d+[a-z]?|MF-\d+|FE-\d+|INC-\w+|AV3-...|[A-Z][A-Z0-9]*(?:-[A-Z0-9]+)+)\b/` (the first match). Result: heads `**MB-90 Row as today ...**`, `**MB-91 ... — task-12 · (R) ...**`, `**MB-92 · queue · lane · stage · task-13 Head ...**` and `**task-14 · MB-93 · queue · lane · stage ...**` all parsed (four rows, ids MB-90..MB-93; the `task-N` text stays in the title). A head with ONLY a task token (`**task-15 Head ...**`) is `unparsed` (`.cursor/MCBYLAWS-QUEUE.md:14`), exactly like any head with no id today, and `auto-board.zsh` then prints the `WARN unparsed status lines` line. So adding `task-N` beside `MB-nn · queue · lane · stage` is tolerated; lowercase `task-N` is never taken as the id.
