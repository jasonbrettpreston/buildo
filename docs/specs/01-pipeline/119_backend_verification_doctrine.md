## 1. The doctrine in one page

Backend work gets to correct code by moving through nine stages, in order, each one closing a failure mode that shipped without it. No stage is a courtesy — every one below has an incident where skipping it (or doing it late) produced a live defect.

| # | Stage | Mechanism | WHY — one incident |
|---|-------|-----------|---------------------|
| 1 | **Spec-first grounding** | Read the governing spec via `docs/specs/00_system_map.md` before reasoning about any script/chain/schema; never infer from a name. | The 2026-07-30 nodriver debugging day spent 13 CI cycles fixing a scraper framed as "regressed" per Spec 115 §2.4's design intent, when two queries (`SELECT count(*), max(scraped_at) FROM permit_inspections`) and one `git log --diff-filter=D` would have shown it had **never once produced a row** — a different bug, a different strategy (`tasks/lessons.md`, "Debugging protocol" section). |
| 2 | **Plan with EXECUTED claims** | A plan may not contain a claim that could be executed but wasn't — a data claim carries its query **run** (host + `current_database()` printed), a SQL shape is **parse-tested**, a census grep runs at **full scope**. "Approved on paper" is not a verification state (Spec 08 §11.1). | Phase A's C2: *"397 permits spell their base revision `'0'`"* — the COUNT was true, the INFERENCE was false (every `'0'` row is a `DCs DeferredFees` administrative stub); it survived **four review rounds** because none of them SELECTed the rows and read `permit_type`. C2 was reverted; the correct fix landed as `eff28a7e` (`AND status = 'Inspection'`, two lines, zero invented spellings). |
| 3 | **Fail-first tests IN the plan, reviewed at plan altitude** | The failing cases — fixtures, red/green expectations, invocation mode — are written INTO `.cursor/active_task.md` and reviewed BEFORE the test file exists, collapsing what used to be a separate test-panel round (Spec 08 §11.4). | Phase A's C7 Case B: the hash-guard vacuity was caught by three blind reviewers reading the DESIGN before any test file existed; the corrected test then enforced the fixed design directly — no separate round needed. |
| 4 | **Lean grounded panels (plan altitude)** | 3–4 seats, reality-grounders first (Integration/Reality-Check/Schema-Fidelity/Ground-truth), CLIs demoted to whole-file audit generators, always grounder-adjudicated (Spec 08 §11.5). | Two 2026-08-13 CLI diff reviews produced **zero** diff findings and DeepSeek re-raised a claim ALREADY refuted (`PG_HOST`) — CLIs without tree/DB access hallucinate confidently on wiring; the grounders (Integration: refuted C2's premise, found the live 4th writer) carried the session. |
| 5 | **Fold-validation is a STEP, not a courtesy** | After folding any review round and BEFORE implementation: one grounder RE-EXECUTES every claim in the fold + one Cross-read Adversary checks the folded decisions PAIRWISE (Spec 08 §11.2). | Phase B's B2+C5 fold-validation (2026-08-14) found a **BLOCKING** defect (B-1: defer decisions computed in-txn would permanently hide parcels from later passes — the exact silent-staleness class the mechanism was built to kill) plus 5 more; the C7 fold-validation round found **10** defects including an unwritten SQL expression and a falsified census query. `tasks/lessons.md`'s closing entry: *"No review pass re-reads the folded corrections against each other, and that is where the worst defects hide."* |
| 6 | **Implementation gated by the suite** | Code is written only after the red-first suite exists and reds for the DESIGNED reason (Spec 08 §11.3). | The 2026-08-13 envelope regex "red" matched nothing — its red was the not-found branch, not the assertion it claimed to prove. A lock never proven red against the defect it names is not a lock; it was rewritten before being trusted. |
| 7 | **Output panel: Guardian + charter-matched grounder** | Lean — typically two seats, not the full plan roster (Spec 08 §11.5). | Phase A's C7 five-seat output round produced exactly **two** novel catches, both reachable by Guardian + one grounder alone — the other three seats added triage cost, not findings. |
| 8 | **Same-session arrival OR an explicitly scheduled deploy** | Landing on `main` is a tracked step, not an assumption from "the panel passed." A cherry-pick vs. branch-merge decision is made and recorded, not defaulted. | C1 (`67663a81`) passed 5 panel reviews, 250 tests, typecheck and lint — and then sat on a local branch for a full day while `chain_permits`/`chain_coa` died nightly on cloud, because **every gate in the workflow measured QUALITY; none measured ARRIVAL** (Phase A SESSION RECORD §5, "PROCESS GAP #3"). It shipped as a deliberate cherry-pick to `cdaea415`, verified byte-identical against the branch commit, specifically BECAUSE the branch also carried an unrelated unapplied migration (240) that a full merge would have shipped alongside the hotfix. |
| 9 | **Standing instrumentation as the post-ship verifier** | The code that watches the shipped behavior in production — trend tripwires, audit rows, WARN/FAIL gates (§4) — is the doctrine's own closing loop; it is what catches what review couldn't. | 118's root incident: the `refresh_snapshot` step went from a **3-minute** historical duration to **64 minutes** under write-traffic-driven heap decorrelation, and NO instrument watched step-duration TRENDS — only thresholds against a point value. Two of three 2026-08 failure days were spent because nobody trended a number that had already moved 10×. |

**The shape, stated once:** ground the plan in reality before arguing about it (1–2) → write the tests the code must pass, reviewed as design (3) → spend review budget on grounders, not headcount (4) → treat a folded plan as a NEW claim needing its own verification (5) → let the suite gate the code, not the other way around (6) → verify the output lean (7) → track the code until it is actually running where it matters (8) → replace "we reviewed it" with "we are watching it" once it ships (9). Spec 08 §11.6's own accounting: this shape ran C7's defect-coverage-equivalent work in ~7 agent passes against the old shape's ~11 — grounding-first and fold-validation are the efficiency, not just the safety.

## 2. The verification ladder — what "verified" means at each tier

A claim is not "verified" in the abstract; it is verified TO A TIER. Confusing tiers is how a green suite ships a broken pipeline.

| Tier | What it proves | What it does NOT prove | Mechanism | Forced by |
|---|---|---|---|---|
| **Parsed** | The file is syntactically valid JS/Python. | Anything about behavior, types, or logic. | `node --check <path>` in a parse-smoke test — `scripts/` is unlinted (eslint ignores it) and untyped (`tsc` is TS-only), so a syntax error here has ZERO other CI coverage. | `load-parcels.js` shipped 2026-05-23 with a backtick inside a template literal — the file never parsed, the sources chain hard-failed for a week, and neither the pre-commit hook nor any test caught it (`tasks/lessons.md`, ESLint/Tooling). |
| **Typechecked** | Shapes agree across module boundaries. | Runtime correctness, DB reality, business logic. | `npm run typecheck` (husky pre-commit). | Standing gate — CLAUDE.md Prime Directive #5. |
| **Unit-locked** | A pure function returns the right value for named inputs, INCLUDING the fixture that would catch the specific historical bug. | Whether the DB schema/types the fixture assumes still exist; whether the fixture's shape actually exercises the bug class. | `*.logic.test.ts` with a fixture chosen to be the ONE case that distinguishes correct from broken (not just "a" case). | `enrich-parcels.js`'s `IS DISTINCT FROM` idempotency guard (2026-05-31): a single-zone fixture round-tripped clean and hid a `float8` vs `NUMERIC(5,4)` type mismatch that made every multi-zone parcel un-idempotent forever; caught only by running the script TWICE on live data. The regression lock now requires a multi-zone fixture explicitly. |
| **Behaviorally red-first** | The lock fails on the OLD shape and passes on the NEW shape — proven in BOTH directions, at the designed assertion. | A lock that only ever ran against the fixed code (never proven to have caught the bug it claims to). | `git checkout HEAD -- <fix files>` (test files left in place) → run → confirm red-for-the-right-reason → restore. | Spec 08 §11.3: the 2026-08-13 envelope regex whose "red" was the not-found branch, matching nothing. C2's own red-first proof (pytest `2 failed, 6 passed`, printing the genuine pre-fix SQL) is the pattern that DID work. |
| **Battery** | The full suite (`npm run test` / `npm run verify`) is green, including every OTHER file's regression locks the change could have touched sideways. | Live DB reality; production data shape. | `npm run test` — CLAUDE.md Prime Directive #4, husky pre-commit gate #5. | Standing — every WF's Green Light. |
| **Live-DB smoke** | The script runs end-to-end against real data and does not crash, miswrite, or bypass a gate. | Whether it will still be correct after next week's write traffic reshapes the table it reads (see §3, substrate class). | A full invocation against the live/dev DB before merge — Spec 47 §R mandates it; the discipline is enforcement. | `backfill-realtor-permit-trades.js` (2026-05-11): merged with a green unit suite and FOUR bugs that only existed because the script was never once invoked — a `NOT NULL` crash (23502), a missing manifest registration, an advisory-lock collision, and a JS/SQL gate mismatch. "Green tests are not a substitute for running the script." |
| **Production observation with pre-pinned expectations** | The shipped behavior matches a number written down BEFORE the run, so a deviation is instantly legible as "new cause" vs. "known noise." | Nothing further — this is the terminal tier; anything this misses becomes an incident that feeds back into §5. | State the expected value/timing before watching (`lessons:104`); compare after. | The 08-14 deep-scrapes run was watched with the pre-pinned expectation "completes ~18:15 under the new envelope" — its failure was recognized in minutes as a NEW cause (heap decorrelation) rather than another crank of the already-fixed envelope-sizing bug, because the deviation had something concrete to deviate FROM. |

**Rule:** a claim carries the tier it was actually verified at, not the tier its author hoped for. "Unit-locked" is not "live-DB smoke"; a green `npm run test` is not "this script has ever run against real data." Confidence is stratified per Spec 08 §4.5, not global.

## 3. The diagnosis skeleton + adaptation map

*(Generalized from Spec 118 §9, which built this while solving three consecutive daily deep-scrapes failures, 2026-08-12/13/14 — 118 §5 is the worked "Timeout/envelope" instance of the skeleton below; read it for the concrete query-by-query execution.)*

**The skeleton (issue-agnostic — six steps, execute in order, stop when decisive):**
1. **Which layer spoke?** Identify the REPORTING mechanism before the failing one — an axe, a verdict, a watchdog, a data gate are four different reporters with four different blind spots.
2. **Account for the resource, don't characterize the symptom.** Time, rows, bytes, locks — find where the budget actually went from timestamps/counts, never from the error message (the error names the reporter, not the cause).
3. **Is it NEW?** Trend the metric before diagnosing the instance. A value at its historical baseline is a sizing problem; the same value at 10× is a pathology.
4. **Slow vs. blocked vs. wrong** — three different investigations. `wait_event` distinguishes the first two in one query; predicted-vs-observed values distinguish the third.
5. **What changed the SUBSTRATE?** When behavior regresses without a code change to the failing component, something changed underneath it (data volume, physical layout, statistics, cadence, environment). Correlate the regression's start date with the write/change history of everything the component reads.
6. **Last-known-good from DATA, not the spec** (`lessons:93`): output-table timestamps and git history decide regression-vs-never-worked, never the spec's stated intent.

**Adaptation map — six issue classes, the skeleton steps that carry the weight, and the class-specific trap:**

| Issue class | Signature | Weight-bearing steps | The trap |
|---|---|---|---|
| **Timeout/envelope** (118's own incidents) | A platform kill; the component itself healthy | 2 (time accounting) + 3 (duration trend) + 5 (substrate: cadence, queue depth, physical layout) | Fixing the CONSTANT instead of adding the missing hierarchy layer; sizing against a baseline your own concurrent work is invalidating |
| **Data drift/smear** (Phase A's C2/C3/C6/C7 arc) | A count grows; every writer looks correct in isolation | 3 (accretion trend) + 5 (find the writer census — grep ALL of `src/`+`scripts/`; a 4th writer was outside the first grep) + 6 | Count-as-inference: a true count with a false story survives review rounds (C2's "397 permits") — SELECT the rows and read their OTHER columns |
| **Silent green / false PASS** | Nothing red, work not actually done | 1 (the reporter's blind spot IS the finding) + 4 (wrong, not slow) | "I could not check" rendered as PASS/0/SKIP — audit the checker's failure PATHS, not the checked data (Spec 30 §5.4.1 criterion 1) |
| **Lock/zombie contention** (`lessons:34`) | Intermittent, environment-scoped, disappears when observed | 4 (`wait_event`, `pg_blocking_pids`) + 2 | The client's death is not the query's death; `idle in transaction` on an advisory-lock holder is NORMAL — know the by-design holders before hunting |
| **False red / observer geometry** (118 §2's two-red watchdog) | Red with healthy underlying work | 1 + the OBSERVER's clock vs. the OBSERVED's schedule | Fixing the observed when the observer's timing is the defect; every absence-checker has a window sized to some cadence — re-derive on every cadence change (`lessons:100`) |
| **Contract drift** (spec-vs-code, e.g. Phase A's four spellings of "the permit's canonical row") | Two artifacts, each internally coherent, disagreeing | 6 + execute BOTH sides' claims (Spec 08 §11.1) | The freshly-written document is not more authoritative than the freshly-written code — whichever was DERIVED from the ruling wins; cite the ruling |

**The meta-learnings 118 burned in, generalized:** fix MECHANISMS, not constants (a numeric patch that fails twice before the missing hierarchy layer is named is a pattern, not bad luck) · instrument TRENDS, not points (every gate historically measured a value against a threshold; none measured it against its own history — §4.1 below is the fix) · cross-read concurrent workstreams like folds (verified independently ≠ verified together; shared substrate — a table's physical layout, a schedule, an env var — is the coupling reviews don't see on their own) · the observer has a schedule too · recovery is part of the design, written down, not re-derived by hand under pressure · predict before you look (`lessons:104`).

## 4. Instrumentation doctrine

### 4.1 Thresholds AND trends
A gate that only compares a value to a static threshold catches the value crossing a line; it never catches the value CHANGING SHAPE while still inside the line. 118's `refresh_snapshot` step ran 3 minutes historically and 64 minutes on 08-14 — every run individually looked plausible against a wall-clock ceiling until the ceiling was hit. The durable form is a **trend tripwire**: compare each run's value to its own trailing distribution (median/percentile over the last N runs), WARN at a multiple (118 proposes ×3), FAIL at a harder multiple (×10). Build this wherever a "suddenly 10×" would hurt — not only timing: row counts, error rates, queue depths.

### 4.2 Standing audit rows over apply-time assertions
An apply-time invariant (a migration's DO-block RAISE, a one-shot backfill's post-verify count) proves a state ONCE, at the moment it runs. It is not enforcement. Migration `138_a` asserted "no administrative row carries a `lead_id`," passed at apply time, and went silently false for months because its trigger was column-scoped to the wrong `UPDATE OF` clause — a permit reclassified into an administrative type on re-ingest never re-fired it. By the time it was measured, **1,190** administrative rows carried one. **A one-shot check proves a state; only a RECURRING check defends it.** Every invariant a migration establishes needs either a trigger that actually fires on every relevant column, or a standing audit row that re-measures it on a cadence, or both.

### 4.3 WARN-not-FAIL for permanently-nonzero metrics
A FAIL gate on a population that is STRUCTURALLY expected to be nonzero (not a bug, a fact about the domain) is a standing red that operators learn to ignore — worse than no gate, because it burns the "red means look" signal for every OTHER gate too. Spec 48 §4.9's rule: a relaxation must never be a silent, forgettable bypass. Emit the live value every run PLUS a `<metric>_retighten` companion naming the machine-observable condition under which it should tighten back to FAIL, and self-retire at zero.

### 4.4 §4.9 self-announcing relaxations
Spec 48 §4.9 is the canonical mechanism for §4.3 — every WARN-not-FAIL demotion carries its own retighten condition IN THE SAME COMMIT, stated in terms the next reader can machine-check, not "revisit later." Phase B's C5 fold-validation caught a live example of this rule being violated in its OWN construction: a proposed `_retighten` flip condition ("zero absent across all five chains") was structurally unreachable until a dependent chain was re-enabled — the fold-validation pass required the threshold text to NAME that dependency explicitly, or the relaxation would have silently outlived its own justification. **A relaxation's retighten condition must itself be checked for reachability before it is folded.**

### 4.5 The escape-rate question — "we don't know what we missed"
No review process, however grounded, catches everything before ship. The doctrine's answer is not ship-time certainty (unachievable) but **bounding the cost of what escapes** on two axes:
- **Detection latency** — how long between a defect shipping and something (a trend tripwire, a standing audit row, a watchdog) noticing. §4.1/§4.2 exist to shrink this number for the classes most likely to escape review (drift, decorrelation, silent regeneration).
- **Blast radius** — how much damage accrues in that window. 118 §8's rule that every orphaned `pipeline_runs` row is terminalized with a cause annotation, never deleted, turns "how bad was it" into a countable INCIDENT INDEX instead of a vague memory. Recovery procedures written down BEFORE the next incident (118 §6) bound the radius directly — the 08-13/14 recoveries were re-derived by hand twice before being written, which is itself the failure mode this doctrine exists to retire.

The escape-rate LEDGER that measures whether this bounding is actually improving over time is §5.1 below — this section states the standard it is measured against; §5 states how the number gets tracked and fed back.

## 5. The improvement loop — how the process improves itself

Detection alone ossifies. The loop below is what keeps the doctrine calibrated against reality instead of decaying into ritual.

### 5.1 The escape-rate ledger
Extend Spec 08 §7b's Roster Manager (A14): every defect LATER found in shipped code is logged against the panel/reviewer that approved the change it lived in — a measured trend, not a feeling. §7b already tracks each agent's real-finding count and false-premise rate per review window; the escape-rate ledger is the same instrument pointed the other direction — findings that arrived AFTER ship, attributed to the panel composition that missed them. A14 is the roster's homeostasis mechanism (Spec 08 §5.9): it recommends new roles from recurring bug CLASSES no current agent owns, retires roles that found nothing real across a window, and — per §5.11 — recommends the standing PROTOCOL RULE or GATE that would have prevented the class, not just a stronger reviewer. This doctrine adds nothing new here; it names the ledger as this spec's improvement mechanism and requires it to be read before any panel-composition change is proposed.

### 5.2 Mutation-testing pilots on lock suites — test STRENGTH, not coverage theater
A lock suite can be green and still be a "snapshot-style change-detector test" — `expect(result).toBe(20)` that locks a value without exercising the logic that produces it, the exact gap Spec 08 §11.3's envelope-regex incident exposed manually (a regex "red" that matched nothing). `docs/specs/00_engineering_standards.md` §12.13 already runs Stryker mutation testing on 4 high-stakes PURE modules (`cost-model.ts`, `distance.ts`, `record-lead-view.ts`, `builder-query.ts`) with a ≥50% mutation-score floor, weekly + per-PR. **Extend the pilot to Backend/Pipeline lock suites** — starting with the files this doctrine's own incidents named as fragile: the envelope-timing locks (`deep-scrapes-workflow.infra.test.ts`), the status-vocabulary locks (`OK_STATUSES`/`RAN_STATUSES` in `check-chain-verdict.logic.test.ts` / `check-pipeline-freshness.logic.test.ts`), and any `resolveChainStatus`/`classifyStepCompleteness`-style pure classifier. A surviving mutant on one of these is the mechanized form of "this lock was never red against the defect it names."

### 5.3 Scheduled WF5 audits sampling shipped code
Panels verify a diff at ship time; they do not re-verify it six weeks later against a table whose write traffic has since reshaped it (118's own root cause). WF5 (Audit, CLAUDE.md trigger table) run on a schedule — not only when a defect is already suspected — is the standing counter to that gap: the `wf5_pipeline_audit.md` bug-pattern checklist exists for exactly this, and its own note ("some findings may have been resolved by intervening WF3 work — verify on next pipeline audit") is itself an instance of the doctrine's own rule (§1 stage 2 — verify by re-running, don't assume prior findings still hold).

### 5.4 Lessons routing per Spec 05's strongest-destination rule
Spec 05 §2 ranks five durable destinations by enforcement strength — test (automatic, forever) > lint/type/pre-commit gate (before commit) > spec/CLAUDE.md (next read) > `tasks/lessons.md` (session start) > `MEMORY.md` (future sessions only) — and the rule is: **choose the strongest destination that fits, never weaker.** A finding routed to `tasks/lessons.md` when it could have been a red-first test is a finding that will recur; the incident ledger in §1–§3 above is proof this routing works when followed (`IS DISTINCT FROM` type-mismatch → a regression-locked multi-zone fixture, not a lessons-file paragraph alone) and proof of the cost when it is skipped (the LPAD collision class recurred across three separate migrations before `138_a` encoded the administrative-exclusion rule as a machine check rather than a convention).

### 5.5 Protocol amendments require an incident citation
Every rule in §1–§4 above carries the incident that forced it — not because incident-citation is decoration, but because a rule without one is a guess about what the next failure will look like, and guesses decay the moment reality diverges from them (the C2 premise — a true count, a guessed inference — is the same failure shape at the level of a SQL query as an uncited protocol rule is at the level of process). Any future amendment to this doctrine, or to Spec 08 §11, must cite the specific run/commit/date that exposed the gap it closes. A rule that cannot point at the incident it prevents is a candidate for deletion, not for enforcement.

## 6. Domain boundaries

This doctrine is **Backend/Pipeline-calibrated** — its evidence base is Phase A/B's `scripts/`+`migrations/` incident ledger, and §11.1's "no unexecuted executable claim" assumes a domain where nearly every load-bearing claim (a row count, a query shape, a duration) IS mechanically executable. Spec 08 §11.5-FE states the necessary qualification explicitly: for Admin/Expo/frontend work, the executable surface is narrower (typecheck, UI-regression suites, render tests, a running app), but visual/UX/interaction-quality claims are NOT executable — reviewer judgment and the non-pipeline 3-reviewer panel carry that weight instead, fold-validation is recommended-lean rather than mandatory, and demanding a query of a design decision is a category error there. **Do not port this doctrine's grounding mechanics to frontend work uncritically** — apply Spec 08 §11.5-FE's frontend nuance at the seam.

### Target Files
The PROCESS this doctrine governs, not a fixed file set: any `scripts/*.js`/`scripts/*.py` pipeline script, `migrations/*.sql`, and their `src/tests/*.{logic,infra,db}.test.ts` / `scripts/tests/*.py` counterparts — i.e., the domain covered by `scripts/CLAUDE.md` and Spec 47's script protocol.

### Out-of-Scope Files
- Panel MECHANICS (roster composition, agent substrates, spawn-prompt templates, cost-tiering rules) — owned by `docs/specs/00-architecture/08_agents.md`, cross-referenced throughout, never duplicated here.
- Frontend/Admin/Mobile process — owned by `docs/specs/02-web-admin/34_web_admin_testing_protocol.md` and `docs/specs/03-mobile/90_mobile_engineering_protocol.md` / `99_mobile_state_architecture.md`; §6 states the seam explicitly.
