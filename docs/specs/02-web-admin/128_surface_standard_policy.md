## §1. Purpose

Every surface in this estate is the same surface, except for its projection. Nothing about how a surface is gated, guarded, validated, metered, recovered or observed is a per-surface invention — it is a declaration chosen from a closed menu, and the schema, the engine and a small set of shape rules make every other answer either impossible to omit or impossible to hide. A surface author's discretion begins and ends at the projection.

**This spec is the durable half** — the part that must still be true after the conversion programme finishes and the packaging Spec 127 describes is forgotten. Spec 126 is the contract; Spec 127 is the procedure; this is the policy, the ruling register, and the open asks.

### §2.1 Rule 2's boundary, named once

Rule 2 ("the client is just glass") is the one rule whose boundary must be written down rather than inferred, because "everything server-side" has five legitimate exceptions and a reviewer who cannot name them will either over-apply the rule or waive it. The five, declared per surface:

1. **Device state** — GPS, push token, permission status. The server cannot know these.
2. **Optimistic UI** — declared as `outputs.optimistic`, not improvised. Spec 90 §3 explicitly encourages it.
3. **Offline cache** — the MMKV projection; a server-driven screen must still render with no network.
4. **Animation / gesture** — Spec 99 §2.1's hard rule; orthogonal to layers 1–4.
5. **Navigation position** — which route is mounted; `expo-router` owns it.

Anything else computed client-side is a Rule 2 violation and needs a `deviations[]` row with an adjudicator and a date.

### §2.2 Two rules with no pipeline ancestor — and the gates that enforce them

The thirteen above are mirrored. Two more exist only here, because the surface estate has two properties the pipeline does not: a schema it *declares but does not generate*, and a projection that must render *identically to more than one target*. Each is stated as a rule so that Spec 127's gate has something to score.

**Rule 14 — a declared schema is asserted against the live catalog, never against its own migration.** Every column, type, nullability, index and RLS policy a descriptor declares is proven against the introspected types and `pg_policies` / `pg_class.relrowsecurity` / `pg_roles`, in **both** directions: a column live but undeclared fails exactly as a column declared but absent does. Reading the migration text back is not an assertion — it is the declaration restated. *Enforced by:* Spec 127 gate **S-schema**, under `BUILDO_TEST_DB=1 npm run test:db`, each lock carrying a RED canary. *Violation reads as:* a red `surface-schema-drift` lock naming the column or policy and which side it was missing from.

**Rule 15 — parity between render targets is a comparison, not a discipline.** A surface declaring more than one `render.targets[]` entry proves its projections equal on the shared field set, by golden comparison. "100% data parity between the web view and the exported document" was a promise in Spec 125 §7 and is a diff here. *Enforced by:* Spec 127 gate **S-parity**, over the golden PAIR. *Violation reads as:* a field present in one target's projection and absent or different in another's, named by the differential.

Both rules are scored in Spec 127 §5's policy-coverage matrix alongside rules 1–13, and both are `PROSE-ONLY GAP` until Phase 1 lands their artifacts — which is the honest status, not a placeholder.

### §2.3 Archetype variance

The Spec 124 §3 variance table has a surface analogue: `✓` = must answer per the archetype's required-field profile, `N/A` = the profile forces `"none"`. The full table is generated per archetype from `surface.schema.json`'s `allOf` blocks once Phase 1 lands, on exactly the mechanism Spec 126 §3 mirrors. ## §3. Budget and refresh rules

**Rule B1 — the descriptor budget is declared before commit 1, and it is a kill criterion.** No descriptor in this repo is under 200 lines; the smallest real one is **388** (`scripts/compute-centroids.descriptor.json`), the largest **8,225**. Fifty-three surfaces at 388 lines is ~20,000 lines of declaration. The archetype required-field profiles are the only mechanism that prevents 53 × 400 lines of `"none"`. **If the pilot descriptor lands over ~250 lines, the profile design is wrong** — that is a stated kill criterion, not a retrospective observation.

**Rule B2 — a proposal to add a declaration carries its measured cost, and the operator rules.** The pipeline's P3 discipline, inherited: every added box, declared check or audit row costs per surface × per render × per user. Visibility wins by default; the cost is *stated*. The cost is reported automatically by `surface-validate.mjs`'s footprint measure (descriptor bytes, notes bytes, `checks[]` row count, golden-pair byte size), never hand-computed once and forgotten.

**Rule B3 — a declared check's READ cost is part of its price, stated against the target it actually runs on.** The EP-D17 extension, inherited and load-bearing here: five `enrich_parcels` post-checks declared `cost_ms` of 180–260 ms from a single local golden sample while the same queries measured 568,601–573,235 EXPLAIN cost against the production heap — and cloud-measured 16–30 s on a vacuumed heap versus 40+ minutes against 1.35M dead tuples, a 150× cliff keyed on heap state alone. **A number an author wrote down once and nobody re-checked is not a cost.** Every surface check that queries pairs a declared ceiling with a per-entry `duration_ms` audit row.

**Rule B4 — goldens refresh on fingerprint, never on request.** A descriptor, contract descriptor, archetype component or format-helper edit after capture forces a recapture. This is mechanical (`source_fingerprint` over `fingerprint_files[]`), not a reviewer's judgment.

**Rule B5 — the register is refreshed at every cutover, not periodically.** A `§R Reflection` section is required after every conversion's cutover (Spec 127 gate S9, binary): a low-confidence table and a recurring / standard-shaping table. The second feeds §4.6's promotion criterion. A ruling with no recurrence claim stays a ledger row.

**Rule B6 — the pre-batch rule. → §5 R-12 is the single home; this is a pointer, not a second statement.** An unaudited admin mutation blocks conversion of the surface that calls it. Measured: **9 of the 15 mutating admin routes write no `admin_audit_log` row**, including `control-panel/configs` **PUT**, which rewrites `logic_variables` plus three more tunable tables. `src/lib/admin/admin-audit.ts`'s own header calls an unaudited admin mutation *"a compliance hole"*, and the mechanism to close each one already exists and is centralised. Closing them is independent of every Spec 126 decision and gets more expensive once the routes are regenerated. **Status: ACCEPTED at R-12** (decided by the measurement plus `admin-audit.ts`'s own header, not by this pass).

### §4.7a ⚠️ Specs 126, 127 and 128 cannot ground each other

Stated here because the protocol above makes it load-bearing. All three specs were authored in **one WF1 pass**, on one date, by one author. §4's step 2 — *a different party adjudicates, never the pass that discovered it* — is a **policy rule** (Spec 124 §4.2, restated per R-I.3), so **a §5 row whose `Amends` cell points only at Spec 126 or 127 is citing its own author.** That is not disqualifying, but it changes what the register is worth for such a row: the value is **the lock, not the rule**.

Two consequences, applied throughout §5:

1. Every `ACCEPTED` row names a **deciding source outside this pass** — a ratified spec, an executed code fact, a prior operator ruling, or law. A row that cannot name one is `PROPOSED`, however obviously right it looks.
2. `Lock` cells are honest: none resolves yet, so **no row reads `BUILT`** (§4.8). `ACCEPTED` means the decision is made and not re-litigated; it does not mean the rule is enforced.

### §4.8 The BUILT-evidence lock (this register's own addition)

**Adopt the resolver, not just the table.** `src/tests/programme-backlog.infra.test.ts`'s `evidenceResolves()` passes only if an evidence token is a real path (`file:line` allowed) or a `git cat-file -e`-resolvable object, with a **RED canary asserting that `'trust me'` fails**. Two commits on this branch (`fc08ff8d`, `b9e3ba8c`) exist solely because evidence strings failed that resolver at pre-push.

Therefore, in this register:

1. The **`Lock`** column is not prose — it holds a path, a `file:line`, or a commit SHA, and it is resolved mechanically.
2. A row may not read `BUILT` unless its `Lock` resolves. A ruling whose lock does not resolve reads `PARTIAL` at best.
3. The same commit that records a ruling adds its both-directions test. **A rule without a lock is not yet a rule** — which is why `Lock` is a column here and was prose in Spec 124.
4. Ask rows (§6) carry a recommended default and a reversibility note, never a lock — an Ask is not a ruling.
