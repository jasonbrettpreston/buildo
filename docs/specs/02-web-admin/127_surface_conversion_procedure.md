**This spec is the mirror of Spec 123 for surfaces.** Spec 126 says what a surface declares; this spec says how an existing surface *becomes* one — the assessment, the gate ladder, the commit form, the scorecard, the acceptance run, and the review panel. Spec 128 holds the durable policy and the ruling register.

## 1. The one rule that makes the rest work

**A surface's conversion is evidenced by artifacts, never by prose.** Every gate below is scored from a file that exists on disk — a descriptor, a golden capture pair, a validator run, a test id — and the scorecard is **generated by one command**, never hand-written. This is Spec 123 §1.1 inherited verbatim, and Spec 124 R-R's ruling with it: *a hand-written scorecard is not evidence.*

**What is generated vs what is authored:**

| Generated | Authored |
|---|---|
| the gate scorecard (S0–S9) · the policy-coverage matrix (Spec 128 rules 1–13) · the mirrored tables in §3/§4 below · the archetype eligibility table · the surface registry page | the descriptor · the `checks[]`/`invariants[]`/`plausibility[]` declarations · the assessment report's narrative sections · the Intent Ledger dispositions |

## 2. PH-0 — the per-surface boundary freeze

**Nothing is converted until its boundary is frozen in writing.** For ONE surface, enumerate:

| # | Frozen artifact | Source of truth |
|---:|---|---|
| 1 | every file the surface renders from — the route file, its components, its format helpers, its hooks | `git ls-files` + the import graph, **from the MAIN tree** (a worktree-isolated reviewer cannot see untracked files) |
| 2 | every contract it calls — **both idioms**: a hook import *and* a literal `fetchWithAuth('/api/…')` | the census's measured trap: five `(onboarding)` screens call `/api/user-profile` directly with no hook; a hook-only sweep returns the wrong number |
| 3 | every table those contracts read or write, with named columns | the CONTRACT descriptor's `database` block, asserted against `src/lib/db/generated/schema.ts` |
| 4 | every render state the surface can reach, and what the user sees in each | the archetype's required `states[]` |
| 5 | every event it emits today | `grep` against the `mobile/src/lib/analytics.ts` whitelist |
| 6 | every hand-written constant — label maps, field whitelists, order arrays, debounce values | `git blame` each one; this list feeds S3 |
| 7 | the surface's guards *and its contracts' auth class*, side by side | `route-guard.ts`'s `classifyRoute` **re-executed**, not read |
| 8 | the Target Spec line, filled from `docs/specs/00-architecture/00_system_map.md`'s owner row **first**, before the standard specs (126/127/128) are added | Spec 123 G0, inherited |
| 9 | `platforms[]` — which of `web` / `mobile` / `pdf` this surface serves | Spec 126 §2.1 |

**PH-0 for a NEW table (the Supabase half).** When the surface needs a table that does not exist, PH-0 additionally freezes **steps 1–2 of Spec 126 §6.1**:

1. **Declare** the table in the owning CONTRACT descriptor's `database.tables[]` — every column with SQL type, nullability and default; PK; FK targets; CHECK vocabularies as closed enums; the RLS block (`class` ∈ A/B/C/D, `owner_col`, per-role `grants`, `why_none` for every `none`); and **each index paired with the declared read that justifies it**.
2. **Claim the migration number by re-measuring** — `ls migrations/ | tail -1`, never by trusting a reserved range (Spec 122 §7.5's reservation has been broken three times, and its own text now says to re-measure).

Nothing may be written to `migrations/` at PH-0; the declaration is the deliverable.

## 2a. PH-1 — the Supabase schema landing

**PH-1 is skipped entirely for a surface that needs no new table** — which is every surface in the pilot's first commit, by design.

### 3.1 The two gates specific to a Supabase-touching conversion

| Gate | Criterion |
|---|---|
| **S-schema** | every declared column, type, nullability, index and RLS policy is asserted against the **live** catalog, both directions, with the RED canary proven — and the assertion reads `pg_policies` / the introspected types, **never the migration text**. Governed by Spec 128 rule 14 |

### 3.2 Scoring and the stopping rule

Inherited from Spec 123 §6 without modification: **ship at ≥14/17 with S6, S7 and S8 full; any zero in S6–S8 is a hard stop regardless of total; S9 is binary and adds no points.** Assessment is DONE for a batch when two consecutive independent passes produce zero new Intent Ledger entries and zero new class-A behaviours, and the gate score clears. **A stopping rule that cannot fire is not a stopping rule** — so the score is generated, and a missing artifact scores zero rather than being waived.

### 4.1 The role split that must not be relaxed

**A different party adjudicates than the one that discovered.** Spec 124 §4.2 makes this a *policy rule*, not merely a procedure step: the same pass may never both discover a fence or ambiguity and rule on its disposition. The adjudicator is named and dated in the assessment report. This applies to every Intent Ledger row at C2 and to every deviation.

### 4.2 The Intent Ledger vocabulary, unchanged

Every hand-written constant frozen at PH-0 step 6 is classified with the closed set: `preserved-in-runner | preserved-in-validator | preserved-in-compute | encoded-as-descriptor-field | encoded-as-deviation | knowingly-retired`. For surfaces, read "runner" as *the SurfaceEngine*, "validator" as *`surface-validate.mjs`*, and "compute" as *the server-side projection assembler*.

**The worked example, live in this tree:** `mobile/src/lib/parcelCostFormat.ts:14 COST_LINE_ORDER` is a transcription of `scripts/lib/parcel-cost.js:77 PARCEL_COST_LINES` with a different order and **no lock**. Its disposition is `encoded-as-descriptor-field`, and the cutover deletes it. The admin twin of the same constant already shipped broken once — three cost lines rendered *"n/a — not computable"* on 100% of 486K parcels with a green UI suite, because the fixture was authored against the wrong keys.

### 4.3 The golden capture PAIR

Two artifacts per named state, **both required**, under `surfaces/__goldens__/<surface>/<state>.json`:

1. an **API response fixture** — what the contract returned;
2. a **rendered-tree snapshot** — what the archetype renderer produced from it.

Carrying `{ harness, spec, surface, archetype, platforms, state, git_head, request, response_fixture, projection, rendered_tree, a11y_tree, emitted_events, nondeterminism[], normalised[], source_fingerprint, fingerprint_files[] }`. The fingerprint spans **descriptor + contract descriptor + the archetype component + the format helpers**, so any of those changing forces a recapture — the `golden-fingerprint.infra.test.ts` mechanism, inherited (Spec 124 R-C).

**The non-determinism inventory is declared BEFORE the first diff.** A diff explained after the fact by a source of non-determinism nobody wrote down is not an explanation.

### 4.4 Batching by archetype

**Compressed form is not legal from day one.** Spec 123 §7's R-PACE-1 requires **two** surfaces of an archetype landed in the full form before further surfaces of that archetype may land in 3 commits — and Spec 124 R-AH then makes the compressed form the **default**, not an option, with a full-form plan legal only when the assessment states a reason.

**Two consequences of the batch order above, stated rather than discovered later.** `SponsorSlot` is the estate's **only** SLOT member (n=1), and the pilot converts it — so after B1 the SLOT archetype has **one** proven member and stays in full form; the remaining SLOT placements in B5 are not eligible unless a second member lands first. Likewise B1 contains **no** SEARCH member, so **SEARCH is not eligible at B2** and `parcel_search` converts in full form. Eligibility is declared data precisely so these two rows are read off a table rather than assumed from "we have done a few by now".

Eligibility is **declared data, not a claim**: a per-archetype row recording the two proven members and the commits that landed them, generated into the conversion roadmap. An archetype with one member is not eligible, and a plan that assumes otherwise fails its own scorecard.

**Scope first: this table batches `parcel_product`, `parcel_admin` and `platform_shared` ONLY.** Spec 126 §2.0 partitions the estate into four programme scopes; `estate_other` — lead generation, the flight center, the lead feed, permit and job detail, builders — is **inventory and seam only**, fenced by Spec 128 R-03, and every one of its rows carries `programme.phase: "not_scheduled"`. It converts under this same procedure in a later programme. A batch below that names a scope-D surface is a scope error, not an ambitious plan.

## 5. The per-surface scorecard

Generated by `node scripts/surfaces/surface-validate.mjs --surface=<id> --write`, written into the assessment report, and asserted by a conformance test — the `step-validate.mjs` / `step-conformance.infra.test.ts` pair, mirrored. It carries:

- the S0–S9 scores, each traced to the artifact that produced it;
- the Spec 128 rules-1–13 policy-coverage matrix, per rule, with `enforced` / `enforced-red` / `PROSE-ONLY GAP`;
- the fast invariants (no DB, no vitest): the descriptor has a `SPEC LINK:` header · every declared `config.logic_variables[].name` has a `scripts/seeds/logic_variables.json` entry · every `identity.archetype` resolves in the registry for every declared platform · every `states[]` entry has a golden pair · every golden's `source_fingerprint` matches the current fingerprint files · `surface.guards.session` agrees with every referenced contract's `auth_class` · an archetype past two members declares either the compressed marker or a literal full-form reason;
- the **P3 footprint**, stated not gated: descriptor bytes, notes bytes, `checks[]` row count, and the newest golden pair's byte size — plus, for any declared check that queries, its `cost_ms` measured **against production scale and production heap state**, never a local single sample (the EP-D17 extension).

## 6. The acceptance run

A conversion is accepted when, in one command and one commit:

1. `node scripts/surfaces/surface-validate.mjs --surface=<id> --write` scores ≥14/17 with S6–S8 full;
2. the golden differential shows **zero unexplained diffs**, every explained diff pointing at a Defect Ledger id;
3. every declared lock is proven **both directions** — red on the old shape, green on the new, red landing at the *designed* assertion;
4. `npm run typecheck`, `npm run lint`, and `npx vitest related <changed files> --run` pass (the admin Pre-Commit Gauntlet);
5. `generate-spec-mirror.mjs --check` is clean;
6. where PH-1 ran, `BUILDO_TEST_DB=1 npm run test:db` passes the schema and RLS locks;
7. `node scripts/generate-system-map.mjs` has been re-run if any entry in the Target Files list changed;
8. the cutover commit **registers the surface, deletes its `pending` entry, retires the hand-written constants, and commits the generated scorecard — all in the same commit** (Spec 124 R-K's mutual-exclusion discipline, mirrored).

**A stage-gated surface's tests are declared data, never a code skip** — R-K inherited: a `pending` entry names the surface, and every genuinely-red claim is `it.fails(...)` tied to that entry, flipped to plain `it()` in the cutover commit.

## 7. The review panel

Composed per Spec 08 §6.4 (Admin column) and §10.3's rule — *pick the domain roster, then drop roles whose **subject-matter** trigger the change does not hit; the trigger is subject-matter, not altitude.* Both altitudes are mandatory.

| Altitude | Roster | Notes |
|---|---|---|
| **PLAN** (reads `.cursor/<plan>.md` + the live tree/DB, before code) | Gemini + DeepSeek **as a lens set** (spec / security / idempotency / error-paths, each adjudicated by a grounder) + Code Reviewer + **Integration (standing member, MAIN tree)** + Schema-Fidelity + Ground-truth → Compliance | Integration is standing for Admin WF1/WF2: it verifies the plan's wiring, schema-seeding and migration assumptions against reality. Schema-Fidelity fires on every PH-1. |
| **OUTPUT** (reads the diff + re-run values) | Integration + Code Reviewer + Schema-Fidelity + Compliance + **Regression Guardian** (whenever the diff modifies or deletes existing code — which a conversion does by definition) + Security (money / auth / PII / admin surfaces) + User-Advocate + Round-2 adjudication | Guardian runs in the MAIN tree: it needs full `git log`/`blame` plus the uncommitted diff, and it must **state the fence for every deletion**. |

**Substrate rule (Spec 08 §10.2, ratified):** a seat's agent type must grant the tools its lens requires. A seat spawned on a tool-less substrate does not fail loudly — it silently downgrades to static reasoning and returns confident PASS verdicts it never executed. **Check each seat's declared `tools:` against its lens before composing the panel.**

**Frontend nuance (Spec 08 §11.5-FE):** §11.1's "execute every executable claim" applies to this domain's executable surface — `npm run typecheck`, the `*.ui.test.tsx` render suites, the golden pairs, a running app. Visual and interaction-quality claims are **not** executable; do not demand a query of a design judgment. Fold-validation is recommended-lean (one validator) for multi-round frontend folds and mandatory where a fold asserts executable facts.

**Reviewer gotcha, measured:** worktree-isolated reviewers **cannot see untracked files**. Every inventory claim — "these are the surfaces", "these are the constants" — must be verified from the **MAIN tree**.

### 8.2 How a reviewer reads it

1. **§1 Summary** — counts by kind, by archetype, by status. This is where an archetype with one member (and therefore no R-PACE-1 eligibility) is visible, and where "generated" vs "hand-written" is a number rather than an intention.
2. **§2 Entries**, grouped by archetype then platform. Each entry leads with a **plain-language paragraph** — what it is, who uses it, what it shows or changes — so the registry is readable by someone who does not read TypeScript. Then its gate, its edges (`Calls` for a surface, `Called by` for a contract — **a contract with no caller renders as `nothing — orphan contract`**), the components it owns, the states it can reach, the tables it touches with their real columns, a collapsed 21-category answer table, and its links.
3. **§3 Tables & fields index** — every table any entry touches, its columns, and which surfaces read or write it, split **existing** vs **net-new**. This is the answer to *"what does this feature need from the database?"* without reading a migration.
4. **§4 Unowned components** — Spec 128 **R-13**'s totality, second direction. Every component file under `src/components/**` or `mobile/src/components/**` must appear in exactly one surface's `owns.components[]`. A file claimed by **two** surfaces makes the generator throw; a file claimed by **none** is listed here, and **this section must be empty**.

### 8.3 The three properties that make it reviewable rather than decorative

- **`_unanswered — assessment_` is a state, not a hole.** A category nobody has assessed says so. It is the difference between a descriptor that is incomplete and a document that is vague.
- **`_unmeasured_` is never a guess.** Where a sweep could not determine a fact, the cell says `_unmeasured_`. A plausible-looking value nobody measured is the defect this whole programme exists to retire — it is how "25 `track()` events" became 46 and "11 Maestro flows" became 12.
- **Nothing in it is hand-written.** Correcting the registry means correcting the census and regenerating. The `--check` arm makes a stale artifact a failure, and the RED canaries prove that arm fires.

### 8.4 Descriptors are the transport — and the shards are temporary

**A census row is not a reporting format. It is a draft descriptor**, in the exact JSON shape `scripts/surfaces/_schema/surface.schema.json` defines — same category keys, same closed vocabularies, same `identity` / `platforms` / `owns.components[]` / `inputs.tables` / `outputs.tables` / `guards` / `emits.ledger_events` / `checks[]` / `evidence` / `spec_refs` / `producing_steps`. Every row is **AJV-validated against that schema on every generator run**; a row that does not validate refuses the build rather than rendering.

So there is **no re-keying step** between the thing a human reviews and the thing the engine reads:

| Command | What it does |
|---|---|
| `node scripts/violations/generate-surface-registry.mjs` | renders the registry from the descriptors |
| `… --emit-descriptors` | writes one file per row to `scripts/surfaces/<kind>/<id>.descriptor.json` — the location the SurfaceEngine, the Supabase seeder and the checkers read, mirroring the pipeline's `scripts/<step>.descriptor.json` convention — **and** regenerates the TypeScript types and the runtime validator from the schema |
| `… --check` | fails on registry drift **and** on descriptor drift, in **both** directions: a planned file that is missing or stale, and an emitted file no census row declares |

**The hand-over, stated before it happens.** The shards under `scripts/surfaces/_schema/census/` exist for one reason: six researchers editing six files instead of one. When every row's `unresearched fields` badge reads **0**, the emitted descriptors become the source of record and **the shards are retired in a single commit**. The both-directions `--check` is what makes that swap safe — it proves the two representations are equal at the moment of the change, so the retirement is a deletion rather than a migration. The `x-draft` block each row carries (raw file list, line counts, the shard it came from) is retired with them; nothing downstream may read it.

### 8.5 Its place in the procedure

The registry is a **PH-0 input**, not a PH-0 output: §2's boundary freeze is filled *from* it (which contracts, which tables, which components), and the conversion commit updates the census row for the surface it converts — `owns.components[]`, the category answers that stop being `_unanswered_`, the states that gain goldens. A conversion that does not move its registry row has not been recorded.

## 9. Review procedure — the fine-tooth comb — added 2026-09-15

**Reviewing 91 entries by reading them is not a method.** A reviewer who improvises a different pass per surface finds different things on each, and nobody can say afterwards what was checked. So the pass is fixed, the questions are fixed, and the answers are generated from the descriptor with their evidence attached.

### 9.1 The artifact

`docs/reports/generated/127-surface-review-queue.md` — one **review card** per entry in scopes A, B and C (Spec 126 §2.0), rendered in **build order**, so reviewing top to bottom reviews a dependency before the things that depend on it. Scope D is not queued: it is inventory, not programme.

Generated by the same generator as the registry, from the same census, and drift-locked by the same test. It is not a checklist someone maintains — it is a projection, and a stale one fails `--check`.

### 9.2 The nine questions, asked of every entry

1. **What does it do, and for whom?** — the plain-language purpose. If it does not describe something a real person does, stop: a descriptor built on it will be wrong in the same way.
2. **Which tables and columns, produced by which step?** — the full lineage, with the chain position of the producing step.
3. **Which contracts, and who calls them?** — for a contract, *nothing calls it* is rendered as such.
4. **What gate, role or entitlement stands in front of it?** — session, RLS class, entitlement product, role.
5. **What archetype, and why that one?** — the archetype decides which fields are mandatory; a wrong one demands the wrong fields and excuses the right ones.
6. **Is any behaviour here lead-gen leakage?** — behaviour belonging to the other product that merely lives in this file today. **Recorded, never deleted.**
7. **Does it match its owning spec section?** — and where the measured behaviour contradicts what a user would expect, the product question is attached rather than resolved.
8. **What is still unresearched?** — a count, not an impression.
9. **What would removing it delete?** — its owned components, and any table it is the sole reader of. This is what makes a feature module a unit of deletion rather than a folder name.

### 9.3 Recording the verdict

Each descriptor carries `programme.review`:

```jsonc
"review": { "status": "reviewed", "reviewer": "…", "date": "2026-09-…", "notes": "…" }
```

`status` is `unreviewed` | `reviewed` | `needs_change`. Set it **in the census shard** and regenerate; the queue renders the current state and its header tallies it. **The verdict lives in the descriptor, not in anyone's memory and not in a comment on a pull request.**

A `needs_change` card states what must change in `notes`. It does not block the queue — it blocks the entry's conversion, which is Spec 127 §2's PH-0 input.

### 9.4 What the reviewer is NOT asked to do

Not to propose a design, not to fix what they find, and not to delete a behaviour they judge misplaced. Leakage and product questions are **recorded with evidence and routed** — to the defect ledger, or to the operator as a ruling (Spec 128 §4). The reviewer's discretion begins and ends at *is this record true*.
